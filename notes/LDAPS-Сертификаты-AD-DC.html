LDAPS и TLS-сертификаты на Samba AD DC

Суть

Active Directory использует LDAP для чтения и записи, и по умолчанию LDAP-соединения не шифруются; чтобы защитить трафик, применяют SSL/TLS — тогда LDAP-клиенты (SSSD, Keycloak, системы мониторинга, сетевые устройства и т. д.) подключаются по LDAPS на порт 636. По странице вики, поддерживаемые версии Samba (4.11.0 и новее) требуют GnuTLS, поэтому LDAP доступен по умолчанию; при первом запуске Samba сама создаёт приватный ключ, самоподписанный сертификат и CA-сертификат со сроком жизни 700 дней. В продакшене его заменяют собственным или выданным доверенным CA сертификатом с CN = FQDN контроллера; параметрами tls * в smb.conf управляют файлами ключа, сертификата и CA, а с Samba 4.19 сертификаты можно перезагружать без перезапуска службы.

Ключевое

Общие сведения (страница «Configuring LDAP over SSL (LDAPS) on a Samba AD DC»)

  • Поддерживаемые версии Samba (4.11.0 и новее) требуют GnuTLS, поэтому LDAP доступен по умолчанию.
  • Приватный ключ должен читаться без пароля, то есть быть незашифрованным (без passphrase).
  • Все файлы, которые использует Samba, должны быть в формате PEM (Base64-encoded DER) — содержимое между строками вида -----BEGIN CERTIFICATE----- и -----END CERTIFICATE-----.
  • Промежуточные сертификаты (intermediate certificates) добавляются в файл cert.pem после серверного сертификата.
  • Все параметры, начинающиеся на tls, задаются в секции [global] файла smb.conf. На странице сказано: «After any changes, you will have to restart Samba» — после любых изменений требуется перезапустить Samba (но с версии 4.19 сертификаты можно перезагружать без рестарта, см. ниже).
  • Пути к файлам параметров tls* отсчитываются от private dir, если путь не начинается с / (man smb.conf(5)); значение по умолчанию private dir = ${prefix}/private. Примеры на странице вики даны для самособранной Samba: /usr/local/samba/private/tls/.

Параметры smb.conf для LDAPS

Значения по умолчанию — из man-страницы smb.conf(5) (раздел «current»; на момент проверки — версия 4.25.0):

Параметр По умолчанию Назначение
tls enabled yes Если yes, Samba использует TLS везде, где возможно.
tls keyfile tls/key.pem Файл (PEM) с приватным RSA-ключом. Ключ должен быть доступен без пароля (не зашифрован).
tls certfile tls/cert.pem Файл (PEM) с RSA-сертификатом, используемым как TLS-серверный сертификат. С версии 4.21 в man-странице явно сказано: при необходимости может также содержать дополнительные промежуточные сертификаты, отправляемые во время TLS-рукопожатия.
tls cafile tls/ca.pem Файл (PEM) с CA-сертификатами корневых CA, которым доверяют подписывать сертификаты, либо промежуточными CA-сертификатами.
tls priority NORMAL:-VERS-SSL3.0 Строка приоритетов (GnuTLS cipher priority string), которая дописывается к списку приоритетов GnuTLS по умолчанию; протокол SSL 3.0 дополнительно отключён.
tls verify peer as_strict_as_possible Насколько строго клиент проверяет сертификат и имя узла-пира (см. значения ниже).
tls crlfile (пусто) Файл со списком отзыва сертификатов (CRL).
tls trust system cas no Доверять системному набору доверенных CA. Man-страница предупреждает: это означает доверие всем CA, установленным в системе.
tls ca directories значения по умолчанию нет Список каталогов с CA-сертификатами (PEM).
ldap server require strong auth yes Требует подписи или подписи и шифрования LDAP-трафика; значения и их смена в 4.21 — см. ниже.

Значения tls verify peer (в порядке возрастания строгости; man smb.conf(5)):

  • no_check — сертификат не проверяется вообще, что допускает тривиальные man-in-the-middle-атаки;
  • ca_only — проверяется подпись от CA, заданного в tls cafile (либо через tls ca directories или tls trust system cas); требуется хотя бы один валидный CA-сертификат, проверяется также срок действия, а при настроенном tls crlfile — и отзыв;
  • ca_and_name_if_available — то же плюс проверка имени узла, если оно передано прикладным уровнем и не является IP-адресом;
  • ca_and_name — имя узла обязательно, проверяется даже IP-адрес;
  • as_strict_as_possible — все предыдущие проверки плюс обязательное требование настроенного tls crlfile; «future versions of Samba may implement additional checks».

Автогенерируемый самоподписанный сертификат (по умолчанию)

При первом запуске Samba сама создаёт приватный ключ, самоподписанный сертификат и CA-сертификат:

  • /usr/local/samba/private/tls/ca.pem
  • /usr/local/samba/private/tls/cert.pem
  • /usr/local/samba/private/tls/key.pem

Сертификаты действительны 700 дней после создания — срок жизни при автогенерации жёстко зашит в source4/lib/tls/tlscert.c. Проверка по исходнику (тег samba-4.19.0, source4/lib/tls/tlscert.c): строка 31 #define LIFETIME 700*24*60*60, строка 51 time_t activation = time(NULL), expiry = activation + LIFETIME;. Там же видно, что генерация пропускается, если хотя бы один из трёх файлов уже существует (строка 54), CN берётся из имени хоста (строки 87–88 и 109–111), а приватный ключ сохраняется с правами 0600 (строка 144); размер ключа RSA — 4096 бит, а в режиме FIPS 140 — 3072 бита (строки 33–34).

По умолчанию TLS включён (tls enabled = yes), используются перечисленные файлы, что соответствует таким параметрам smb.conf (дословно со страницы):

tls enabled  = yes
tls keyfile  = tls/key.pem
tls certfile = tls/cert.pem
tls cafile   = tls/ca.pem

Замена: собственный самоподписанный сертификат

  1. Перейти в каталог, где будут храниться ключ и сертификат:
# cd /usr/local/samba/private/tls/
  1. Создать приватный ключ (2048 бит) и самоподписанный сертификат на 1 год (-nodes — ключ без пароля). Страница подчёркивает: при запросе Common Name обязательно указать FQDN контроллера, для которого создаётся сертификат, — $(hostname -f):
# openssl req -newkey rsa:2048 -keyout myKey.pem -nodes -x509 -days 365 -out myCert.pem
  1. Ограничить права на приватный ключ:
# chmod 600 myKey.pem
  1. Добавить в smb.conf (дословно со страницы):
tls enabled  = yes
tls keyfile  = tls/myKey.pem
tls certfile = tls/myCert.pem
tls cafile   =
  1. Перезапустить Samba (либо на 4.19+ перечитать сертификаты через smbcontrol, см. ниже).

Замена: сертификат от доверенного CA

  1. Создать 2048-битный серверный ключ:
# openssl genrsa -out myKey.pem 2048
  1. Сгенерировать запрос на сертификат (CSR); при запросе Common Name снова указать FQDN контроллера $(hostname -f):
# openssl req -new -key myKey.pem -out myCSR.pem

  1. Получить у CA доверенный сертификат и положить его в каталог с ключом (в примере — myCert.pem). Если CA требует промежуточные сертификаты, их тоже кладут в тот же каталог (в примере — myIntermediate.pem).

  2. Добавить параметры в smb.conf (дословно со страницы; пробел перед .pem — опечатка источника):

tls enabled  = yes
tls keyfile  = tls/myKey.pem
tls certfile = tls/myCert.pem
tls cafile   = tls/myIntermediate .pem  # if not required, set empty
  1. Перезапустить Samba.

Для версии 4.21 и новее man-страница прямо разрешает класть промежуточные сертификаты в tls certfile — они будут отправлены в TLS-рукопожатии; в man-страницах 4.19/4.20 этот текст отсутствует. Для самоподписанных вариантов проверка выполняется по CA-файлу: страница вики даёт команды openssl verify ... -CAfile и s_client ... -CAfile (см. «Проверка сертификата»).

Перезагрузка сертификатов без перезапуска (Samba 4.19+)

Release notes 4.19.0, раздел «Samba AD TLS Certificates can be reloaded»: TLS-сертификаты LDAP-сервера AD DC раньше читались только при запуске, поэтому по истечении срока действия требовался перезапуск Samba, прерывающий обслуживание. Теперь их можно перечитать «на лету»:

 smbcontrol ldap_server reload-certs

Man-страница smbcontrol(1) (сообщение reload-certs): «Instruct the LDAP server of a Samba AD DC to reload the TLS certificates protecting ldaps:// connections. This message can only be sent to ldap_server.» — команда посылается только процессу/цели ldap_server.

Ужесточение: ldap server require strong auth, SASL над TLS и channel bindings

  • Опция ldap server require strong auth появилась вместе с исправлением CVE-2016-2112 (уязвимы Samba 3.0.0–4.4.0). Публичные security-релизы — 4.4.2, 4.3.8 и 4.2.11: «4.4.2, 4.3.8 and 4.2.11 have been issued as security releases to correct the defect… Note that Samba 4.4.1, 4.3.7 and 4.2.10 were privately released to vendors, but had a regression». Гайд Updating Samba ведёт отсчёт опции от 4.4.1/4.3.7/4.2.10 — это ветки, где она появилась впервые, но безопасным ориентиром при обновлении считайте исправленные 4.4.2/4.3.8/4.2.11 (подробнее — Харденинг Samba AD DC, Обновление Samba). Тогда значениями были no, allow_sasl_over_tls и yes, по умолчанию yes; до этого LDAP-сервер не умел требовать строгую аутентификацию.
  • Страница вики (проверена 13.10.2026; под изменения 4.21 её текст, судя по всему, не обновлён) констатирует: Samba не реализует LDAP channel binding, как того требуют «2020 LDAP channel binding and LDAP signing requirements for Windows»; ещё в 2016 году с CVE-2016-2112 было признано, что при отсутствии криптографической связи между ответом NTLM/Kerberos-токеном и TLS-слоем возможна relay-атака. Samba просто отклоняет такие сессии по умолчанию. Для совместимости есть значение allow_sasl_over_tls (или no), но на странице написано: «Do not set these options». Безопасная альтернатива — шифрование LDAP-слоя средствами NTLM или Kerberos (SASL encryption): оно криптографически привязано к аутентификации, и MITM-релей не может изменить сообщения.
  • С версии 4.21 LDAP-сервер поддерживает SASL-binds (kerberos или NTLMSSP) поверх TLS (ldaps или starttls) с корректными TLS channel bindings. Установки, где раньше требовалось ldap server require strong auth = allow_sasl_over_tls, теперь, скорее всего, могут использовать значение по умолчанию yes. Если SASL-binds без корректных channel bindings всё же нужны, следует использовать allow_sasl_without_tls_channel_bindings; значение allow_sasl_over_tls теперь лишь alias этого значения, при каждом старте samba и [samba-tool ]testparm выводится предупреждение, и в будущих версиях alias будет удалён. Это аналог LdapEnforceChannelBinding в ветке HKLM\SYSTEM\CurrentControlSet\Services\NTDS\Parameters на Windows. Все клиентские утилиты, использующие ldaps, также теперь включают корректные channel bindings.
  • Man-страница smb.conf(5) (4.21+) сопоставляет значения с Windows: no — LdapEnforceChannelBinding=0; allow_sasl_without_tls_channel_bindings — LdapEnforceChannelBinding=1 (простые и SASL-binds без sign/seal поверх TLS, отсутствие channel bindings игнорируется; незашифрованные соединения — только SASL с sign или seal); yes — LdapEnforceChannelBinding=2 (только simple binds и SASL-binds с корректными TLS channel bindings поверх TLS; незашифрованные соединения — только SASL с sign или seal).
  • Смежное требование 4.19: смена пароля (unicodePwd/userPassword) на AD DC по незашифрованному или только подписанному LDAP-соединению отклоняется — нужна шифрованная LDAP-сессия. Важная оговорка из release notes 4.19: если Samba стоит за TLS-фронтендом или балансировщиком нагрузки, запрос будет считаться открытым текстом.
  • Клиенты: в 4.21 параметр client ldap sasl wrapping получил значения starttls (STARTTLS на TCP-порт 389) и ldaps (TLS напрямую на TCP-порт 636); это касается winbindd и net ads, которым LDAP нужен для связи с DC. Для корректной проверки сертификата требуется настроить доверие минимум одним из способов: tls trust system cas, tls ca directories или tls cafile; также важны tls verify peer и tls crlfile.

Ограничение TLS-протоколов

Параметр tls priority принимает строку приоритетов GnuTLS (описание в GnuTLS Priority-Strings), что позволяет отключать устаревшие шифры/протоколы. GnuTLS сам управляет набором шифров по умолчанию, но SSLv3 в Samba дополнительно отключён. Пример со страницы (предполагает, что библиотека уже отключает SSLv3, а также отключает TLS 1.0 и 1.1):

tls priority = NORMAL:-VERS-TLS1.0:-VERS-TLS1.1

Проверка сертификата

Просмотреть содержимое сертификата:

# openssl x509 -in /usr/local/samba/private/tls/myCert.pem -noout -text

Локальная проверка (для самоподписанного сертификата ожидаемо error 18 ... self signed certificate, затем OK):

# openssl verify /usr/local/samba/private/tls/myCert.pem

Если в smb.conf используется CA-файл — проверка с ним:

# openssl verify /usr/local/samba/private/tls/myCert.pem -CAfile /path/to/ca-file.pem

Проверка «снаружи» по TCP (порт 636; выход из s_client — [Ctrl]+[C]):

# openssl s_client -showcerts -connect dc1.samdom.example.com:636

Вариант из источника с CA-файлом (на странице указан localhost:636):

# openssl s_client -showcerts -connect localhost:636 -CAfile /path/to/ca-file.pem

В выводе s_client для самоподписанного сертификата на странице показан Verify return code: 18 (self signed certificate).

Подводные камни

  • Страница вики требует перезапуска Samba после смены сертификатов — это верно для версий старше 4.19 (в них сертификаты читались только при старте). Начиная с 4.19 используйте smbcontrol ldap_server reload-certs и не прерывайте работу службы.
  • Автогенерируемый сертификат живёт 700 дней; по истечении в версиях старше 4.19 потребовался бы перезапуск Samba — планируйте замену на собственный/корпоративный сертификат заранее.
  • Приватный ключ не должен быть зашифрован (без passphrase) — и в вики, и в man smb.conf(5); ключ должен иметь ограниченные права (в примере chmod 600 myKey.pem).
  • CN сертификата обязан быть FQDN контроллера ($(hostname -f)), иначе проверка имени у клиентов не пройдёт.
  • Промежуточные сертификаты: вики предписывает дописывать их в cert.pem после серверного; в man-страницах 4.19/4.20 о промежуточных сертификатах в tls certfile речи нет — это явно задокументировано только с 4.21.
  • allow_sasl_over_tls с 4.21 — устаревший alias, вызывающий предупреждение при старте samba и в testparm; используйте yes (или allow_sasl_without_tls_channel_bindings, если иначе нельзя).
  • tls verify peer = no_check не проверяет сертификат вообще (допускает MITM), а as_strict_as_possible требует настроенного tls crlfile — выбирайте значение осознанно.
  • tls trust system cas = yes означает доверие абсолютно всем CA, установленным в системе.
  • Если Samba AD DC стоит за TLS-фронтендом или балансировщиком, запрос на смену пароля по LDAP считается незашифрованным и отклоняется (release notes 4.19).
  • Автогенерация сертификатов пропускается, если существует хотя бы один из трёх файлов (key.pem/cert.pem/ca.pem); при этом в лог пишется TLS autogeneration skipped - some TLS files already exist — «пустые» или частично подложенные файлы не будут догенерированы.
  • Включённый системный режим FIPS влияет на размер ключа автогенерируемого сертификата (3072 вместо 4096 бит) и, как отмечают release notes, может ломать другие протоколы Samba.
