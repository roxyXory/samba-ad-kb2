Writing Torture Tests — написание torture-тестов Samba

Суть

Страница описывает, как писать новые torture-тесты для фреймворка smbtorture, входящего в состав Samba: это мощный инструмент для проверки неочевидных частей протоколов Windows и реакции на них разных серверных реализаций, включая саму Windows. Написание torture-тестов — бесценный способ выяснить поведение сервера в нестандартных сценариях: до публикации документации по протоколам Microsoft smbtorture был единственным способом узнать, как Windows-сервер отвечает на легальные пакеты, которые штатный клиент Windows не отправляет. Страница даёт гайдлайны по разработке новых тестов и сосредоточена на добавлении их в коллекцию source4/torture.

Ключевое

Сначала подумайте про Python или cmocka

  • Не каждый новый тест обязан быть частью бинарника smbtorture4.
  • Python: если тестируемый протокол — DCERPC, PIDL уже автогенерирует для него Python-биндинги; LDAP легко доступен через LDB. Как писать новые Python-тесты — описано на странице Writing Python Tests.
  • cmocka: интегрирован в Samba и выводит Subunit. Позволяет собирать небольшие самодостаточные тестовые бинарники для юнит-тестирования кода на C (тогда как smbtorture больше подходит для протокольных тестов).

Структура каталога source4/torture

  • basic — исходные SMB-тесты, перенесённые из каталога source/torture; используют обёртки smbcli_*() с абстрагированным API. Тесты в основном касаются старых аспектов SMBv1 и считаются легаси — новые тесты сюда по возможности не добавлять.
  • raw — SMBv1-тесты, проверяющие почти все аспекты протокола файлового доступа манипуляцией сырых битов каждого пакета. Большинство новых тестов корректности SMBv1 добавляется сюда.
  • smb2 — тесты корректности SMBv2; как и raw, задают каждый отдельный бит в каждом пакете. Новые SMBv2-тесты добавлять сюда.
  • rpc — тесты различных DCE/RPC-сервисов, реализуемых Samba.

Лучшие практики

Проще всего добавить новый тест, скопировав существующий и изменив его поведение. Однако все новые тесты должны следовать правилам ниже — даже в ущерб существующей структуре кода файла.

Вывод сообщений. printf() использовать нельзя: вместо него — torture_comment() (для предупреждений — torture_warning()). Разные фронтенды torture, включая Samba build farm, могут форматировать или игнорировать текст, идущий от тестов; функция torture_comment это обеспечивает.

Фиксация результата. Старые тесты просто возвращали false при неудаче. Теперь у каждого теста есть состояние torture_result, которое должно выставляться одним из значений:

enum torture_result {
        TORTURE_OK=0,
        TORTURE_FAIL=1,
        TORTURE_ERROR=2,
        TORTURE_SKIP=3
};
  • Проще всего задавать его макросами torture_assert_*() из lib/torture/torture.h — они выставляют состояние torture_result и возвращаются из функции.
  • Если при неудаче нужен cleanup (например, удаление тестовых файлов), есть варианты torture_assert_*_goto() — они выполняют переход на метку вместо выхода из функции.
  • Допустимы и собственные макросы CHECK_*(), оборачивающие функцию torture_result() — оба способа приемлемы.

Тестовые наборы (suites). Все новые тесты добавляются только в под-набор: например, новый locking-тест каталога raw — в файл lock.c с записью в инициализирующей функции torture_raw_lock(). Это позволяет запускать отдельные тесты вида RAW-LOCK-ASYNC. В верхнеуровневые наборы (RAW, BASE) новые тесты добавлять нельзя.

Задание поведения целевого сервера. Не все серверы поддерживают все аспекты протоколов Windows; набор тестов должен оставаться гибким, давая максимальное покрытие при вариативности поведения цели. Для сервера без поддержки документированной возможности задаётся конфигурационный параметр, меняющий проверку результата в тесте. Пример — параметрическая опция torture:sacl_support, определённая в source4/torture/smbtorture.h; поскольку параметрическая конфигурация сравнивает строковые имена, «определение» параметра — просто комментарий:

/* torture:sacl_support
 *
 * This parameter specifies whether the server supports the setting and
 * retrieval of System Access Control Lists.  This includes whether the server
 * supports the use of the SEC_FLAG_SYSTEM_SECURITY bit in the open access
 * mask.*/

Целевые серверы без такой возможности выставляют параметр в false в source4/torture/smbtorture.c:

        } else if (strcmp(target, "onefs") == 0) {
                lp_set_cmdline(cmdline_lp_ctx, "torture:sacl_support", "false");
        }

Затем в тестах, где результат зависит от поддержки возможности, параметр проверяется — например, в source4/torture/basic/denytest.c:

        /* Skip all SACL related tests. */
        if ((!torture_setting_bool(tctx, "sacl_support", true)) &&
            ((cxd->cxd_access1 & SEC_FLAG_SYSTEM_SECURITY) ||
             (cxd->cxd_access2 & SEC_FLAG_SYSTEM_SECURITY)))
                goto done;

Запуск тестов

Полный прогон — make test из каталога source3 или source4, но он запускает все наборы против Samba 3 или Samba 4, идёт долго, и сложно отследить конкретный тест. Обычно запускают одиночный тест (подмножество тестов в Samba 3 или Samba 4 — см. страницу make selftest).

Запуск RPC-SVCCTL из бинарника s4 smbtorture против Samba 3:

make test TESTS=samba3.posix_s3.rpc.svcctl

Переменная TESTS принимает wildcards и простые шаблоны — это запустит тот же RPC-SVCCTL:

make test TESTS=svcctl

У многих тестов есть под-тесты; все тесты DCE/RPC-интерфейса samr запускаются так (стартуют RPC-SAMR, RPC-SAMR-USERS, RPC-SAMR-PASSWORDS и т.д.):

make test TESTS=samr

Все тесты, запускаемые этим способом, должны быть определены в opt-in списках; все DCERPC-тесты smbtorture перечислены в source3/script/tests/test_posix_s3.sh.

Можно задать серверные опции конфигурации samba:

make test TESTS=samr INCLUDE_CUSTOM_CONF="lanman auth = no"

Запуск selftest с опциями smbd (переменные SMBD_OPTIONS, NMBD_OPTIONS, WINBINDD_OPTIONS):

make test SMBD_OPTIONS="-d10" TESTS=spoolss

Запуск smbtorture в selftest под valgrind:

make test TESTS="spoolss" VALGRIND="1" VALGRINDLOG="$(pwd)/smbtorture.%p.log"

Запуск демонов samba в selftest под valgrind (SAMBA_VALGRIND, SMBD_VALGRIND, NMBD_VALGRIND, WINBINDD_VALGRIND):

make test TESTS="spoolss" SMBD_VALGRIND="valgrind --leak-check=full --trace-children=yes --log-file=valgrind-%p.log"

Показ вывода теста (обратите внимание: для каждого теста данные будут дописываться в файл):

make test SMBD_OPTIONS="-d2" TESTS=spoolss SUBUNIT_FORMATTER="cat"

make test SMBD_OPTIONS="-d2" TESTS=spoolss SUBUNIT_FORMATTER="tee selftest.log"

Запуск теста с серверами в screen-сессиях:

TDB_NO_FSYNC=1 make -j testenv SELFTEST_TESTENV=nt4_dc SCREEN=1

Чтобы тесты шли быстрее, отключите синхронизации:

TDB_NO_FSYNC=1 make test TESTS=spoolss

Тестовое окружение

Есть два окружения: простое — для запуска клиентских команд, и такое, где к smbd и winbind подключается gdb. Всё перечисленное работает и для Samba 3, и для Samba 4.

make testenv SCREEN=1

С gdb, подключённым к smbd и winbind:

make gdbtestenv SMBD_OPTIONS="-d2" WINBIND_OPTIONS="-d2" SCREEN=1

В конкретном окружении:

make testenv SELFTEST_TESTENV=ad_dc SCREEN=1

Доступные окружения включают ad_dc, dc, nt4_dc, fileserver, customdc и другие; окружения описаны в файлах selftest/target/Samba*.pm.

Внутри testenv можно автоматически снимать pcap-файл, задав SOCKET_WRAPPER_PCAP_FILE:

export SOCKET_WRAPPER_PCAP_FILE=debug.pcap

Ручной запуск smbtorture

Тест winreg против Windows-машины (в исходнике места-подстановки выделены курсивом — IP Windows-машины, имя и пароль администратора):

bin/smbtorture4 ncacn_np:[''IP of Windows machine''] -U[''Admin username'']%[''Admin password''] RPC-WINREG

Актуальные версии Windows

На момент написания (конец 2016) Samba 4 явно не поддерживает Windows Server 2012 или Windows Server 2016; рекомендуется запускать тесты против Windows Server 2008R2 / Windows 7 и Windows Server 2008 / Windows Vista — тесты должны проходить против обоих серверов до коммита. Поведение Windows-сервера изначально считается эталонной реализацией, но у Windows тоже есть баги, поэтому может понадобиться параметризация проверки в зависимости от того, Windows это или другой целевой сервер (см. выше про Specifying Target Behavior).

Сбои make test

smbtorture используется фреймворками selftest и Samba3, и Samba4; тесты непрерывно гоняются на Samba Build Farm, предотвращая регрессии от нового кода. Поэтому перед коммитом нового теста в git важно проверить его поведение на существующих серверах Samba3 и Samba4 — проще всего прогнать make test для обоих. Если возникают сбои — заводятся баги в базе http://bugs.samba.org, чтобы разработчики сервера разобрались.

  • Фреймворк Samba3 — opt-in: добавленные тесты не запускаются автоматически.
  • Фреймворк Samba4 — opt-out: новый падающий тест немедленно вызывает сбои в Samba Selftest System.
  • Поэтому падающие тесты (после заведения багов) добавляются в файл в selftest/knownfail.d/ — так make test знает, что сбой ожидаем, и GitLab CI не поднимает тревогу.

Подводные камни

  • printf() в torture-тестах запрещён: фронтенды (включая Samba build farm) должны иметь возможность форматировать или игнорировать вывод — используйте torture_comment() и torture_warning().
  • Новые тесты нельзя добавлять в верхнеуровневые наборы (RAW, BASE) — только в под-наборы, иначе отдельные тесты вида RAW-LOCK-ASYNC нельзя будет запустить по отдельности.
  • Каталог basic — легаси для старых аспектов SMBv1; новые SMBv1-тесты кладут в raw, SMBv2-тесты — в smb2.
  • Samba4 selftest — opt-out: новый падающий тест сразу ломает CI. Сначала завести баг на bugs.samba.org, затем добавить тест в файл в selftest/knownfail.d/.
  • Samba3 selftest — opt-in: пока тест не внесён в opt-in список (для DCERPC-тестов — source3/script/tests/test_posix_s3.sh), он не запустится.
  • Тест должен проходить против Windows Server 2008R2 / Windows 7 и против Windows Server 2008 / Windows Vista до коммита; поддержка Windows Server 2012/2016 на момент страницы (конец 2016) явно не заявлена.
  • SUBUNIT_FORMATTER="tee selftest.log": данные дописываются в файл после каждого теста, а не перезаписываются.
