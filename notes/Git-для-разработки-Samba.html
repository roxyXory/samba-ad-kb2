Using Git for Samba Development (Creating a Samba patch series)

[!note] Страница «Using Git for Samba Development» в Samba Wiki сейчас является редиректом на «Creating a Samba patch series» — ниже конспект именно этого материала.

Суть

Страница описывает требования к качеству патчей и merge request'ов (MR) Samba: разработка строится вокруг «серии патчей», где каждый коммит делает одну вещь, самостоятельно компилируется и сопровождается тестом. Это не технический учебник по git — предполагается, что читатель уже владеет основами. Главная мысль: хорошо подготовленная серия патчей легко проходит Код ревью, а нематериализуемая (не bisectable) — не принимается вовсе.

Ключевое

Структура серии патчей

  • Разработка Samba сосредоточена вокруг серии патчей, которая затем становится merge request'ом.
  • Каждый git-коммит должен быть лаконичным и делать только одну вещь.
  • Каждая новая возможность (feature) или исправление бага должны включать второй коммит с тестом, проверяющим изменение.

Хорошее сообщение коммита

Сообщение коммита должно включать как минимум:

  1. Краткое резюме исправления/возможности с указанием версии Samba и компонента, затем пустая строка.
  2. Более подробное описание.
  3. Номер бага, если есть (обязателен для бэкпортов в выпущенную ветку — см. Планирование релизов Samba; сначала заводится баг).
  4. Описание для release notes, начинающееся с RN: — формулировкой, понятной администраторам.
  5. Тег Signed-off-by согласно политике авторских прав Samba (см. Код ревью).

Пример из источника (дословно):

s3:smbd: Add new funky shiny and groovy feature

The funky shiny and groovy feature has been added to
be able to do whatever you like. A typical usecase is the
following.

BUG: https://bugzilla.samba.org/show_bug.cgi?id=1
RN: Fix problem xyz.

Signed-off-by: Author <author@example.org>

Bisectability (возможность bisect)

  • Малые лаконичные коммиты позволяют запускать git bisect по истории и находить коммит, внёсший баг.
  • Каждый и каждый коммит должен компилироваться самостоятельно.
  • Ожидается, что каждый коммит ветки пройдёт полный CI; автоматической проверки нет, поэтому для крупных MR рекомендуется после каждого коммита локально запускать сборку и соответствующие тесты — использовать для этого git rebase.
  • MR, которые не являются bisectable, не могут быть приняты — даже если рецензенту предлагают оценивать серию по конечному результату.

«Расскажи историю» и «Полированные жемчужины»

  • MR — это история, рассказанная рецензенту. Важно, чтобы её рассказывали и описание MR, и сами патчи: описание MR со временем теряется, а коммиты остаются в истории.
  • Каждый коммит описывает один шаг: что меняется и почему; в значимом коммите — детали общей архитектуры или исправляемого бага.
  • Результат MR — как нитка жемчуга: каждая «жемчужина» (коммит) отполирована индивидуально; качество итога почти целиком определяется качеством каждого элемента. Хорошо изготовленная серия проходит code review «на ура».

Тесты

  • Тесты к изменениям включаются в MR отдельным коммитом.
  • Идеально (для частей Samba с основным make test): сначала вносится тест с записью в новом файле в selftest/knownfail.d/, покрывающей ожидаемый отказ; запись удаляется более поздним коммитом, когда проблема устранена. Так видно, что тест действительно покрывает изменение.
  • Не все части Samba используют эту систему: заметнее всего CTDB (см. «Подводные камни»).
  • Большинство тестов запускается командой make test из дерева исходников Samba.
  • Виды тестов:
    • smbtorture (написание torture-тестов — Написание torture тестов): каталог source4/torture, прямые протокольные тесты на C.
    • Python-тесты: для протокола DCERPC привязки Python уже автогенерируются PIDL; LDAP доступен через LDB.
    • cmocka-тесты: идеальны для юнит-тестов функций на C.
    • LDB: тесты в lib/ldb/tests, начиная с Samba 4.21 запускаются через make test с верхнего уровня.
    • CTDB: тесты — shell-скрипты в ctdb/tests, запускаются через make test внутри ctdb.

Git-процесс: centralised + forking

  • Samba лучше всего описывается централизованным git-процессом: ветки существуют только для мажорных релизов.
  • При этом разработка идёт в ветках либо частного репозитория (для новых разработчиков), либо общего репозитория разработки https://gitlab.com/samba-team/devel/samba — то есть фактически используется forking-процесс.

Rebase на origin/master

  • Разработчик начинает работу от master и часто выполняет:
git rebase origin/master
  • Изменения в конечном счёте всё равно должны встать на актуальный master, иначе после всей работы на code review их нельзя будет слить; GitLab и сам покажет в интерфейсе, что код не сливается.

Примеры

  • Плохой MR (реальный пример из другого open source проекта): 47 коммитов, заголовок не объясняет суть, итог — изменение одной строки кода. Такие 47 коммитов следовало перебазировать в один коммит и, вероятно, добавить тест.
  • Хороший MR: 2 коммита — первый с исправлением бага, второй с тестами. Заголовок конкретен (компонент, имя функции, краткое описание исправления), патч меняет только исправляемое (кроме тестов).

Подводные камни

  • Не-bisectable серии не принимаются: каждый коммит обязан компилироваться и, по ожиданиям, проходить полный CI самостоятельно; аргумент «оценивайте MR целиком» не работает.
  • Описание MR потеряется — в истории останутся только коммиты, поэтому «история» изменений должна быть видна из сообщений коммитов.
  • Бэкпорты в выпущенную ветку требуют номера бага — сначала заводится баг в bugzilla, потом патч.
  • Система selftest/knownfail.d/ работает не везде: основная — make test, но CTDB живёт по своим правилам (shell-тесты в ctdb/tests, запуск make test внутри ctdb).
  • Страница — не учебник по git: от читателя ожидается, что базовые понятия git он уже знает.
