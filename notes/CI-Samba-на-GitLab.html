Samba CI на GitLab

Суть

Страница описывает зеркало официального git-репозитория Samba на GitLab и общий репозиторий разработки с бесплатным CI: каждый push в определённым образом названную ветку запускает автоматическую сборку и прогон тестов — до открытия merge request. CI идёт на комбинации облачных VM и общих runner'ов GitLab.com. Оба репозитория:

  • Официальное зеркало: https://gitlab.com/samba-team/samba — против него открывают merge request'ы;
  • Общий репозиторий разработки: https://gitlab.com/samba-team/devel/samba — в него пушат ветки для прогона полного CI (форк на gitlab.com по умолчанию прогоняет не весь набор тестов).

Ключевое

Доступ

  • Члены Samba Team — просят доступ в командном списке рассылки с командного адреса, указав имя пользователя GitLab; участник с правами Maintainer добавляет их как Developer через https://gitlab.com/groups/samba-team/-/group_members.
  • Остальные разработчики — пишут на contributing@samba.org с именем пользователя GitLab и историей/планами контрибуции; доступ выдают активным в списке рассылки участникам с патчами, добавляя в https://gitlab.com/samba-team/devel/samba/project_members.

Запуск CI

Настроить remote и пушить ветку с префиксом — своим именем пользователя GitLab в формате $USER/topic (если локальное имя отличается от GitLab-имени, использовать GitLab-имя):

git remote add gitlab-ci git@gitlab.com:samba-team/devel/samba.git
git push gitlab-ci +HEAD:$USER/foo

На странице вики примеры имён веток приведены в двух форматах — и $USER-foo (через дефис), и $USER/topic (через слэш); критичен именно префикс с именем пользователя GitLab, а не разделитель. Здесь и в Вклад в код Samba используется единый формат $USER/topic.

Push автоматически запускает CI; результаты — https://gitlab.com/samba-team/devel/samba/pipelines. Описательное имя ветки заодно подставляется в заголовок merge request'а.

Merge request'ы

  • После push GitLab печатает ссылку «Create Merge Request» (нет ссылки — возможна проблема ssh-конфигурации; MR создают вручную).
  • Сменить целевой проект: GitLab иногда предлагает целевым репозиторий samba-team/devel/samba — в описании будет предупреждение, что MR должны идти против https://gitlab.com/samba-team/samba/; исправляется кнопкой «Change branches».
  • Повторный push в ту же ветку (git push gitlab-ci +HEAD:$USER/foo -f) обновляет MR и перезапускает CI; пока MR открыт, имя ветки не переиспользуют.
  • Дополнительно можно послать URL MR в список рассылки samba-technical.

Слияние (члены команды)

Кнопка Merge в GitLab для слияния в master не работает. Процедура ручная: скачать патч (например, https://gitlab.com/samba-team/samba/merge_requests/12.patch), добавить теги ревью, выполнить git autobuild локально; после попадания в master закрыть MR комментарием вида Merged into master as <git hash> for Samba <next version>.

Особые приёмы CI

Push-опции -o ci.variable=...:

# Полный autobuild без ранней остановки на первой ошибке
git push -o ci.variable='AUTOBUILD_FAIL_IMMEDIATELY=0' gitlab-ci
# Пропустить задачи -O3 (экономит 9 VM)
git push -o ci.variable='AUTOBUILD_SKIP_SAMBA_O3=1' gitlab-ci
# Оба флага сразу
git push -o ci.variable='AUTOBUILD_FAIL_IMMEDIATELY=0' -o ci.variable='AUTOBUILD_SKIP_SAMBA_O3=1' gitlab-ci
# Пропустить CI целиком (пуши только документации/правок сообщений)
git push -o ci.skip gitlab-ci
# Сборка с покрытием
git push -o ci.variable='SAMBA_CI_AUTOBUILD_ENABLE_COVERAGE=--enable-coverage' gitlab-ci

Контейнерные образы для CI описаны в bootstrap/README.md репозитория samba-team/samba.

Подводные камни

  • Таймаут задач на форке: по умолчанию 1 час; без увеличения до 3 часов (допустимо на бесплатных runner'ах) push падает с ERROR: Job failed: execution took longer than 1h0m0s seconds.
  • Неверный целевой репозиторий MR: GitLab предлагает devel/samba — целевым должен быть samba-team/samba.
  • Нет ссылки на создание MR после push — проверить ssh-конфигурацию или создать MR вручную.
  • Coverage-задачи могут падать на общих runner'ах: окружение слабее плановых пайплайнов.
  • Недоступность gitlab.com: статус — https://status.gitlab.com/; git децентрализован, локальная работа не прерывается.
  • Слияние в master — только через локальный git autobuild членом команды (см. Вклад в код Samba, Код ревью).
