База знаний Samba AD DC

SELinux и AppArmor для Samba AD DC

Суть

На RHEL/Fedora с SELinux в режиме enforcing и на Ubuntu/Debian с AppArmor мандатный контроль может молча ломать вход AD-пользователей через winbind и динамические обновления DNS при BIND9_DLZ (samba_dnsupdate, ошибка dns_tkey_negotiategss: TKEY is unacceptable). Официальный HOWTO по развёртыванию AD DC мандатный контроль не рассматривает, а типовой совет из интернета — «выключить SELinux» — не нужен: и вики Samba, и документация Ubuntu/Fedora показывают, как точечно доразрешить доступ. Общий алгоритм один: найти отказ в аудит-логе, добавить узкое правило (булев флаг, метку файла, локальный модуль политики или локальное дополнение профиля AppArmor) и вернуть enforcing. Отдельно разобрана не мандатная, а обычная DAC-ловушка: при umask 077 библиотеки и сокеты Samba в /usr/local/samba недоступны непривилегированным процессам.

Ключевое

SELinux: убедиться, что дело в нём (RHEL/Fedora)

Диагностика со страницы вики (пример — не работал вход AD-пользователя на DC):

# sestatus

sestatus(8) показывает, включён ли SELinux, загруженную политику и режимы — в том числе отдельно Current mode и Mode from config file. Если режим enforcing, отказы пишет auditd:

# grep denied /var/log/audit/audit.log

Если вывод есть — особенно строки, связанные с winbind — вероятная причина найдена. Проверка гипотезы: перевести SELinux в permissive и повторить вход.

# setenforce 0
# [attempt to log in as an AD user on console interface]

Если вход заработал — виноват SELinux. По setenforce(8): setenforce 0 или Permissive — permissive-режим, setenforce 1 или Enforcing — enforcing.

Локальный модуль: audit2allow + semodule

В permissive-режиме SELinux доступ не запрещает, но продолжает логировать то, что запретил бы. Поэтому сначала надо выполнить все способы входа, которые должны работать (в примере — консоль, SSH и графический вход GDM): иначе на каждый раунд сборки модуля удастся пройти только первый отказ.

# cd /tmp
# grep denied /var/log/audit/audit.log > selinuxloginfails
# audit2allow -M samba4 -i selinuxloginfails
# semodule -i samba4
# setenforce 1
  • audit2allow -M <имя> генерирует загружаемый пакет модуля, -i — читать вход из файла (audit2allow(1)).
  • semodule -i MODULE_PKG устанавливает или заменяет пакет модуля (semodule(8)).
  • Затем setenforce 1 — вернуть enforcing и заново проверить вход на всех интерфейсах.

Автору страницы это дало вход на консоли, но не по SSH (из-за настроек sshd_config) и не в графическом входе; в консоли всё равно появлялось id: cannot find name for user id 3000018 — причина оказалась в правах (см. раздел про DAC-ловушку).

Булевы политики samba/smbd

Man-страница samba_selinux(8) / smbd_selinux(8) (пакет selinux-policy-doc, Fedora/RHEL/OpenSUSE) перечисляет булевы с описанием и значением по умолчанию. Для Samba важны:

Булев Что разрешает По умолчанию
samba_domain_controller samba действует как контроллер домена: добавлять пользователей и группы, менять пароли off
samba_create_home_dirs создавать новые домашние каталоги (например, через PAM) off
samba_enable_home_dirs шарить домашние каталоги (samba и winbind-rpcd) off
samba_export_all_ro шарить любой файл или каталог только для чтения off
samba_export_all_rw шарить любой файл или каталог на чтение и запись off
samba_portmapper samba действует как portmapper off
samba_run_unconfined запускать unconfined-скрипты off

Там же есть samba_share_nfs, samba_share_fusefs, samba_load_libgfapi (все отключены по умолчанию).

Включение (команды из man-страницы; -P делает значение постоянным, без него булев вернётся к значению после перезагрузки — setsebool(8)):

setsebool -P samba_domain_controller 1
setsebool -P samba_create_home_dirs 1
setsebool -P samba_enable_home_dirs 1
setsebool -P samba_export_all_ro 1
setsebool -P samba_export_all_rw 1
setsebool -P samba_portmapper 1
setsebool -P samba_run_unconfined 1

Значения булева: 1, true, on — включить; 0, false, off — выключить. Синопсис setsebool(8) допускает список булевых в одной команде, и пример man-страницы использует именно samba-булевы:

# setsebool -P samba_create_home_dirs=on samba_enable_home_dirs=on

(это дословный пример из setsebool(8); собранный из нескольких булевых набор в одну команду — композиция из документации, а не цитата.)

Вместо правки отдельного булева можно объявить permissive сам тип процесса:

# semanage permissive -a smbd_t

Тогда SELinux не будет отказывать smbd_t, но AVC-сообщения об отказах всё равно генерируются (smbd_selinux(8)).

Метки файлов: samba_share_t и restorecon

Страница Fedora «SELinux/samba» (это текст samba_selinux(8), автор Dan Walsh, 22 Nov 2011) про файловые контексты: если публиковать не только домашние каталоги, файлы должны иметь метку samba_share_t.

chcon -t samba_share_t /var/eng

Чтобы метка пережила relabel, правило добавляют через semanage fcontext и применяют restorecon:

semanage fcontext -a -t samba_share_t "/var/eng(/.*)?"
restorecon -R -v /var/eng/
  • semanage fcontext пишет локальное правило в /etc/selinux/POLICYTYPE/contexts/files/file_contexts.local, а restorecon применяет его на диск.
  • По semanage-fcontext(8) локальные правила из file_contexts.local приоритетнее правил из модулей политики, обрабатываются от новых к старым, и побеждает первое совпадение — поэтому регулярка должна быть как можно конкретнее.
  • restorecon по умолчанию не рекурсивен (нужен -R или -r) и меняет только type-часть контекста, если не указан -F (restorecon(8)).

Актуальный пример из Fedora Quick Docs (шара для пользователя):

$ sudo mkdir /home/jane/share
$ sudo semanage fcontext --add --type "samba_share_t" "/home/jane/share(/.*)?"
$ sudo restorecon -R ~/share

Fedora-страница напоминает и про использование удалённых домашних каталогов:

setsebool -P use_samba_home_dirs 1

и про public_content_t / public_content_rw_t — общий контекст для шаринга одного каталога несколькими сервисами (Apache, FTP, rsync, Samba), с разрешением записи через булев allow_smbd_anon_write:

setsebool -P allow_smbd_anon_write=1

AppArmor на Ubuntu/Debian: профили smbd и nmbd

Профили для /usr/sbin/smbd и /usr/sbin/nmbd поставляются пакетом apparmor-profiles (поиск по содержимому пакетов Ubuntu подтверждает: /etc/apparmor.d/usr.sbin.smbd — пакет apparmor-profiles).

$ sudo apt install apparmor-profiles apparmor-utils

По умолчанию оба профиля стоят в режиме complain: Samba работает без правки профиля, а нарушения только логируются. Исключения для общих ресурсов добавлять не нужно — unit smbd делает это сам через helper-скрипт. Сообщение ALLOWED значит, что в enforce-режиме действие было бы запрещено:

Jun 30 14:41:09 ubuntu kernel: [ 621.478989] audit:
type=1400 audit(1656600069.123:418):
apparmor="ALLOWED" operation="exec" profile="smbd"
name="/usr/lib/x86_64-linux-gnu/samba/samba-bgqd" pid=4122 comm="smbd"
requested_mask="x" denied_mask="x" fsuid=0 ouid=0
target="smbd//null-/usr/lib/x86_64-linux-gnu/samba/samba-bgqd"

(в источнике это одна запись, разбитая на строки для наглядности.)

Перевод профиля в enforce и перезагрузка:

$ sudo aa-enforce /usr/sbin/smbd
$ sudo apparmor_parser -r -W -T /etc/apparmor.d/usr.sbin.smbd
  • aa-enforce переключает профиль в enforce-режим (режим по умолчанию — enforce, а aa-complain его меняет) — aa-enforce(8).
  • apparmor_parser -r заменяет уже загруженное в ядро определение профиля, -W пишет кэш, -T отключает чтение профиля из кэша — apparmor_parser(8).

Мониторинг: /var/log/syslog на записи DENIED, либо /var/log/audit/audit.log, если запущен auditd. Действия, заблокированные AppArmor, могут выглядеть в приложении как странные и не связанные с профилем ошибки.

Важная деталь aa-complain(8): в complain-режиме политика не применяется, но правила deny продолжают действовать и в этом режиме («Note that 'deny' rules will be enforced even in complain mode»).

Профиль /etc/apparmor.d/usr.sbin.named в Ubuntu поставляется пакетом bind9, а профиля AppArmor для winbindd в Ubuntu noble в пакетах нет (поиск по содержимому пакетов файла профиля не находит).

AppArmor и SELinux для BIND9_DLZ (samba_dnsupdate и TKEY)

Страница интеграции: если samba_dnsupdate и nsupdate возвращают dns_tkey_negotiategss: TKEY is unacceptable, процесс BIND должен иметь

  • чтение: /usr/local/samba/private/dns.keytab, /usr/local/samba/private/named.conf;
  • чтение-запись: каталог /usr/local/samba/private/dns/ и свои zone-файлы.

Provision пытается выставить права сам, но правка AppArmor/SELinux может понадобиться; при AppArmor помогает команда aa-logprof.

Права (DAC), переменная задаёт имя зоны:

MYREALM="samdom.example.com"

chown named:named /usr/local/samba/private/dns
chgrp named /usr/local/samba/private/dns.keytab
chmod g+r /usr/local/samba/private/dns.keytab
chmod 775 /usr/local/samba/private/dns

Метки разово (chcon):

chcon -t named_conf_t /usr/local/samba/private/dns.keytab
chcon -t named_conf_t /usr/local/samba/private/named.conf.update
chcon -t named_var_run_t /usr/local/samba/private/dns
chcon -t named_var_run_t /usr/local/samba/private/dns/${MYREALM}.zone

Те же метки постоянно (semanage fcontext, чтобы пережили relabel):

semanage fcontext -a -t named_conf_t /usr/local/samba/private/dns.keytab
semanage fcontext -a -t named_conf_t /usr/local/samba/private/named.conf
semanage fcontext -a -t named_conf_t /usr/local/samba/private/named.conf.update
semanage fcontext -a -t named_var_run_t /usr/local/samba/private/dns
semanage fcontext -a -t named_var_run_t /usr/local/samba/private/dns/${MYREALM}.zone
semanage fcontext -a -t named_var_run_t /usr/local/samba/private/dns/${MYREALM}.zone.jnl

Инструкция вики оговорена как предназначенная для RHEL6, но пригодная как ориентир для других дистрибутивов; там же сказано, что Samba-специфичная SELinux-политика ещё не написана, но всё должно работать без отключения SELinux.

AppArmor: дополнения в конец файла /etc/apparmor.d/local/usr.sbin.named (создать, если его нет), затем перезапустить apparmor:

# Samba DLZ and Active Directory Zones (default source installation)
/usr/local/samba/lib/** rm,
/usr/local/samba/private/dns.keytab rk,
/usr/local/samba/private/named.conf r,
/usr/local/samba/private/dns/** rwk,
/usr/local/samba/etc/smb.conf r,

Дополнительные пути, понадобившиеся на конкретных дистрибутивах (там же):

/var/tmp/** rwmk,     # Ubuntu 14.04.1 LTS: BIND создавал /var/tmp/DNS_110
/dev/urandom rw,      # Ubuntu 16.04 LTS

Диагностика по странице про ошибку TKEY:

# sudo dmesg | grep DENIED

искать usr.sbin.named; пример отказа:

apparmor="DENIED" operation="file_lock" profile="/usr/sbin/named" name="/var/tmp/krb5_108.rcache2" pid=99523 comm="named" requested_mask="k" denied_mask="k" fsuid=108 ouid=108

Недостающие права добавляют в /etc/apparmor.d/usr.sbin.named или в /etc/apparmor.d/local/usr.sbin.named («Don't forget the include in /etc/apparmor.d/usr.sbin.named»), после чего перезагружают профиль:

# sudo systemctl restart apparmor

или

# sudo apparmor_parser -r /etc/apparmor.d/usr.sbin.named

Версии: private → bind-dns (Samba 4.8)

  • Страница интеграции с AppArmor/SELinux: «From Samba 4.8.0 /usr/local/samba/private is replaced by /usr/local/samba/bind-dns».
  • Страница про ошибку TKEY: «The binddns dir was changed at Samba 4.8.0 from /usr/local/samba/private/dns to /usr/local/samba/bind-dns/dns».
  • В smb.conf(5) параметр binddns dir (синоним bind dns directory) по умолчанию равен ${prefix}/bind-dns, и каталог должен быть на том же mount point, что и private-каталог.
  • В release notes 4.8.0 параметр binddns dir помечен как новый.
  • При этом страница BIND9_DLZ_DNS_Back_End местами всё ещё приводит старые пути: named.conf там описан уже как /usr/local/samba/bind-dns/named.conf (с оговоркой про 4.7 и раньше), а tkey-gssapi-keytab в примере — /usr/local/samba/private/dns.keytab.

DAC-ловушка: umask 077 и права на /usr/local/samba

Отдельно от мандатного контроля: при umask 077 (как было у автора при сборке Samba 4 из исходников) файлы принадлежат root и доступны только root. Библиотеки в /usr/local/samba/lib и сокет winbind недоступны процессам, работающим от имени пользователя, поэтому id и whoami не видят AD-пользователя, даже когда вход уже разрешён. Симптомы: id: cannot find name for user id 3000018, приглашение ["I have no name!"@server]$, а графический вход GDM аутентифицирует пользователя, но X сразу завершается и возвращает на экран входа. Лечение:

# chmod 755 /usr/local/samba /usr/local/samba/var /usr/local/samba/var/run \
     /usr/local/samba/var/run/winbindd
# chmod -R 755 /usr/local/samba/lib

Если не помогло — войти AD-пользователем на консоль и выполнить strace на id и whoami, обращая внимание на ошибки ENOACCES (в источнике именно так); для X смотреть ~/.xsession-errors.

Подводные камни

  • Цель — не отключать защиту целиком, а точечно доразрешить нужное: это прямо позиция страницы вики («Everything working without disabling SELinux») и документации Ubuntu (профили можно оставлять включёнными, отслеживая ALLOWED/DENIED).
  • audit2allow генерирует только TE allow-правила, и man-страница предупреждает: результат нужно оценивать осторожно, часто правильнее определить новые домены и типы, чем слепо внедрять широкие разрешения (audit2allow(1)).
  • В permissive-режиме SELinux логирует только то, что произошло фактически: если не выполнить все нужные операции (все интерфейсы входа) до сборки модуля, придётся делать несколько раундов audit2allow/semodule.
  • setsebool без -P не переживёт перезагрузку: постоянные значения пишутся в файл политики только с -P (setsebool(8)).
  • В complain-режиме AppArmor правила deny всё равно применяются (aa-complain(8)), а профили smbd/nmbd в Ubuntu по умолчанию именно в complain — то есть до перевода в enforce они ничего не блокируют; после перевода стоит отдельно последить за логом, потому что заблокированные операции могут выглядеть как не связанные с профилем ошибки приложения.
  • Локальные правила semanage fcontext приоритетнее правил модулей политики и срабатывают по первому совпадению, поэтому нужны максимально конкретные регулярные выражения (semanage-fcontext(8)); после изменения контекстов не забыть restorecon, иначе метка на файлах не поменяется.
  • restorecon не рекурсивен без -R и меняет только type-часть контекста без -F (restorecon(8)).
  • Массового restorecon -Rv / (по всей файловой системе) в источниках нет: и страница Fedora, и Fedora Quick Docs применяют restorecon к конкретному каталогу (restorecon -R -v /var/eng/, restorecon -R ~/share). Точечная разметка каталогов общих ресурсов безопаснее полного relabel.
  • Пути в примерах зависят от версии Samba: /usr/local/samba/private/... актуально для 4.7 и раньше, с 4.8.0 — /usr/local/samba/bind-dns/...; примеры вики и вывод samba_upgradedns местами всё ещё показывают старые пути, поэтому команды нельзя копировать без подстановки актуального пути.
  • Причина может быть не в мандатном контроле, а в обычных правах: для provision/join/upgrade на Samba до 4.4.0 у dns.keytab были неверные права и их исправляют (chmod 640, chown root:named); при обновлении с версии раньше 4.8.0 проверяют права на каталог /usr/local/samba/bind-dns (chmod 770, chown root:named); у join на Samba >= 4.8.0 известен баг 14535 — keytab не создаётся в правильном каталоге (обходной путь на момент описания — временно переключиться на внутренний DNS-бэкенд и снова на BIND9_DLZ).
  • SELinux-раздел страницы BIND9_DLZ написан для RHEL6 и признаёт, что полноценной Samba-специфичной политики ещё нет; сам автор страницы про SELinux подчёркивает, что настройка отличается от системы к системе и от дистрибутива к дистрибутиву, а официальный HOWTO по AD DC SELinux не рассматривает.
  • Примеры правил AppArmor для named помечены в вики как «default source installation» (сборка из исходников в /usr/local/samba); для пакетных установок пути другие, и на некоторых дистрибутивах требуются дополнительные пути — источник советует смотреть собственные логи AppArmor.
