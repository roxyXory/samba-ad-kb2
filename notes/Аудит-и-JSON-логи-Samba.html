База знаний Samba AD DC

Аудит и JSON-логи Samba AD DC

Суть

Samba AD DC умеет писать события аудита — удачные и неудачные аутентификации, авторизации и изменения базы sam.ldb — в свой debug-лог через отдельные debug-классы (auth_audit, dsdb_audit, dsdb_password_audit, dsdb_group_audit, dsdb_transaction_audit и их JSON-варианты), не поднимая общий уровень логирования. Аудит — локальная настройка: его включают на каждом сервере отдельно, и событие пишет тот сервер, который его обработал. JSON-формат — основа для централизованного сбора (rsyslog imfile) и для блокировки перебора паролей через fail2ban по полю remoteAddress. Формат JSON-строк менялся в 4.25 (убраны два ведущих пробела, встроенные переводы строк заменены пробелами — см. «Подводные камни»), а 4.24 добавила новые логируемые атрибуты и ещё одно значение поля action ("Auth info change") — это не смена формата, но парсеры и фильтры fail2ban всё равно стоит проверять при обновлении.

Ключевое

Что и с какой версии логируется

  • Samba 4.7 и новее — аудит аутентификации и авторизации (debug-классы auth_audit и auth_json_audit; в release notes 4.7 сказано: подробная информация аудита пишется в debug-логи под классом auth_audit, «including in particular the client IP address triggering the audit line», а при сборке с библиотекой jansson — JSON-представление под классом auth_json_audit).
  • Samba 4.9 — аудит изменений базы AD DC: изменения sam.ldb пишутся под dsdb_audit / dsdb_json_audit, транзакции — под dsdb_transaction_audit / dsdb_transaction_json_audit, смена паролей — под dsdb_password_audit / dsdb_password_json_audit, изменения членства в группах — под dsdb_group_audit / dsdb_group_json_audit (release notes 4.9). Там же: Jansson по умолчанию требуется для сборки Samba; для сборок --without-ad-dc JSON-аудит отключается опцией --without-json-audit при configure (это историческое имя той же по смыслу опции, которая в текущих версиях называется --without-json — см. ниже). В release notes 4.9 также отмечено, что длительность аутентификации для NTLM и Kerberos KDC попадает только в JSON-записи.
  • Samba 4.24 — классы dsdb_password_audit и dsdb_password_json_audit дополнительно логируют изменения атрибутов, связанных с аутентификацией: altSecurityIdentities, dNSHostName, msDS-AdditionalDnsHostName, msDS-KeyCredentialLink, servicePrincipalName; в JSON-логе такие изменения имеют значение "Auth info change" в поле "action" (release notes 4.24.0 от 18 марта 2026).
  • Samba 4.25 (первые стабильные release notes от 24 сентября 2026) изменила формат JSON-строк, см. ниже раздел «Подводные камни».
  • Аудит — локальная настройка: «Audit logging is a local setting and you must enable this feature on each Samba server individually. Events are logged on the Samba server the event was performed on.» В домене с несколькими DC запрос аутентификации пишет только тот DC, которому он был адресован.
  • Покрытие: аутентификация и авторизация пользовательских учёток полноценно аудируются только на Samba AD DC; в файловом сервере и члене домена покрываются NTLM-аутентификация, авторизация SMB и RPC («support is comprehensive only in the AD DC»).
  • Логируются и успешные, и неудачные события аутентификации, а из авторизации — только успешные: «Samba supports logging of successful authorization events but not unsuccessful authorization events. It can log both successful and unsuccessful authentication events.» При NTLM события authentication и authorization пишутся парой; при Kerberos аутентификацию фиксирует KDC (на члене домена событие аутентификации не появится), а авторизация — при каждом обращении к сервису.
  • Парольные события попадают в два места: изменения пароля логируются под dsdb_password_audit и одновременно видны как события аутентификации через auth_audit (man-страница smb.conf(5)).

Debug-классы и уровни (smb.conf(5), версия man-страницы — 4.25.0)

В man-странице log level перечислены классы аудита: auth_audit, auth_json_audit, dsdb_audit, dsdb_json_audit, dsdb_password_audit, dsdb_password_json_audit, dsdb_transaction_audit, dsdb_transaction_json_audit, dsdb_group_audit, dsdb_group_json_audit.

Класс (текстовый / JSON) Что логирует Уровни (дословно из man-страницы)
auth_audit / auth_json_audit аутентификация и авторизация 2: Authentication Failure; 3: Authentication Success; 4: Authorization Success; 5: Anonymous Authentication and Authorization Success
dsdb_audit / dsdb_json_audit изменения базы sam.ldb AD DC 5: Database modifications; 5: Replicated updates from another DC
dsdb_group_audit / dsdb_group_json_audit изменения членства в группах в sam.ldb те же уровни 5, что и у dsdb_* (в man-странице уровни перечислены одним списком для dsdb_audit, dsdb_json_audit, dsdb_group_audit, dsdb_group_json_audit)
dsdb_password_audit / dsdb_password_json_audit смена и сброс пароля, а также изменения аутентификационных атрибутов (список в 4.24+) 5: Successful password changes and resets, and authentication related attribute changes
dsdb_transaction_audit / dsdb_transaction_json_audit откаты транзакций и сбои prepare commit 5: Transaction failure (rollback); 10: Transaction success (commit)

Дополнительно из man-страницы:

  • JSON-вариант пишется, «if Samba was not compiled with --without-json».
  • Про два configure-флага: это одна и та же по смыслу опция — отключение JSON-поддержки целиком (вместе с JSON-аудитом). В 4.9 она называлась --without-json-audit (жила в lib/audit_logging/wscript и требовала --without-ad-dc); в текущих версиях это --without-json (верхнеуровневый wscript: «Build without JSON support», тоже требует --without-ad-dc, потому что JSON нужен и AD DC, и JSON-формату аудита, и JSON-выводу net). Отдельного флага «только JSON-аудит» нет.
  • В JSON-логе dsdb_password_json_audit изменения аутентификационных атрибутов получают в поле "action" значение "Auth info change", а смена и сброс пароля — "change" и "reset" — так пишет man-страница; фактический код возвращает "Change" и "Reset" с заглавной буквы (см. «Подводные камни»).
  • Про транзакции: «Audit logs are already generated and sent to the system logs before the transaction is complete. Logging the transaction details allows the identification of password and sam.ldb operations that have been rolled back, and so have not actually persisted.»
  • Значение по умолчанию: log level = 0. Действует правило: более высокий уровень включает и события более низких уровней (так же сформулировано в вики).

Включение аудита

Проверить, что сборка вообще умеет JSON (вики, раздел «Verifying if JSON Support is Enabled in Samba»):

# smbd -b | grep HAVE_JSON_OBJECT
HAVE_JSON_OBJECT

Если вывода нет — Samba собрана без поддержки JSON (нужны заголовочные файлы jansson и пересборка). Классический пример включения аутентификационного аудита (значение по умолчанию 1, для классов — 3, т.е. неудачи и успехи) из вики:

log level = 1 auth_audit:3 auth_json_audit:3

Включение аудита изменений базы AD DC в JSON (из вики):

log level = 1 dsdb_json_audit:5 dsdb_password_json_audit:5 dsdb_group_json_audit:5 dsdb_transaction_json_audit:5

После изменения log level нужно перезапустить Samba (вики: «Restart Samba.»). Вывод одного класса в отдельный файл — суффикс @PATH:

log level = 1 auth_json_audit:3@/var/log/samba/samba_audit.log

Синтаксис @PATH документирован в man-странице log level: «To configure the logging for specific classes to go into a different file then log file, you can append @PATH to the class, eg log level = 1 full_audit:1@/var/log/audit.log». Пример именно с auth_json_audit:3@/var/log/samba/samba_audit.log даёт документация Tranquil IT и помечает эту конфигурацию как «Added in version 4.10»; проверка по man-страницам подтверждает: в smb.conf(5) для 4.10 предложение про @PATH уже есть, а в версии для 4.9 его ещё нет (см. раздел «Источники»).

Форматы записей

Текстовый формат доступен всегда, без дополнительных библиотек. Пример успешной авторизации из вики (обратите внимание на два ведущих пробела в строке сообщения — до 4.25 так выглядели и JSON-строки):

[2017/07/04 21:07:41.410381,  4, pid=21757] ../auth/auth_log.c:848(log_successful_authz_event_human_readable)
  Successful AuthZ: [SMB2,krb5] user [SAMDOM]\[Administrator] [S-1-5-21-469703510-2364959079-1506205053-500] at [Di, 04 Jul 2017 21:07:41.410364 CEST] Remote host [ipv4:10.99.0.81:58828] local host [ipv4:10.99.0.1:445]

Пример JSON-записи из вики (Samba 4.7):

  {"type": "Authorization", "timestamp": "2017-07-04T21:07:41.410408+0200", "Authorization": {"version": {"major": 1, "minor": 0}, "sid": "S-1-5-21-469703510-2364959079-1506205053-500", "serviceDescription": "SMB2", "localAddress": "ipv4:10.99.0.1:445", "remoteAddress": "ipv4:10.99.0.81:58828", "transportProtection": "SMB", "authType": "krb5", "domain": "SAMDOM", "account": "Administrator", "logonServer": "DC1", "accountFlags": "0x00000210"}}

Структура верхнего уровня: timestamp, type и объект данных, ключ которого совпадает с type. Значения type: Authentication, Authorization, dsdbChange, dsdbTransaction, passwordChange, replicatedUpdate, groupChange. Вики отдельно предупреждает: примеры на странице переформатированы для читаемости, а реальный JSON аудита «will always be formatted on a single line».

Поле version у каждого типа — версия формата JSON: major увеличивается, если поля меняют смысл, minor — если поле добавлено; изменение набора возможных значений (например, поддерживаемых форматов пароля в passwordType) версию обычно не меняет.

Разбор JSON-событий

Атрибуты по типам (страница вики «Interpreting JSON Audit Logs», правка от 13 января 2023):

  • Authentication (version = {"major": 1, "minor": 2}): authDescription (тип аутентификации: "simple bind", "simple bind/TLS", "guest", "bare-NTLM", "plaintext", "interactive", "network", "Unknown Auth Description"/"Unknown Pre-authentication" для событий KDC, "ServerAuthenticate", "LDAP Modify" — «this is a password change, not strictly an authentication event, but logged here so you don't miss it»), becameAccount / becameDomain / becameSid, clientAccount / clientDomain, mappedAccount / mappedDomain, duration (микросекунды), eventId, localAddress, logonId (случайный 64-битный идентификатор для сквозной трассировки), logonType (2 — Interactive, 3 — Network, 8 — NetworkCleartext), netlogon*-поля, passwordType, remoteAddress, serviceDescription ("LDAP", "SMB2", "NETLOGON"), status, workstation. Неприменимые атрибуты могут присутствовать с пустыми значениями ("null", "0x00000000"). Поле status — сообщение NT STATUS; при успехе "NT_STATUS_OK", типовые ошибки: NT_STATUS_ACCESS_DENIED, NT_STATUS_WRONG_PASSWORD, NT_STATUS_NO_SUCH_USER, NT_STATUS_NO_SUCH_DOMAIN, NT_STATUS_ACCOUNT_RESTRICTION, NT_STATUS_DOWNGRADE_DETECTED и др. (полный перечень — на странице вики).
  • Authorization (version = {"major": 1, "minor": 1}): account, accountFlags, authType ("krb5", "NTLMSSP", "simple bind"), domain, localAddress, logonServer, remoteAddress, serviceDescription, sessionId (GUID сессии), sid, transportProtection ("SMB", "TLS", "SEAL", "NONE").
  • dsdbChange (version = {"major": 1, "minor": 0}): dn, operation ("Modify", "Add", "Delete"), attributes, performedAsSystem (true, если Samba действует от системной учётки), remoteAddress, sessionId, status (строка) и statusCode (число, эквивалент LDAP result code из RFC4511: "Success", "insufficient access rights", "No such object", "Entry already exists" и т.п.), transactionId, userSid. Блок attributes эквивалентен LDIF-станзам: action — add, replace или delete; секретные значения заменяются на redacted: true; значения длиннее 1024 байт обрезаются с флагом truncated и многоточием; значения с непечатаемыми символами кодируются в base64 (base64: true). Пример из вики:
"dsdbChange": {
  "operation": "Modify",
  "dn": "@SAMBA_DSDB",
  "attributes": {
   "backupDate": {"actions": [
     {"action": "add",
      "values": [
        {"value": "2023-01-14T09-43-55.333333"}
       ]
     }
   ]
  }}}

чему соответствует LDIF:

dn: @SAMBA_DSDB
changetype: modify
add: backupDate
backupDate: 2023-01-14T09-43-55.333333
  • dsdbTransaction (version = {"major": 1, "minor": 0}): action ("begin", "commit", "rollback"), duration (микросекунды), transactionId (GUID, который связывает записи о транзакции с входящими в неё dsdbChange).
  • passwordChange (version = {"major": 1, "minor": 1}): частный случай dsdbChange; action ("Change" или "Reset"), dn, eventId (4723 — change, 4724 — reset), remoteAddress, sessionId, status, statusCode, transactionId, userSid (SID того, кто меняет пароль, а не обязательно того, кому меняют).
  • groupChange (version = {"major": 1, "minor": 1}): action ("Removed", "Added", "PrimaryGroup"), eventId, group (DN группы), remoteAddress, sessionId, status, statusCode, transactionId, user (DN пользователя, чьё членство меняется), userSid (SID того, кто вносит изменение). Возможные eventId: 4728/4729 — добавление/удаление из глобальной security-группы, 4732/4733 — локальной security-группы, 4746/4747 — локальной группы, 4751/4752 — глобальной группы, 4756/4757 — универсальной security-группы, 4761/4762 — универсальной группы.
  • replicatedUpdate: в вики есть только заголовок раздела, описание полей отсутствует (на дату правки страницы).

Централизация логов

  • Вики рекомендует для сбора логов на одном сервере настроить централизованный syslog: «configure Samba to log to the syslog daemon, and configure the syslog daemon to send the logs to the centralized server»; в качестве шлюза для отправки упоминаются параметры logging, syslog и syslog only из smb.conf(5).
  • В smb.conf(5) (4.25.0) параметр logging задаёт список бэкендов вида backend[:option][@loglevel]; доступные бэкенды: syslog, file, systemd, lttng, gpfs, ringbuf; пример: logging = syslog@1 file. Когда logging задан, он переопределяет параметры syslog и syslog only. Параметр syslog отображает уровни отладки Samba на уровни syslog: 0 → LOG_ERR, 1 → LOG_WARNING, 2 → LOG_NOTICE, 3 → LOG_INFO, всё выше — LOG_DEBUG.
  • Практический вариант от Tranquil IT (документация Samba-AD) — не через syslog-бэкенд Samba, а по файлу: класс auth_json_audit пишется в отдельный файл, а rsyslog читает его модулем imfile и пересылает по TCP. Важное замечание оттуда: «Samba RPM packages are not compiled with direct rsyslog support. You must then configure rsyslog to monitor Samba logs.» Конфигурация на отправляющем хосте (в файле /etc/rsyslog.d/send_samba.conf; параметры File, Tag, Severity, Facility — из документации модуля imfile):
module(load="imfile" PollingInterval="10") #needs to be done just once
input(type="imfile"
      File="/var/log/samba/samba_audit.log"
      Tag="samba_auth"
      Severity="info"
      Facility="auth")
if ($syslogtag == "samba_auth") then {
    action(type="omfwd" target="143.126.200.167" port="514" protocol="tcp"
           action.resumeRetryCount="100"
           queue.type="linkedList" queue.size="10000")
}

перезапуск: systemctl restart rsyslog. На хосте-сборщике (файл /etc/rsyslog.d/recv_samba.conf) — приём по TCP и запись по тегу:

# Provides TCP syslog reception
$ModLoad imtcp
$InputTCPServerRun 514
if ($syslogtag == "samba_auth")  then /var/log/samba/audit_auth.log

(каталог /var/log/samba на сборщике создаётся заранее: mkdir -p /var/log/samba; затем systemctl restart rsyslog).

  • Документация модуля rsyslog imfile полезна ещё двумя параметрами: PollingInterval — «Seconds between file scans in polling mode; default 10» (именно это значение задано в примере Tranquil IT) и экспериментальный reopenOnTruncate — «reopen the input file if it was truncated without changing its inode».

Блокировка перебора: fail2ban

Логика от Tranquil IT: AD-политики сами блокируют учётку после нескольких неудачных попыток, но это открывает путь к DoS — злоумышленник перебором паролей блокирует чужие учётки; поэтому рекомендуется блокировать не учётку, а IP-адрес источника через fail2ban.

Предварительно включается вывод аудита в отдельный файл:

log level = 1 auth_json_audit:3@/var/log/samba/auth_json_audit.log

Фильтр /etc/fail2ban/filter.d/samba.conf (дословно):

[Definition]
failregex = NT_STATUS_WRONG_PASSWORD.*remoteAddress": "ipv4:<HOST>:

Тюрьма /etc/fail2ban/jail.d/samba.conf (дословно):

[samba]
filter = samba
enabled = true
action = iptables-multiport[name=samba, port="88,135,389,445,464,636,3328,3329", protocol=tcp]
#   mail[name=samba, dest=technique@mondomaine.fr]
logpath = /var/log/samba/auth_json_audit.log
maxretry = 5
findtime = 600
bantime = 600

Исключения для доверенных адресов — файл /etc/fail2ban/jail.d/customisation.local:

[DEFAULT]
ignoreip = 192.168.154.217

Запуск: systemctl enable fail2ban и systemctl start fail2ban. Разблокировка и просмотр: fail2ban-client set samba unbanip <COMPUTER_IP> и fail2ban-client status samba.

Про <HOST> в регулярном выражении документация fail2ban говорит: это место, куда подставляется IP или доменное имя, которое нужно заблокировать; и предупреждает, что слабые регулярные выражения уязвимы к DoS — если удалённый пользователь может подставить в лог текст, попадающий в часть <HOST>, он способен заблокировать любой хост, поэтому <HOST> должен опираться на текст, сгенерированный приложением, а не пользователем (в нашем случае — на поле remoteAddress и префикс ipv4: из JSON-записи Samba).

Подводные камни

  • Формат JSON изменился в 4.25. Release notes 4.25.0: «The two leading spaces before the opening '{' on JSON audit log lines have been removed. And any embedded new line characters '\n' are converted to spaces.» До 4.25 JSON-строка шла с двумя ведущими пробелами (это видно и по примеру на вики) и могла содержать встроенные переводы строк. Простейший парсер json.loads(line) без strip() на старых версиях падал, а парсер, «настроенный» на два пробела, ломается после обновления до 4.25. В коммите, внёсшем изменение (lib:audit_logging JSON remove leading spaces, 28.01.2026, bug 15898), старая строка DEBUGADDC(debug_class, debug_level, ("%s\n", s)) заменена на DEBUGJSONC(debug_class, debug_level, (s)), а в комментарии к новой функции dbgjson() в lib/util/debug.c прямо сказано: «msg is output without any added leading white space», «Any embedded "\n" characters are replaced with spaces».
  • Склейка длинных строк. Буфер форматирования debug-вывода ограничен (FORMAT_BUFR_SIZE = 4096 байт); в юнит-тесте lib/util/tests/test_json_logging.c, добавленном вместе с этими изменениями, сообщение длиной 5111 байт даёт не одну, а несколько записей (4095 и 1016 байт). Похоже, что очень длинная JSON-строка аудита может попасть в лог частями — парсеру, возможно, придётся склеивать такие записи. Это вывод из юнит-теста, а не документированное поведение.
  • Область и адресность. Аудит включается на каждом сервере отдельно; в домене с несколькими DC событие пишет только тот DC, который его обработал (без централизованного syslog картина будет неполной). Аутентификация через Kerberos пишется на DC (KDC), а не на члене домена; при NTLM — парой authentication + authorization.
  • Авторизация только успешная. Неудачные события авторизации Samba не логирует — по журналу нельзя судить о неуспешных авторизациях.
  • Двойной учёт парольных событий. Смена пароля попадает и в dsdb_password_audit, и в auth_audit как событие аутентификации (authDescription = "LDAP Modify") — при подсчёте событий это даёт дубли.
  • Регистр значения "action" у парольных событий. Man-страница пишет "change"/"reset", но код возвращает "Change"/"Reset" (source4/dsdb/samdb/ldb_modules/audit_log.c, функция get_password_action); юнит-тест source4/dsdb/samdb/ldb_modules/tests/test_audit_log.c проверяет именно заглавные — assert_string_equal("Reset", …) и assert_string_equal("Change", …). Парсеру значение лучше сравнивать без учёта регистра.
  • Секреты и усечение. В dsdbChange секретные значения заменяются на redacted: true, значения длиннее 1024 байт обрезаются (truncated: true) — полного значения в логе не будет.
  • Правка базы в обход Samba не логируется. Предупреждение в smb.conf(5): «Changes to sam.ldb made locally by the root user with direct access to the database are not logged to the system logs, but to the administrator's own console.» То есть локальный root-доступ к sam.ldb аудитом не покрывается — это и понятно, такой пользователь может просто отключить аудит.
  • fail2ban и NTLM. Документация Tranquil IT предупреждает: при NTLM-аутентификации к контроллеру домена подключается файловый сервер (а не сам клиент), поэтому надо настроить ignoreip, чтобы случайно не заблокировать собственный файловый сервер.
  • Фильтр fail2ban завязан на формат лога. failregex ищет подряд NT_STATUS_WRONG_PASSWORD, затем remoteAddress": "ipv4:<HOST>: — то есть опирается на конкретные имена полей и префикс ipv4:. Изменение формата (или отсутствие поля remoteAddress для какого-то типа аутентификации) тихо ломает блокировку. Перед внедрением фильтр стоит проверить fail2ban-regex на реальном логе.
  • Порты в примере fail2ban. В тюрьме перечислены порты 88,135,389,445,464,636,3328,3329 (дословно из источника). В вики Samba порты глобального каталога — 3268/tcp и 3269/tcp (см. Порты AD DC); расхождение в источнике никак не поясняется, так что перед копированием конфигурации список портов стоит сверить со своей инфраструктурой.
  • Имя класса в man-странице. В перечислении уровней smb.conf(5) пишет «Log levels for auth_audit and auth_audit_json are…», хотя класс в списке классов и в документации Tranquil IT называется auth_json_audit. Используйте имя из списка классов.
  • Расхождение версий JSON-схемы. Пример JSON на вики (2017 год, Samba 4.7) содержит для Authorization значение "version": {"major": 1, "minor": 0}, тогда как страница «Interpreting JSON Audit Logs» (2023) документирует для Authorization {"major": 1, "minor": 1}. Поле minor увеличивалось по мере добавления полей — парсер не должен жёстко фиксировать минорную версию.
  • Ротация. В smb.conf(5) описан только встроенный механизм самого debug-лога: max log size (в килобайтах, по умолчанию 5000) — «Samba periodically checks the size and if it is exceeded it will rename the file, adding a .old extension»; 0 означает отсутствие лимита. Отдельный файл, открытый через @PATH, в прочитанных источниках не описан — для него нужна внешняя ротация, а при сборе через rsyslog imfile учитывайте поведение при усечении файла (параметр reopenOnTruncate).
