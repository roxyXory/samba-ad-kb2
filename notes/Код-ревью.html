Код-ревью (CodeReview)

Суть

Ревью кода в проекте Samba обязательно. Правила страницы: код, написанный членом Samba Team, должен быть проверен другим членом команды; код от внешнего разработчика проверяют два члена Samba Team. Пункт политики уточняет, что каждый коммит в ветке master должен быть «отревьюен как минимум двумя членами Samba Team», причём участие в создании патча засчитывается как ревью: для члена команды это автор + один ревьюер, для внешнего разработчика — двое членов команды (без зачёта его участия). Подтверждением ревью служит тег Reviewed-by: в сообщении git-коммита — его проставляет ревьюер, не участвовавший в создании патча.

Ключевое

Политика обязательного ревью

  • Все изменения кода от члена Samba Team проверяются другим членом команды перед попаданием в репозиторий; код от внешнего разработчика — двумя.
  • Тег Reviewed-by: в сообщении коммита показывает, что патч прошёл ревью: ревьюер считает себя частично ответственным за патч и убеждён, что он разумный и полезный.
  • Процесс вдохновлён практикой ядра Linux, но значение тегов не всегда совпадает (в частности, в вопросах DCO — Developer's Certificate of Origin).

Подготовка патчей

  • Каждый патч-сет должен быть настолько мал, насколько это возможно.
  • Каждый патч должен менять только одну вещь.
  • Патч должен иметь соответствующее (подходящее) описание коммита.
  • Патчи, исправляющие баг, должны содержать соответствующий тег BUG.

Теги в сообщениях коммитов

Теги добавляются с помощью git commit --amend. Это документированные теги:

  • Signed-off-by — автор(ы) коммита; каждая строка патч-сета должна заканчиваться этим тегом. Формат:

    Signed-off-by: Author M. Writer <author@example.com>

    Git имеет встроенный ключ -s / --signoff для команд commit, cherry-pick и am.

  • Reviewed-by — для ревьюера, который не участвовал в создании патча. Это также документированный тег git, но у git нет и не планируется (по словам разработчиков git) ключа для его добавления — теги ревью добавляются в сообщение коммита вручную.

  • Pair-programmed-with — опционально при наличии нескольких авторов патча; обычно избыточен, так как вклад в создание патча уже засчитывается как участие в ревью.

  • Acked-by — этот тег не используется, чтобы не усложнять систему.

Ревью на практике (стиль кодирования)

  • C: стиль кодирования описан в файле README.Coding.md; патч должен соответствовать ему, где это возможно. Соблюдение поощряется ревью и git-хуками. Общие требования — строки не длиннее 80 символов и инициализация указателей:

    struct ldb_result *res = NULL;
struct ldb_message *msg = NULL;
TALLOC_CTX *mem_ctx = NULL;
struct loadparm_context *lp_ctx = NULL

    Учтите, что существующий старый код не обязан следовать текущим стандартам кодирования.

  • Python: должен следовать PEP8; make test проверяет это частично. Код должен быть совместим и с Python 2, и с Python 3.

  • Shell: скрипты должны быть POSIX-совместимыми /bin/sh, а не BASH. Нельзя считать, что /bin/sh — это BASH: например, Debian/Ubuntu используют dash. Если нужен BASH, используйте явно #!/bin/bash.

  • Неформальные правила: осмысленные имена переменных, например:

    res      — результат запроса ldb
msg      — сообщение ldb
mem_ctx  — контекст talloc
lp_ctx   — контекст loadparm

  • Избегайте лишней переработки кода (code churn): если в существующем коде нет ошибки и патч не улучшает его существенно — не трогайте его.

  • Автоматические тесты обязательны: используйте тесты для проверки новых возможностей и для гарантии, что изменения не ломают существующее поведение.

Инструменты для крупных изменений

  • Для масштабных изменений, затрагивающих кодогенераторы, #define в заголовках или проверки configure в Waf, особенно полезен инструмент gcc -E: он позволяет увидеть, во что развернётся препроцессор, и проверить результат таких изменений.

Куда отправлять патчи

  • Патчи отправляются на ревью согласно инструкциям на странице Contribute (см. Вклад в код Samba).

Действия ревьюера (Reviewers Action)

Ревьюер делает следующее:

  1. Применяет патч-сет к локальной копии ветки master с помощью git am (или выполняет pull из репозитория автора).
  2. Проводит ревью патчей, собирает и тестирует код.
  3. Если всё в порядке — добавляет тег Reviewed-by: к каждому коммиту патч-сета и запушивает в master через autobuild, либо выполняет git format-patch и отправляет патч-сет обратно автору.
  4. Если нет — отправляет автору комментарии и ждёт следующей итерации патч-сета.

Как ревьюить код (рекомендации metze)

Для полного ревью решения патчей нужны соответствующие проверки (careful_mode++):

  • Внимательно прочитать сообщение коммита.
  • Прочитать diffstat.
  • Читать патчи по частям (hunk by hunk) как обычный код, например с -U<contextlines> для контекста строк.
  • При необходимости включить very_careful_mode и проверить больше контекста с -U<contextlines>.
  • Использовать git grep, чтобы найти всех вызывающих (callers) изменённых функций.
  • Убедиться, что был сделан хотя бы один ручной runtime-тест, покрывающий путь кода, либо запросить такой тест.

Ревью собственного кода

  • Ревьюите собственный код: «самое важное — каждый проверяет свои патчи так же тщательно, как чужие» (рекомендация metze со страницы, а не формальный пункт политики). Самопроверка не заменяет внешнее Reviewed-by: — ревьюер обязан не участвовать в создании патча; в зачёт «двух ревью» политики при этом идёт участие автора в создании патча (см. раздел «Суть»). Исследования показывают, что автор находит больше дефектов в своём коде, чем кто-либо другой.

Как работать с ревью (этикет)

  • Процесс ревью сравнивается с игрой в теннис: если ваш патч-сет «в игре», на замечания нужно отвечать быстро — каждое сообщение (ping) должно получать ответ (pong) в течение пары дней. Чем дольше патч-сет не отвечает, тем больше он рискует стать устаревшим (например, из-за изменений в master) и его придётся перерабатывать.

Подводные камни

  • У git нет и не планируется ключа для добавления тега Reviewed-by: — теги ревью вставляются в сообщение коммита вручную (через git commit --amend).
  • Теги сообщений коммитов вдохновлены ядром Linux, но их значение в Samba не всегда совпадает со значением в ядре — особенно в вопросах DCO.
  • Тег Acked-by в Samba не используется.
  • Существующий старый код может не соответствовать текущим стандартам кодирования — не стоит «чинить» его без необходимости (лишний code churn).
  • Shell-скрипты нельзя писать в расчёте на BASH: /bin/sh в Debian/Ubuntu — это dash; при необходимости bash указывайте шебанг #!/bin/bash.
  • Python-код должен быть совместим одновременно с Python 2 и Python 3.
  • Изменения кодогенераторов, #define в заголовках и configure-проверок Waf требуют особо внимательной проверки (например, просмотром вывода gcc -E).
  • Патч-сеты, в которых новый код сначала вводится, а сразу в следующем патче перерабатывается, — плохой стиль: ревьюеры просят такие патчи переделать.
  • Без ответа на замечания ревьюеров патч-сет быстро устаревает и его приходится переделывать.
