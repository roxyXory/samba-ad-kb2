База знаний Samba AD DC

Репликация SysVol

Суть

Samba AD до сих пор не поддерживает репликацию SysVol — каталога с содержимым групповых политик (GPO) и сценариями входа, который DFS-R/FRS реплицируют между Windows DC. При двух и более DC (Присоединение второго DC к домену) содержимое SysVol нужно синхронизировать обходными путями; без этого на новом DC с нестандартными GPO падает даже samba-tool ntacl sysvolreset. Варианты со страницы join: «Rsync based» (только Samba DC — быстрый и простой, односторонний), «Bidirectional Rsync/Unison» и «Bidirectional Rsync/osync» (двусторонние, сложнее), «Robocopy based» (Samba DC → Windows DC; процедура, команда и предупреждения — в Windows DC рядом с Samba DC).

Ключевое

Идея rsync-варианта

  • Репликация односторонняя: один DC — «мастер», на нём редактируют все GPO/скрипты; остальные DC регулярно забирают копию, локальные изменения на них затираются.
  • Мастер — DC с ролью PDC_Emulator: GPMC по умолчанию подключается именно к нему (см. Передача и захват FSMO ролей).
  • Модуль rsync на мастере — read-only: ничего нельзя «затолкать» обратно.
  • Реплицируется всё дерево SysVol: политики (GPT.INI, Registry.pol, Machine/User-каталоги) и скрипты.
  • Транспорт — собственный демон rsync с файлом секретов (не SSH; допускается адаптация на SSH-туннель — тогда MITM-риск ниже).

Настройка на PDC Emulator

  1. Установить rsync с поддержкой расширенных ACL.

  2. /etc/xinetd.d/rsync (запуск демона через xinetd, доступ ограничен сетью DC):

    only_from       = 10.99.0.0/28
server          = /usr/bin/rsync
server_args     = --daemon

  3. /etc/rsyncd.conf — модуль:

    [SysVol]
path = /usr/local/samba/var/locks/sysvol/
read only = yes
auth users = sysvol-replication
secrets file = /usr/local/samba/etc/rsyncd.secret

  4. /usr/local/samba/etc/rsyncd.secret — строка sysvol-replication:pa$$w0rd (не world-readable), перезапустить xinetd.

Настройка на остальных DC

  1. /usr/local/samba/etc/rsync-sysvol.secret — файл с одним паролем (не world-readable).
  2. Сначала пробный прогон с --dry-run, затем рабочий запуск:
rsync --dry-run -XAavz --delete-after --password-file=/usr/local/samba/etc/rsync-sysvol.secret rsync://sysvol-replication@{IP-of-your-PDC-Emulator}/SysVol/ /path/to/your/sysvol/folder/
  1. По расписанию (cron, каждые 5 минут):
*/5 * * * * rsync -XAavz --delete-after --password-file=/usr/local/samba/etc/rsync-sysvol.secret rsync://sysvol-replication@{IP-of-your-PDC-Emulator}/SysVol/ /path/to/your/sysvol/folder/

Предпосылка: одинаковые ID-маппинги

Синхронизация SysVol работает корректно, только если встроенные пользователи/группы имеют одинаковые ID на всех DC — иначе idmap.ldb с держателя PDC_Emulator предварительно синхронизируют вручную (процедура в Присоединение второго DC к домену).

Подводные камни

  • Односторонность: GPO правят только на PDC Emulator; изменения, сделанные на других DC, будут перезаписаны при следующей синхронизации.
  • --delete-after деструктивен: команда удаляет в целевом каталоге всё, чего нет на источнике, — сверить путь назначения, прежде чем запускать (можно повредить систему).
  • Задержка распространения: cron-интервал (в примере 5 минут) — изменения доходят не мгновенно.
  • rsync без SSH небезопасен (риск man-in-the-middle); для большинства инсталляций содержимое SysVol неконфиденциально, но при возможности используют SSH-вариант.
  • Двусторонние схемы (Unison, osync) требуют сторонних скриптов и cron-задач на каждом DC против каждого — сложнее в сопровождении.
  • Кластеризация через GlusterFS+CTDB для AD DC не вариант: по утверждению самой страницы-источника, CTDB (необходимый для кластерного Samba) несовместим с ролью Samba AD DC; о CTDB как компоненте кластера из членов домена — CTDB и кластерный Samba.
  • Не забывать samba-tool ntacl sysvolreset после ручного восстановления SysVol на новом DC (см. Присоединение второго DC к домену).
