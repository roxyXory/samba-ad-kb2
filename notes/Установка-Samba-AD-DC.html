База знаний Samba AD DC

Установка Samba как контроллера домена Active Directory

Суть

Страница описывает установку Samba и подготовку (provisioning) первого контроллера домена (DC) для построения нового леса Active Directory; та же инструкция применяется при миграции домена Samba NT4 на AD (classic upgrade). Начиная с версии 4.0 (2012 год) Samba способна работать контроллером домена AD и обслуживает функциональный уровень леса Windows Server 2008 R2. Весь процесс состоит из пяти шагов: установка Samba и сопутствующих пакетов, удаление заготовочных конфигурационных файлов Samba и Kerberos, provisioning утилитой samba-tool, правка smb.conf (включение Group Policy и других функций), настройка окружения под конкретный дистрибутив Unix/Linux.

Ключевое

Что поддерживает Samba AD DC

  • Функциональный уровень леса — Windows Server 2008 R2 (достаточно для предприятий с Windows 10/11 и строгими требованиями соответствия, включая NIST 800-171). Начиная с Samba 4.19 можно задать более высокий функциональный уровень, но это work in progress — не для production.
  • В качестве бэкенда AD — только встроенный LDAP-сервер (OpenLDAP и другие внешние LDAP-серверы не поддерживаются).
  • Kerberos KDC — только Heimdal. MIT Kerberos KDC поддерживается экспериментально (Samba 4.7+, сборка с опцией --with-system-mitkrb5).
  • В production рекомендуется два и более DC ради отказоустойчивости.
  • Установка Samba и provisioning DC не включают функциональность Group Policy автоматически — после provisioning нужно вручную включить её в smb.conf: добавить в секцию [global] параметр apply group policies = yes (страница Group Policy, раздел Winbind); ручное применение политик — samba-gpupdate --force.

Пример из документации: Hostname DC1, IP контроллера 10.99.0.1, домен аутентификации SAMDOM.EXAMPLE.COM, домен верхнего уровня EXAMPLE.COM.

Подготовка (свежая установка)

  • Выбрать DNS-домен для леса AD: не использовать домен верхнего уровня организации (он начнёт резолвиться в DC, и публичный сайт станет недоступен); определить поддомен — в примере SAMDOM.EXAMPLE.COM. Это же имя станет Kerberos realm. В лаборатории можно использовать, например, .INTERNAL, но только там: .internal — недействительный TLD (с 01.11.2015 удостоверяющие центры не выдают на такие имена сертификаты; RFC 8375 вместо подобных имён предлагает home.arpa) — для production брать поддомен принадлежащего вам домена, см. Именование домена FAQ.
  • Имя хоста DC — менее 15 символов (ограничение netbios); в примере DC1. Не использовать термины NT4 (PDC, BDC) — таких режимов в AD нет.
  • Задать статический IP и сделать резервацию на роутере: DC станет DNS-резолвером для всех рабочих станций домена, поэтому IP может понадобиться вынести за пределы пула DHCP.
  • Отключить инструменты, автоматически обновляющие /etc/resolv.conf (например, resolvconf).
  • Проверить, что /etc/hosts на DC резолвит FQDN и короткое имя в LAN IP контроллера:
127.0.0.1     localhost
10.99.0.1     DC1.samdom.example.com     DC1
  • Узнать путь к существующему smb.conf и удалить его:
# smbd -b | grep "CONFIGFILE"
   CONFIGFILE: /usr/local/samba/etc/samba/smb.conf
  • Если Samba ранее уже стояла на этом хосте — удалить все файлы баз данных (*.tdb, *.ldb). Папки с базами показывает команда:
# smbd -b | egrep "LOCKDIR|STATEDIR|CACHEDIR|PRIVATE_DIR"
  LOCKDIR: /usr/local/samba/var/lock/
  STATEDIR: /usr/local/samba/var/locks/
  CACHEDIR: /usr/local/samba/var/cache/
  PRIVATE_DIR: /usr/local/samba/private/

Чистое окружение предотвращает смешивание файлов старой и новой установок.

Provisioning (создание домена)

  • Provisioning требует прав root.
  • Рекомендуется включить NIS-расширения параметром --use-rfc2307: недостатков нет, а включение их в уже существующем домене требует ручного расширения схемы AD.
  • Справка по параметрам: # samba-tool domain provision --help.

Интерактивный режим. Сначала отбросить созданный установкой smb.conf, иначе provisioning завершится ошибкой:

# mv /etc/samba/smb.conf /etc/samba/smb.conf.initial

затем:

# samba-tool domain provision --use-rfc2307 --interactive

Диалог выглядит так:

 Realm [SAMDOM.EXAMPLE.COM]: SAMDOM.EXAMPLE.COM
  Domain [SAMDOM]: SAMDOM
  Server Role (dc, member, standalone) [dc]: dc
  DNS backend (SAMBA_INTERNAL, BIND9_FLATFILE, BIND9_DLZ, NONE) [SAMBA_INTERNAL]: SAMBA_INTERNAL
  DNS forwarder IP address (write 'none' to disable forwarding) [10.99.0.1]: 8.8.8.8
 Administrator password: Passw0rd
 Retype password: Passw0rd

По завершении выводится итог: Server Role: active directory domain controller, Hostname: DC1, NetBIOS Domain: SAMDOM, DNS Domain: samdom.example.com, DOMAIN SID.

Неинтерактивный режим (те же настройки одной командой):

# samba-tool domain provision --server-role=dc --use-rfc2307 --dns-backend=SAMBA_INTERNAL --realm=SAMDOM.EXAMPLE.COM --domain=SAMDOM --adminpass=Passw0rd

Параметры:

  • --use-rfc2307 — включает NIS-расширения, нужные для вкладки ADUC Unix Attributes.
  • --realm — Kerberos realm: домен AD DNS в верхнем регистре, например SAMDOM.EXAMPLE.COM.
  • --domain — NetBIOS-имя домена (Workgroup): одно слово, не длиннее 15 символов, без точки; рекомендуется первая часть AD DNS-домена (samdom); не использовать короткое имя хоста.
  • --server-role=dc — роль контроллера домена.
  • --dns-backend — бэкенд DNS; первый DC в AD обязан устанавливаться с DNS-бэкендом.
  • DNS forwarder IP address — доступен только при бэкенде SAMBA_INTERNAL (настройка DNS forwarder — см. Samba Internal DNS Back End).
  • --adminpass — пароль администратора домена; при несоответствии требованиям сложности provisioning завершится ошибкой.

Для сервера с несколькими сетевыми интерфейсами используют --option="interfaces=lo eth0" --option="bind interfaces only=yes" — это позволяет samba-tool зарегистрировать корректный LAN IP в каталоге.

Настройка DNS-бэкенда AD

Пропустить, если использовали SAMBA_INTERNAL. Для BIND: настроить BIND DNS server и модуль BIND9_DLZ (см. BIND9 DLZ DNS бэкенд), затем запустить BIND:

# systemctl start named

Настройка DNS-резолвера

Члены домена находят службы (LDAP, Kerberos) через DNS, поэтому DC должен использовать DNS, разрешающий зоны AD. В /etc/resolv.conf указать домен AD в search и IP контроллера в nameserver:

search samdom.example.com
nameserver 10.99.0.1

Других строк добавлять не нужно: DC использует сам себя как nameserver и находит остальные DNS-данные на своём DNS-сервере.

Настройка Kerberos

Во время provisioning Samba создала файл конфигурации Kerberos — скопировать его в конфигурацию ОС (путь всегда брать из вывода provisioning):

# cp /usr/local/samba/private/krb5.conf /etc/krb5.conf

Созданный заранее конфиг использует SRV-записи DNS для поиска KDC.

Запуск и проверка DC

Запуск вручную:

# samba

Samba не поставляет init-скрипты System V, systemd, upstart и другие файлы служб: при установке из пакетов использовать включённый в пакет скрипт/юнит, при самостоятельной сборке — см. Managing the Samba AD DC Service.

Проверка, что шары на месте (вывод различается до/после Samba 4.11.0):

$ smbclient -L localhost -N

Шары netlogon и sysvol создаются автоматически при provisioning и обязаны существовать на DC.

Проверка аутентификации — подключение к шаре netlogon от имени администратора домена:

$ smbclient //localhost/netlogon -UAdministrator -c 'ls'

Обратная зона DNS (опционально)

Перед созданием зоны Samba AD DC должен быть запущен. Создание обратной зоны:

# samba-tool dns zonecreate <Your-AD-DNS-Server-IP-or-hostname> 0.99.10.in-addr.arpa -U Administrator
 Password for [administrator@SAMDOM.EXAMPLE.COM]:
 Zone 0.99.10.in-addr.arpa created successfully

Для нескольких подсетей команду повторяют с данными каждой. Зона работает сразу, без перезапуска Samba или BIND. Затем добавить PTR-запись для DC (для FQDN dc1.samdom.example.com и IP 10.99.0.1):

# samba-tool dns add <Your-AD-DNS-Server-IP-or-hostname> 0.99.10.in-addr.arpa 1 PTR dc1.samdom.example.com -U Administrator
 Password for [administrator@SAMDOM.EXAMPLE.COM]:
 Record added successfully

Проверка DNS (опционально)

$ host -t SRV _ldap._tcp.samdom.example.com.
 _ldap._tcp.samdom.example.com has SRV record 0 100 389 dc1.samdom.example.com.

$ host -t SRV _kerberos._udp.samdom.example.com.
 _kerberos._udp.samdom.example.com has SRV record 0 100 88 dc1.samdom.example.com.

$ host -t A dc1.samdom.example.com.
 dc1.samdom.example.com has address 10.99.0.1

$ host -t PTR 10.99.0.1
 1.0.99.10.in-addr.arpa domain name pointer dc1.samdom.example.com.

Проверка Kerberos (опционально)

Запросить билет Kerberos для учётной записи администратора домена:

$ kinit administrator
 Password for administrator@SAMDOM.EXAMPLE.COM:

Показать кэшированные билеты:

$ klist
 Ticket cache: FILE:/tmp/krb5cc_0
 Default principal: administrator@SAMDOM.EXAMPLE.COM

Если принципал не передан в формате user@REALM, Kerberos realm добавляется автоматически; realm всегда вводится в верхнем регистре.

Синхронизация времени

Kerberos требует синхронизированного времени на всех членах домена; настраивается службами ntpd или chrony (см. Time Synchronization). Если Samba DC администрирует Group Policy, можно задать GPO, синхронизирующий рабочие станции с time.windows.com.

DC как файловый сервер

Samba не рекомендует использовать DC как файловый сервер: лучше держать более одного DC (это хорошая мера резервирования и упрощает обновления), обновления DC выполняются установкой с нуля с репликацией изменений, у DC и файлового сервера разные циклы развития, а на DC принудительно включён обязательный SMB signing. Если всё же решено использовать DC как файловый сервер — см. раздел «Подводные камни».

Подводные камни

  • Samba 4.19+: поддержка более высоких функциональных уровней — work in progress, в production не использовать.
  • Установка и provisioning не включают Group Policy автоматически — после provisioning требуется добавить в [global] параметр apply group policies = yes (Group Policy → Winbind; ручное применение политик — samba-gpupdate --force).
  • Samba не поддерживает переименование AD DNS-зоны и Kerberos realm — provisioning выполнять доменом, который не придётся менять.
  • Не использовать .local в качестве TLD — он занят Avahi.
  • Не использовать домен верхнего уровня организации: домен установки Samba будет резолвиться в контроллер, и публичный сайт станет недоступен.
  • Имя хоста DC — менее 15 символов; не использовать PDC/BDC в качестве имени — в AD таких режимов нет, будет путаница.
  • Имя хоста и FQDN не должны резолвиться в 127.0.0.1 или любой другой IP, кроме LAN IP контроллера.
  • Пути в вики даны для самособранной Samba (/usr/local/samba); для пакетов дистрибутива пути другие (обычно /etc/samba и /var/lib/samba) — сверяться с документацией дистрибутива.
  • Provisioning требует прав root.
  • При интерактивном provisioning существующий smb.conf нужно отбросить (переименовать/удалить), иначе процесс завершится ошибкой.
  • Несоответствующий требованиям сложности пароль администратора приводит к падению provisioning.
  • Не использовать NONE в качестве DNS-бэкенда; при BIND не использовать BIND9_FLATFILE — оба не поддерживаются и будут удалены в будущих версиях Samba.
  • После provisioning первого DC новые контроллеры в этом домене не provision-ят, а присоединяют (join).
  • Не создавать символическую ссылку на сгенерированный krb5.conf: с Samba 4.7 каталог /usr/local/samba/private/ недоступен пользователям кроме root, и через symlink файл не смогут прочитать — например, сломаются динамические DNS-обновления при бэкенде BIND_DLZ.
  • В /etc/resolv.conf контроллера не добавлять лишних строк: DC должен использовать сам себя как nameserver.
  • Запустить Samba AD DC до добавления обратной зоны.
  • Обратные (PTR) записи не добавляются автоматически — их создают вручную или настраивают Windows-компьютеры на самостоятельное добавление при обновлении DNS-записей.
  • Kerberos realm в kinit всегда вводить в верхнем регистре.
  • Не использовать AD DC как файловый сервер при нескольких DC — это проблематично и может вызывать странные ошибки; допускается только если это единственный экземпляр Samba в домене (лучше завести отдельный Unix domain member, например в VM).
  • На файловых шарах DC авто-включённый VFS-объект acl_xattr позволяет настраивать шары только с Windows ACL — POSIX ACL не работают.
  • Дополнительный VFS-объект на шаре DC нельзя задавать как vfs objects = recycle — это отключит дефолтные dfs_samba4 и acl_xattr; нужно vfs objects = dfs_samba4 acl_xattr recycle.
  • На DC не добавлять строки idmap config, используемые на Unix domain member, — они не работают и вызывают проблемы.
  • Права на шарах DC задавать только из Windows; старые методы (force user и т.п.) не работают корректно и вызывают проблемы.
