Миграция NT4-домена в Samba AD (classicupgrade)

Суть

samba-tool domain classicupgrade — встроенная в samba-tool функция полной замены существующего Samba NT4-домена на Samba Active Directory. Она выполняет роль шага provisioning в инструкции по установке AD DC и работает со всеми passdb-бэкендами (smbpasswd, tdbsam, ldapsam). Пользователи и машины после миграции просто переподключаются к новому контроллеру без повторного ввода в домен — SID домена, RID и пароли аккаунтов (включая машинный пароль DC из secrets.tdb) переносятся из старых баз, поэтому доверие машинных аккаунтов членов домена сохраняется. Межлесные и междоменные доверия NT4 при этом не переносятся — их создают заново уже как доверия AD (см. Доверительные отношения между доменами). Миграция односторонняя: как только клиенты обратились к новому AD DC, вернуться к NT4-домену нельзя даже откатом изменений, поэтому процесс сначала прогоняют в изолированной от production сети. Отдельный сценарий — переезд с Windows AD: до вывода Windows DC нужно поднять схему и preparation level штатным adprep, а домен с функциональным уровнем 2012 или выше Samba долгое время присоединить не могла (ошибка WERR_DS_INCOMPATIBLE_VERSION).

Ключевое

Что такое classicupgrade

  • Это функция внутри samba-tool, предназначенная для полной замены существующего Samba NT4-домена. Пользователи и машины после конвертации просто переподключаются к новому Samba AD — вручную заново вводить их в домен не требуется.
  • «Doing a classicupgrade is possible from all passwd backends (smbpasswd, tdbsam and ldapsam)» — поддерживаются все три бэкенда passdb.
  • Процедура применима как к апгрейду существующей установки Samba на том же сервере, так и к переносу на новый сервер (например, при одновременной замене железа).
  • classicupgrade заменяет шаг provisioning: после успешного апгрейда нужно продолжить по инструкции установки AD DC (см. Установка Samba AD DC), пропустив provisioning.
  • Запуск возможен и на PDC, и на BDC-инсталляции; в коде serverrole берётся из старого smb.conf, а если роль не PDC/BDC, то DNS-бэкенд принудительно ставится в NONE.

Точная команда

Синтаксис (man-страница samba-tool, раздел domain classicupgrade): domain classicupgrade [options] classic_smb_conf, описание — «Upgrade from Samba classic (NT4-like) database to Samba AD DC database». Старый smb.conf передаётся последним позиционным аргументом.

С внутренним DNS (из вики, дословно):

# samba-tool domain classicupgrade --dbdir=/usr/local/samba.PDC/dbdir/ \
--realm=SAMDOM.EXAMPLE.COM --dns-backend=SAMBA_INTERNAL /usr/local/samba.PDC/etc/smb.PDC.conf

С BIND9_DLZ (из вики, дословно):

# samba-tool domain classicupgrade --dbdir=/usr/local/samba.PDC/dbdir/ \
--realm=SAMDOM.EXAMPLE.COM --dns-backend=BIND9_DLZ /usr/local/samba.PDC/etc/smb.PDC.conf

Пояснения параметров из вики:

--dbdir=                 Path to samba classic DC directory, containing all databases required for
                         the migration
--realm=                 Set the realm name
--dns-backend=           Optional. 
                         Required if BIND9_DLZ should be used as DNS backend.
                         Default is the internal DNS (SAMBA_INTERNAL)

Если у контроллера несколько NIC, classicupgrade сам выбирает IPv4/v6-адрес одного из них; чтобы привязать Samba к конкретному интерфейсу и localhost, в вики предлагается добавить в команду --option="interfaces=lo eth0" --option="bind interfaces only=yes".

Опции, которые реально объявлены в коде команды (python/samba/netcmd/domain/classicupgrade.py):

  • --dbdir=DIR — «Path to samba classic DC database directory» (каталог старых баз).
  • --testparm=PATH — путь к утилите testparm прежней установки: тогда пути по умолчанию берутся из старой инсталляции. --dbdir и --testparm — альтернативы, одну из них указать обязательно (иначе ошибка «Please specify either dbdir or testparm»); если заданы обе, --dbdir игнорируется с предупреждением «both dbdir and testparm specified, ignoring dbdir.»
  • --targetdir=DIR — «Path prefix where the new Samba 4.0 AD domain should be initialised».
  • -q/--quiet, -v/--verbose.
  • --dns-backend — выбор из SAMBA_INTERNAL (по умолчанию), BIND9_FLATFILE, BIND9_DLZ, NONE; в тексте справки: NONE пропускает настройку DNS целиком (этот DC не будет DNS-сервером). В вики для этой процедуры описаны только SAMBA_INTERNAL и BIND9_DLZ.
  • --use-xattrs=yes|no|auto (по умолчанию auto) и --use-ntvfs — объявляются только если Samba собрана с файловым сервером NTVFS (samba.is_ntvfs_fileserver_built()). Справка: «Define if we should use the native fs capabilities or a tdb file for storing attributes likes ntacl when --use-ntvfs is set. auto tries to make an intelligent guess based on the user rights and system capabilities». При обычной сборке (s3fs) --use-xattrs=no без --use-ntvfs отклоняется ошибкой «--use-xattrs=no requires --use-ntvfs (not supported for production use). Please re-run with --use-xattrs omitted.», а режим auto даёт eadb = False, то есть атрибуты хранятся в xattr файловой системы.
  • --realm — это общая опция Samba (-r|--realm=REALM), а не специфичная для classicupgrade; man-страница пишет: «Set the realm for the domain. Note that specifying this parameter here will override the realm parameter in the ${prefix}/etc/smb.conf file.» В коде classicupgrade значение из --realm подставляется в старый конфиг перед апгрейдом.

Запускать classicupgrade нужно от root: «The classicupgrade step must be run as user root. Otherwise you will get permission denied errors!». Файл smb.conf из позиционного аргумента и каталог --dbdir должны существовать — иначе команда сразу падает с CommandError.

Что обязательно перенести: tdb-базы и старый smb.conf

Вся информация берётся из баз старого PDC, поэтому их надо собрать в одном каталоге (в вики — /usr/local/samba.PDC/dbdir/). Создание каталогов и перенос баз (дословно из вики; именно mv, чтобы старая установка не подняла их снова при автозапуске):

# mkdir -p /usr/local/samba.PDC/dbdir/
# mkdir /usr/local/samba.PDC/etc

# mv /usr/local/samba/private/secrets.tdb /usr/local/samba.PDC/dbdir/
# mv /usr/local/samba/private/schannel_store.tdb /usr/local/samba.PDC/dbdir/
# mv /usr/local/samba/private/passdb.tdb /usr/local/samba.PDC/dbdir/
# mv /usr/local/samba/var/locks/group_mapping.tdb /usr/local/samba.PDC/dbdir/
# mv /usr/local/samba/var/locks/account_policy.tdb /usr/local/samba.PDC/dbdir/

Перенос старого конфига:

# mv /usr/local/samba/etc/smb.conf /usr/local/samba.PDC/etc/smb.PDC.conf

Роль отдельных файлов (по коду python/samba/upgrade.py и вики):

  • secrets.tdb — обязателен: без него апгрейд падает с «Could not open '%s', the Samba3 secrets database… Perhaps you specified the incorrect smb.conf, --testparm or --dbdir option?». Оттуда берутся доменное имя (если нет workgroup), пароль машинного аккаунта DC (get_machine_password) и, для ldapsam, пароль привязки к LDAP (get_ldap_bind_pw).
  • passdb.tdb + group_mapping.tdb — пользователи, группы и их маппинги (для бэкендов smbpasswd/tdbsam).
  • account_policy.tdb — парольная политика.
  • schannel_store.tdb — переносится вики-инструкцией в общий каталог баз.
  • Дополнительно classicupgrade пытается прочитать wins.dat и idmap-базу в том же --dbdir. Если их нет — это не ошибка: в примере вывода вики видно «Cannot open wins database, Ignoring: [Errno 2] No such file or directory: '/usr/local/samba.PDC/dbdir/wins.dat'» и «Cannot open idmap database, Ignoring». Обратите внимание: wins.dat в списке mv из вики не упомянут, хотя читается именно из --dbdir.

Что мигрирует

  • SID домена и RID. Новый домен создаётся на основе SID старого NT4-домена, а аккаунты сохраняют свои SID (provision вызывается с domainsid и next_rid из старой базы). Следующий свободный RID считается от максимального: в примере вывода вики «Next rid = 1007». Именно поэтому клиенты и машины продолжают работать без повторного ввода в домен — Windows опознаёт аккаунты по SID.
  • Пользователи, группы, алиасы и членство. Импортируются пользовательские и машинные аккаунты, группы и локальные группы вместе с участниками; в примере вывода: «Adding groups / Importing groups … Adding users / Importing users / Adding users to groups». Уже существующие группы пропускаются с предупреждением, например «Group already exists sid=…-513, groupname=Domain Users existing_groupname=Domain Users, Ignoring.».
  • Парольная политика. Переносятся только min password length, password history, minimum password age, maximum password age, lockout duration (в терминах NT: minPwdLength, pwdHistoryLength, minPwdAge, maxPwdAge, lockoutDuration). Не переносятся: reset count minutes, user must logon to change password, bad lockout minutes, disconnect time — это прямо перечислено комментарием в коде.
  • POSIX-атрибуты и idmap. Импортируется idmap-база (нижняя граница диапазона выставляется по старому high-water mark), а в AD записываются uidNumber/gidNumber (и posixAccount/posixGroup), unixHomeDirectory, loginShell, msSFU30NisDomain — provision выполняется с use_rfc2307=True. Источники значений: старый idmap, а при его отсутствии — записи /etc/passwd (или LDAP-атрибуты для ldapsam). Подробнее про idmap — Idmap бэкенды и RFC2307.
  • WINS-база — если wins.dat есть, записи переносятся («Importing WINS database»).
  • Пароль Administrator. В конце апгрейда выполняется «Setting password for administrator»: пароль AD-администратора становится паролем старого аккаунта administrator, а если такого нет — аккаунта root (сообщение «Administrator password has been set to password of user '%s'»). Для аккаунта administrator жёстко требуется RID 500: иначе «User 'Administrator' in your existing directory has SID … expected it to be …-500» и ProvisioningError. Про root выводятся предупреждения: если у него SID -500, то «User root has been replaced by Administrator», иначе «User root has been kept in the directory, it should be removed in favour of the Administrator user».
  • Машинный пароль DC переносится из secrets.tdb — благодаря этому доверие машинных аккаунтов членов домена сохраняется: сами машинные пароли лежат в старых базах, компьютеры не переприсоединяются. Это не межлесные/междоменные доверия — те не переносятся (см. ниже и Доверительные отношения между доменами).
  • BDC. Аккаунт BDC понижается до обычного машинного аккаунта: «Demoting BDC account trust for %s, this DC must be elevated to an AD DC using 'samba-tool domain dcpromo'» (команда domain dcpromo задокументирована в man-странице как «Promote an existing domain member or NT4 PDC to an AD DC»). Межлесные/междоменные доверия NT4 не переносятся: «Skipping inter-domain trust from domain %s, this trust must be re-created as an AD trust».
  • Функциональный уровень. Апгрейд провижинит домен с dom_for_fun_level=dsdb.DS_DOMAIN_FUNCTION_2003 (в libds/common/flags.h DS_DOMAIN_FUNCTION_2003 = 2), то есть и домен, и лес получают уровень 2003 (в provision значение по умолчанию, если параметр не задан, — DS_DOMAIN_FUNCTION_2008_R2). Повышать уровень нужно отдельно (см. ниже).

Что не мигрирует и что нельзя изменить потом

  • Не все LDAP-атрибуты. Для passdb backend = ldapsam вики прямо предупреждает: «Sadly classicupdate currently does not migrate all attributes found in LDAP» (в вики указан трекер — bug report #9908). Улучшения, если они появятся, сработают только в момент апгрейда — после миграции уже нет. Обходной путь из вики: перевести LDAP старого домена на нестандартный порт (если он на той же машине, что и новый AD) и скриптом перенести нужные атрибуты в LDIF, затем импортировать их в sam.ldb:
# ldbmodify -H path/to/sam.ldb LDIFfilename
  • AD-имя и realm. «Currently Samba does not provide capabilities to change the AD Domain Name afterwards!» — имя AD-домена/realm выбирается один раз и навсегда (это согласуется с Именование домена FAQ).
  • Реестр/шары старого PDC. В коде upgrade.py вызов import_registry(...) закомментирован с пометкой # FIXME, то есть определения шар из реестра Samba 3 не переносятся.
  • Пользователи с RID < 1000. Код пропускает «well-known» записи: «Skipping wellknown rid=%d (for username=%s)». Если такие пользователи должны существовать в AD, их RID надо изменить до апгрейда (см. ниже).
  • Маппинги well-known SID на Unix-группы. Вики: если well-known SID (например, Domain Users) были смаппированы на Unix-группу, такие маппинги надо удалить и не создавать заново.
  • Unix ID, равные Windows RID. Вики не рекомендует использовать Windows RID как uidNumber/gidNumber и советует поменять такие значения и снять Unix ID с well-known SID до апгрейда.

Подготовка: необратимость, дубли SID, конфликты имён

  • Обратимость: «The migration from an NT4-style domain to Active Directory is one way! This means that once your clients contact your migrated AD Domain Controller, they will never be able to access the NT4-style domain again - even if you roll back your changes!» Вики настоятельно рекомендует сначала прогнать процесс в отдельной от production сети.
  • Дубли SID: они встречаются в старых базах из-за отсутствия проверок, ручных правок и т. п. Проверять их надо до апгрейда — иначе classicupgrade невозможен. Для ldapsam вики даёт скрипт, который ищет дубли по выводу slapcat (скрипт в вики написан под Python 2 — print без скобок); для smbpasswd/tdbsam — разбирать вывод:
# pdbedit -Lv
# net groupmap list
  • Смена SID у группы — удалить маппинг и создать заново (новый SID получит следующий свободный RID):
# net groupmap delete ntgroup="demo group"
Successfully removed demo group from the mapping db

# net groupmap add ntgroup="Demo Group" unixgroup="demo group"
No rid or sid specified, choosing a RID
Got RID 1009
Successfully added group Demo Group to the mapping db as a domain group
  • Смена RID у пользователя/машины — вручную:
# net maxrid
Currently used maximum rid: 3001

# pdbedit -U 3002 -u demo1
...
User SID:   S-1-5-21-4097619914-84555263-3210783664-3002
  • Код дополнительно проверяет совпадения и падает: «Please remove duplicate group sid entries before upgrade.», «Please remove duplicate user sid entries before upgrade.», «Please remove duplicate sid entries before upgrade.» и «Please remove common user/group names before upgrade.» (последнее — если имя пользователя совпадает с именем группы; в вики то же сообщение приведено как «ProvisioningError: Please remove common user/group names before upgrade.»). Также требуется уникальность displayName у групп.
  • slapd.conf только при ldapsam: если объектов много, надо поднять лимит выдачи поиска, иначе classicupgrade не вычитает всё: sizelimit {<integer>|unlimited} (по умолчанию 500).
  • Имя DC: netbios name задаётся в старом smb.conf, который пойдёт на вход апгрейду (например, netbios name = DC1), и обязан совпадать с коротким hostname будущего DC. Переименование DC после миграции возможно, но вики называет это лишней работой и источником проблем.
  • Realm: если в старом smb.conf нет параметра realm, а старая установка — PDC/BDC, апгрейд останавливается ошибкой «No realm specified in smb.conf file and being a DC. That upgrade path doesn't work! Please add a 'realm' directive to your old smb.conf…». Либо добавьте realm в старый конфиг, либо задайте --realm в командной строке.
  • Порядок запуска: на той же машине, что старый PDC, службы smbd, nmbd и winbind останавливаются, а LDAP-сервер (при ldapsam) продолжает работать до конца апгрейда.
  • Повторный запуск classicupgrade требует очистки результата предыдущей попытки:
# rm -f /usr/local/samba/etc/smb.conf
# rm -rf /usr/local/samba/private/*
  • Если на машине есть ещё и старая Samba, вики советует поставить /usr/local/samba/bin/ и /usr/local/samba/sbin/ в начало $PATH и проверять версию командой samba --version, чтобы случайно не запустить старые бинарники.

После classicupgrade: зачистка и продолжение

Список вики:

  • Для ldapsam — выключить внешний LDAP-сервер: Samba AD поднимает собственный LDAP на портах 389/tcp и 636/tcp.
  • Отключить автоматический запуск служб старого PDC и LDAP.
  • Включить автозапуск службы Samba AD (см. Управление службой AD DC).
  • Для smbpasswd/tdbsam — удалить доменные группы из /etc/group (все группы с маппингом импортированы вместе с участниками) и убрать Samba-пользователей из /etc/passwd (теперь они хранятся в AD).
  • При внутреннем DNS добавить в smb.conf строку форвардера, например dns forwarder = 8.8.8.8.
  • В /etc/resolv.conf первым nameserver указать IP-адрес DC.
  • Установить winbind, если он ещё не установлен.
  • Жёсткое ограничение вики: «Once you have upgraded your NT4-style domain to an AD domain, be very selective about what lines you add to your new smb.conf. Never add any idmap config or vfs object lines.»
  • Продолжить по инструкции AD DC (Установка Samba AD DC) — с шага, следующего за provisioning. Кроме того, вики просит сообщать обо всех необработанных исключениях в bugzilla: classicupgrade пока не все ошибки объясняет понятным сообщением.

Ориентир для проверки — пример вывода успешного апгрейда из вики (фрагмент; многоточиями отмечены пропущенные промежуточные строки): Reading smb.conf → Provisioning → Exporting account policy → Exporting groups → Exporting users → Next rid = 1007 → Exporting posix attributes → Reading WINS database → … → Setting up sam.ldb schema → … → Setting up well known security principals → Setting up sam.ldb users and groups → … → Importing WINS database → Importing Account policy → Importing idmap database → Adding groups → Importing groups → Adding users → Importing users → Adding users to groups → Setting password for administrator.

Переезд с Windows AD: что сделать до вывода Windows DC

Полный разбор adprep, трёх уровней (схема, подготовка, функциональный) и обхода для Windows 2016 — в Windows DC рядом с Samba DC; здесь — только шаги, специфичные для переезда. На Windows за всё это отвечает adprep.exe; сам adprep и новые способы его вызова против контроллера Samba не работают.

  • Рекомендация вики для переезда с Windows на Samba: «If you are migrating from Windows to Samba, then we recommend that you use Windows adprep to upgrade your domain schema and preparation level to 2008 R2 before decommissioning your Windows DCs.» То есть схему и preparation level поднимают штатным Windows-инструментом до вывода Windows DC.
  • Samba умеет обновлять схему только начиная с доменов 2008R2: «Samba only supports schema upgrades from 2008R2 domains onwards. If you originally created your domain using a Windows DC older than 2008R2, then samba-tool will not be able to upgrade your domain schema for you.»
  • Если adprep нельзя запустить напрямую, используют обход через промежуточный Windows 2008 R2 DC: шаги (промежуточный DC → FSMO → Windows 2012 DC → adprep обновляет схему и подготовку) и требования к ролям — в Windows DC рядом с Samba DC, см. также Передача и захват FSMO ролей.
  • Домен с функциональным уровнем 2012 и выше долгое время не принимал Samba DC — join падал с WERR_DS_INCOMPATIBLE_VERSION. Поддержка подтянулась: 4.19 заявляет FL 2012/2012_R2, 4.20 — FL 2016, 4.21 — «Samba can now claim Functional Level 2012R2 support» и gMSA «completing support for Functional Level 2012». Оговорки и обход, если уровень понизить нельзя, — в Windows DC рядом с Samba DC; старая вики-страница (правка 13.04.2021) по-прежнему описывает FL 2012 и выше как неподдерживаемый — сверяйтесь с release notes своей версии.
  • Смежное требование при переезде с домена, созданного ещё на Windows 2003 или раньше: у него должен быть доменно-интегрированный DNS, настроенный на поведение 2008; иначе присоединение Samba DC к домену не пройдёт.
  • Полезно проверить домен на соответствие смешанной схеме заранее — см. Windows DC рядом с Samba DC.

Функциональные уровни: что поднимать после миграции

classicupgrade провижинит домен с dom_for_fun_level=dsdb.DS_DOMAIN_FUNCTION_2003 — и домен, и лес получают уровень 2003, поэтому перед вводом в строй уровень нужно осознанно поднять. Поддерживаемые уровни по версиям Samba (2003/2008/2008_R2 — с 4.0, 2012/2012_R2 — с 4.19, 2016 — с 4.20), таблица и полные оговорки — в Windows DC рядом с Samba DC.

  • Подъём выполняется командой samba-tool domain level raise, например # samba-tool domain level raise --domain-level=2008_R2; после подъёма функционального уровня контроллеры Samba AD нужно перезапустить. Лес нельзя поставить выше домена. Последовательность для существующего домена по release notes 4.19 (samba-tool domain schemaupgrade --schema=2019 → samba-tool domain functionalprep --function-level=2016 → samba-tool domain level raise --domain-level=2016 --forest-level=2016) разобрана в Windows DC рядом с Samba DC.
  • Схема: до Samba 4.11 по умолчанию была 2008 R2, с 4.11 — 2012 R2 («Default AD schema changed from 2008_R2 to 2012_R2»). Для доменов, провижиненных до 4.11, схему поднимают samba-tool domain schemaupgrade; вики замечает, что инструмент может выдать ошибку на работающем сервере, хотя фактически сработает, и что команда есть начиная с 4.8, но сначала рекомендуется обновиться до Samba 4.11, так как в ней добавлены важные исправления.
  • Новые домены: release notes 4.19 говорят, что база готовится под FL 2016 «with AD Schema 2019», а release notes 4.21 называют ту же схему «default 2016 schema» — формулировки источников расходятся. Фактическое умолчание samba-tool domain provision — --base-schema=2019 и --function-level=2008_R2 (проверено по исходнику тегов samba-4.19.0/4.20.0/4.21.0 и локально на 4.22.11), то есть база готовится под схему 2019, но функциональный уровень по умолчанию остаётся 2008 R2.
  • Расхождение источников: вики-страница Windows 2012 Server compatibility (правка 2021) заявляет, что Samba «does not currently support any attempts to update the functional level» и что поднимать уровень надо средствами Windows. Нынешняя вики-страница Raising the Functional Levels (правка 2024) описывает подъём через samba-tool domain level raise и одновременно помечает подъём через оснастку Windows «Active Directory Domains and Trusts» как неподдерживаемый (ссылка на bug 10360). Для своей версии сверяйтесь с release notes.
  • Имена опций — тоже источник путаницы: man-страница (docs-xml/manpages/samba-tool.8.xml, версия 4.25.0) в прозе пишет --functional-level, тогда как реально объявленная опция — --function-level (проверено на Samba 4.22.11). Пример вики для functionalprep использует именно samba-tool domain functionalprep --function-level=[2012|2012_R2].

Проверено локально (Samba 4.22.11, Debian 13)

  • samba-tool --version → 4.22.11-Debian-4.22.11+dfsg-0+deb13u1.
  • samba-tool domain classicupgrade --help → есть --dbdir=DIR, --testparm=PATH, --targetdir=DIR, -q/--quiet, -v/--verbose, --dns-backend=NAMESERVER-BACKEND (SAMBA_INTERNAL описан как default), общие опции --option=, --realm=REALM; опций --use-xattrs/--use-ntvfs в этой сборке нет.
  • python3 -c "import samba; print(samba.is_ntvfs_fileserver_built())" → False — именно поэтому опции NTVFS/xattr не показываются (в коде они добавляются условно).
  • samba-tool domain functionalprep --help → опция называется --function-level, значения по умолчанию нет («Default is (Windows) 2016»).
  • samba-tool domain level --help → синтаксис domain level (show|raise <options>), значения --domain-level/--forest-level: 2003 | 2008 | 2008_R2 | 2012 | 2012_R2 | 2016.

Подводные камни

  • Миграция необратима: после первого обращения клиентов к AD DC возврат к NT4-домену невозможен даже откатом; обязательный прогон в изолированной сети.
  • classicupgrade не «дополняет» существующий AD, а создаёт новый домен по старому SID; после него нельзя просто запустить provisioning «поверх».
  • Аккаунт administrator обязан иметь RID 500, иначе ProvisioningError и остановка.
  • Пользователи и группы с RID < 1000 не переносятся (пропускаются как well-known) — RID надо менять заранее.
  • Дубли SID (в том числе между пользователем и группой) и совпадение имён пользователя и группы останавливают апгрейд.
  • «Сломанные» машинные аккаунты тоже останавливают апгрейд: если у аккаунта с флагами ACB_* не ровно один из ACB_NORMAL / ACB_WSTRUST / ACB_SVRTRUST / ACB_DOMTRUST, выводится «Failed to upgrade due to invalid account … Please fix this account before attempting to upgrade again». Часть некорректных комбинаций, наоборот, исправляется автоматически с предупреждениями (например, «Fixing account %s which had both ACB_NORMAL (U) and ACB_WSTRUST (W) set…»).
  • BDC в NT4-домене перестаёт быть контроллером: его аккаунт понижается до машинного, и контроллер нужно потом поднимать через samba-tool domain dcpromo; доверия NT4 не переносятся и создаются заново как AD-доверия.
  • realm и имя AD-домена после миграции изменить нельзя — выбирайте сразу; имя DC (netbios name) должно совпадать с коротким hostname будущего сервера.
  • DNS-бэкенд NONE при апгрейде не PDC/BDC подставляется кодом принудительно, а BIND9_FLATFILE/NONE в вики для этой процедуры вообще не описаны — используйте SAMBA_INTERNAL или BIND9_DLZ (см. Внутренний DNS бэкенд, BIND9 DLZ DNS бэкенд).
  • Опции --use-xattrs/--use-ntvfs существуют только в сборках с NTVFS; --use-xattrs=no без --use-ntvfs — ошибка (и это прямо помечено как «not supported for production use»).
  • Для ldapsam нужен работающий LDAP-сервер и пароль привязки в secrets.tdb; при отсутствии — ошибка ProvisioningError. Плюс лимит выдачи поиска slapd по умолчанию 500 записей может обрезать миграцию.
  • wins.dat читается из --dbdir, хотя в списке переносимых файлов вики его нет: если WINS нужен, перенесите его сами, иначе будет лишь предупреждение.
  • Не все атрибуты из LDAP переносятся (bug #9908), а определения шар из реестра не переносятся вовсе (в коде FIXME).
  • После апгрейда нельзя добавлять в новый smb.conf строки idmap config и vfs objects — предупреждение вики; старые POSIX-идентификаторы уже лежат в AD как RFC2307-атрибуты, а на DC авто-включён acl_xattr (см. Общий ресурс с Windows ACL).
  • Старый /etc/passwd и /etc/group нужно чистить руками (для smbpasswd/tdbsam), а внешний LDAP — выключать; иначе легко получить два источника правды.
  • Повторный запуск classicupgrade требует удалить сгенерированный smb.conf и содержимое private/.
  • Новый домен после classicupgrade имеет функциональный уровень 2003 (и домен, и лес) — перед вводом в строй продумайте подъём уровня; допустимые уровни зависят от версии Samba (2012/2012_R2 — с 4.19, 2016 — с 4.20).
  • Источники расходятся в вопросе подъёма функционального уровня (samba-tool против «только Windows») и в имени опции functionalprep (--functional-level в прозе man-страницы против --function-level в коде и в --help) — проверяйте --help своей версии.
