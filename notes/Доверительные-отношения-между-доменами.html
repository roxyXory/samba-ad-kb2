База знаний Samba AD DC

Доверительные отношения между доменами Samba AD

Суть

Доверие (trust) — это отношение между двумя доменами, при котором пользователь одного домена аутентифицируется в другом. В Samba поддержка доверий реализована для роли AD DC: external-доверия между отдельными доменами и транзитивные forest-доверия (для корневых доменов лесов) работают в обе стороны — inbound и outbound. Управляют довериями подкоманды samba-tool domain trust (появились в 4.3, существенно развиты в 4.9). Правила SID filtering Samba не применяет, а в 4.9 добавлена возможность включать пользователей и группы доверенного домена в группы локального домена, поэтому старые формулировки FAQ («нельзя добавить пользователей и группы доверенного домена в группы») устарели.

Ключевое

Что реально работает

  • «External trusts between individual domains work in both ways (inbound and outbound). The same applies to root domains of a forest trust.» — external-доверия между отдельными доменами и forest-доверия корневых доменов лесов работают в обе стороны (страница Active Directory Trusts вики Samba, последняя правка 22.02.2025).
  • 4.3: транзитная маршрутизация в другой лес (transitive routing into the other forest) «is fully functional for kerberos, but not yet supported for NTLMSSP» — для Kerberos полностью, для NTLMSSP ещё нет.
  • 4.9: «External domain trusts, as well a transitive forest trusts, are supported in both directions (inbound and outbound) for Kerberos and NTLM authentication.» — оба типа доверий работают в обе стороны и для Kerberos, и для NTLM.
  • Ограничение 4.9: «Samba can still only operate in a forest with just one single domain» — Samba по-прежнему работает только в лесу из одного домена (release notes 4.9.0; в более новых release notes уточнений по этому пункту не нашлось).

Подкоманды samba-tool domain trust

Man-страница samba-tool(8) (актуальная версия) перечисляет подкоманды так; в man-странице 4.9 тот же список, но без modify:

domain trust create DOMAIN options [options]
    Create a domain or forest trust.
domain trust modify DOMAIN options [options]
    Modify a domain or forest trust.
domain trust delete DOMAIN options [options]
    Delete a domain trust.
domain trust list options [options]
    List domain trusts.
domain trust namespaces [ DOMAIN ] options [options]
    Manage forest trust namespaces.
domain trust show DOMAIN options [options]
    Show trusted domain details.
domain trust validate DOMAIN options [options]
    Validate a domain trust.

Что появилось когда (по исходникам и release notes):

  • 4.3.0: «samba-tool got "domain trust" subcommands to manage trusts: create / delete / list / namespaces / show / validate» — подкоманды create, delete, list, namespaces, show, validate. Подкоманды modify в 4.3.0 и 4.9.0 нет (проверено по исходникам обеих версий); она упоминается как «newly added» в security-релизах 4.15.13 / 4.16.8 / 4.17.4 по CVE-2022-37966 (ноябрь 2022).
  • Все trust-опции 4.3 и текущего master совпадают, кроме добавленных позже к modify — --use-aes-keys и --raw-kerb-enctypes.
  • Проверено на месте (samba-tool domain trust <subcommand> --help, Samba 4.22.11-Debian): в 4.22 доступны все семь подкоманд, включая modify.

create: опции и поведение

Справка samba-tool domain trust create --help (4.22.11; формулировки идентичны исходнику master):

--type=TYPE           The type of the trust: 'external' or 'forest'.
--direction=DIRECTION The trust direction: 'incoming', 'outgoing' or 'both'.
--create-location=LOCATION
                      Where to create the trusted domain object: 'local' or 'both'.
--cross-organisation  The related domains does not belong to the same organisation.
--quarantined=yes|no  Special SID filtering rules are applied to the trust.
                      With --type=external the default is yes. With --type=forest the default is no.
--not-transitive      The forest trust is not transitive.
--treat-as-external   The treat the forest trust as external.
--no-aes-keys         The trust does not use AES kerberos keys.
--skip-validation     Skip validation of the trust.

Детали из исходника (python/samba/netcmd/domain/trust.py, master):

  • Значения по умолчанию: --type=external, --direction=both, --create-location=both.
  • --not-transitive и --treat-as-external допустимы только с --type=forest; иначе команда завершается ошибкой «--not-transitive requires --type=forest» / «--treat-as-external requires --type=forest».
  • --quarantined не задан: при --type=external карантин включается (в атрибуты TDO пишется LSA_TRUST_ATTRIBUTE_QUARANTINED_DOMAIN), при --type=forest — нет.
  • --create-location=both (по умолчанию): объекты доверия (TDO) создаются на обеих сторонах; пароль доверия не запрашивается — каждая сторона получает случайный секрет 240 байт; нужны учётные данные администратора второго домена (группа Credentials Options: -U, --password, -W).
  • --create-location=local: создаётся только локальный TDO; интерактивно запрашиваются пароли «New Incoming Trust Password» / «New Outgoing Trust Password» (с подтверждением, при несовпадении — «Sorry, passwords do not match.»), и тот же пароль нужно задать на другой стороне.
  • Локальный DC берётся через ncalrpc (нужна роль AD DC); параметры --local-dc-* позволяют обратиться к удалённому/чужому DC, включая Windows (CVE-2022-37966).
  • Имена второго домена берутся с его DC (LocalDomain Netbios[...] DNS[...] SID[...], RemoteDomain Netbios[...] DNS[...] SID[...]), удалённый DC ищется через Net.finddc() (NBT_SERVER_LDAP|DS|WRITABLE|PDC), при неудаче — «Failed to find a writeable DC for domain '%s'».
  • Если доверие уже существует: «TrustedDomain %s already exist'». При сбое создания в режиме both выполняется откат: «Deleting remote TDO.» / «Deleting local TDO.».
  • Если validation не отключена (--skip-validation), команда сама проверяет доверие: «Validating outgoing trust...», «Validating incoming trust...», затем строки вида OK: LocalValidation: DC[...] CONNECTION[...] TRUST[...] (при VERIFY_STATUS_RETURNED добавляется VERIFY_STATUS_RETURNED) и в конце Success.

modify / delete / list / show / validate / namespaces

  • modify: --use-aes-keys, --no-aes-keys, --raw-kerb-enctypes=KERB_ENCTYPES (взаимоисключающие) — меняет типы шифрования Kerberos у существующего доверия, печатает Old kerb_EncTypes: / New kerb_EncTypes: (или No kerb_EncTypes update needed).
  • delete: --delete-location=local|both (по умолчанию both; в режиме both нужны учётные данные удалённой стороны).
  • list: собственных опций нет; печатает строки вида Type[...] Transitive[...] Direction[...] Name[...].
  • show: собственных опций нет; печатает NetbiosName, DnsName, SID, Type, Direction, Attributes, PosixOffset, kerb_EncTypes, а для forest-доверия — ещё и пространства имён леса.
  • validate: --validate-location=local|both (по умолчанию both); выполняет netlogon-вызовы NETLOGON_CONTROL_TC_VERIFY (печатает OK: LocalValidation: DC[...] CONNECTION[...] TRUST[...]) и NETLOGON_CONTROL_REDISCOVER (OK: LocalRediscover: DC[...] CONNECTION[...]), при both — то же для удалённой стороны (RemoteValidation, RemoteRediscover).
  • namespaces: --refresh=check|store, --enable-all, --enable-tln/--disable-tln (DNSDOMAIN), --add-tln-ex/--delete-tln-ex, --enable-nb/--disable-nb, --enable-sid/--disable-sid, --add-upn-suffix/--delete-upn-suffix, --add-spn-suffix/--delete-spn-suffix. Часть операций требует аргумент DOMAIN (иначе ошибки вида «--refresh=store not allowed without DOMAIN»). Набор опций совпадает в 4.3 и в текущем master.

Последовательность настройки обеих сторон

  1. Уникальные NetBIOS-имена. Имя NetBIOS по умолчанию (первые 15 символов левой части DNS-имени, для ad.example.com — AD) выбирать не стоит: «Selecting such a NetBIOS domain name would be a bad idea, as it would be quite likely to conflict with any other domains that had the same NetBIOS name. This would pose an issue if you ever had to set up a trust relationship between these two domains.» (Active Directory Naming FAQ). Команды надёжности оперируют NetBIOS-именами обеих сторон (Netbios[...] в выводе create, netbios_name в TDO).
  2. Разрешение имён второго домена. Перед созданием доверия локальный DC ищет DC второго домена по имени домена через Net.finddc() (setup_remote_server в trust.py) — значит имена второго домена должны разрешаться. Внутренний DNS-сервер Samba условные форвардеры не умеет: «Conditional forwarders are not implemented yet. The same error message as above is returned» и «The DNS forwarder can only be changed in the smb.conf, not via the MMC Snap-In» (вики, DNS Administration; правка страницы 25.04.2023). Доступный во внутреннем DNS механизм — только глобальный список серверов dns forwarder в smb.conf (smb.conf(5): «This option specifies the list of DNS servers that DNS requests will be forwarded to if they can not be handled by Samba itself. The DNS forwarder is only used if the internal DNS server in Samba is used.», пример dns forwarder = 192.168.0.1 192.168.0.2). Альтернативный вариант — бэкенд BIND9_DLZ: DNS обслуживает BIND, файлы вида named.conf формируются Samba (см. BIND9 DLZ DNS бэкенд), и задачу разрешения имён второго домена приходится решать средствами DNS самостоятельно. Дополнительно нужны открытые порты AD DC между доменами (Порты AD DC).
  3. Учётные данные администратора второго домена — для режима --create-location=both (по умолчанию); свой DC при этом не требует учётных данных (ncalrpc, роль AD DC).
  4. Пароль доверия. both — пароль не вводится, стороны получают случайные 240-байтовые секреты; local — пароль вводится интерактивно и должен быть одинаковым с другой стороны, где доверие заводят отдельно.
  5. Проверка. create сам выполняет validation (см. выше), отдельно — samba-tool domain trust validate DOMAIN (TC_VERIFY + REDISCOVER, по умолчанию для обеих сторон), плюс инвентаризация через list/show.
  6. Управление. modify (типы шифрования), delete (--delete-location), namespaces (пространства имён леса).

Ограничения и безопасность

  • Актуальные ограничения со страницы вики (правка 22.02.2025): «Both sides of the trust need to fully trust each other!»; «No SID filtering rules are applied at all!»; «This means DCs of domain A can grant domain admin rights in domain B.»
  • 4.9: дополнительно «Selective (CROSS_ORGANIZATION) authentication is not supported. It's possible to create such a trust, but the KDC and winbindd ignore them.» — несмотря на наличие флага --cross-organisation, в Samba он не поддержан.
  • AES-ключи доверий. CVE-2022-37966 (релизы 4.15.13, 4.16.8, 4.17.4): «the fallback for an unspecified msDS-SupportedEncryptionTypes ... for trustedDomain objects are changed in an incompatible way! The fallback is now aes256-cts-hmac-sha1-96 instead of rc4-hmac! It is therefor recommended to explicitly set the value on both sides of the trust before or immediately after the update». Рекомендации оттуда же: явно включать AES256 на обеих сторонах через GUI или samba-tool domain trust modify --use-aes-keys; для legacy-доверий к Windows 2000/2003 — принудительно RC4 через samba-tool domain trust modify --no-aes-keys; к удалённым (в том числе Windows) DC можно обращаться опциями --local-dc-ipaddress= и другими --local-dc-*; уже закэшированные cross-realm-билеты RC4 после перехода на AES могут перестать работать, снизить проблемы помогает сокращение времени жизни билета до 1 часа.
  • Как записать это в конфигурации — важная тонкость. В smb.conf опция пишется через пробел: kdc:user ticket lifetime = 1 (аналогично kdc:service ticket lifetime и kdc:renewal lifetime) — именно такое имя параметрической опции запрашивает KDC: lpcfg_parm_long(lp_ctx, NULL, "kdc", "user ticket lifetime", 10) в lib/param/util.c. Форма с подчёркиванием kdc:user_ticket_lifetime — это ключ GPO-хранилища gpo.tdb, куда значение кладёт samba-gpupdate из Kerberos-политики GPO (python/samba/gp/gp_sec_ext.py, apply_map). При старте KDC сначала читает gpo.tdb и только потом берёт параметрическую опцию из smb.conf (lpcfg_default_kdc_policy). Проверено по исходникам master и 4.22.11; сама рекомендация 1 часа — из advisory CVE-2022-37966.
  • Ограничение объёма доверия на стороне winbind: winbind:ignore domains = DOMAIN1, DOMAIN2 — «Allows one to enter a list of trusted domains winbind should ignore (untrust). This can avoid the overhead of resources from attempting to login to DCs that should not be communicated with.» (smb.conf(5)).
  • Мониторинг: samba-tool domain trust list и show дают тип/направление/транзитивность доверия и выставленные kerb_EncTypes; validate проверяет работоспособность канала netlogon в обе стороны — это можно использовать как регулярную проверку.
  • Доверие — полное взаимное: раз администраторы второго домена получают те же права, доверие стоит заводить только между доменами одного владельца/уровня доверия.

Подводные камни

  • Вики-FAQ (страница FAQ, правка 20.10.2024) до сих пор утверждает: «The trust feature is experimental and has several limitations, such as: SID filtering rules are not applied / You cannot add users and groups of a trusted domain into domain groups.» Пункт про группы неверен начиная с 4.9: «It's now possible to add users/groups of a trusted domain into domain groups. The group memberships are expanded on trust boundaries.», «foreignSecurityPrincipal objects (FPO) are now automatically created when members (as SID) of a trusted domain/forest are added to a group», «The 'samba-tool group *members' commands allow members to be specified as foreign SIDs.» Пункт про SID filtering на странице Active Directory Trusts подтверждается и в 2025 году.
  • Справка --no-aes-keys в 4.3 и 4.9 была сформулирована наоборот: «The trust uses aes kerberos keys.» (хотя флаг означает отказ от AES); в текущих версиях текст исправлен на «The trust does not use AES kerberos keys.». Само поведение тоже менялось: в 4.9 при --no-aes-keys типы шифрования вообще не записывались (enc_types = None), а в master явно записывается RC4 (комментарий в коде: «CVE-2022-37966: Trust objects are no longer assumed to support RC4, so we must indicate support explicitly.»).
  • Изменение умолчания AES (CVE-2022-37966) ломает доверия с неявно заданными типами шифрования — значения надо явно выставить на обеих сторонах до/сразу после обновления.
  • --not-transitive и --treat-as-external без --type=forest — ошибка; --cross-organisation создаёт доверие, но selective authentication всё равно не работает.
  • Доверие «в одну сторону» не заработает: обе стороны должны полностью доверять друг другу (вики), поэтому недостаточно создать TDO только на своей стороне.
  • Внутренний DNS Samba не поддерживает условные форвардеры (страница DNS Administration) — под trust придётся планировать DNS-пересылку заранее (глобальный dns forwarder или внешний/BIND9_DLZ).
  • Подкоманда modify есть не во всех версиях, где есть остальные trust-команды: в 4.3/4.9 её нет, в справочниках этих версий ориентироваться на неё нельзя.
