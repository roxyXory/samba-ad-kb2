Wireshark Keytab (расшифровка трафика в Wireshark)

Суть

Страница «Wireshark Decryption» (ранее «Wireshark Keytab») объясняет, как расшифровывать зашифрованный SMB3- и Kerberos/DCE-RPC-трафик в Wireshark. Есть три пути: передать SessionId → SessionKey, начиная с Wireshark 2.5.0; передать напрямую серверный и клиентский ключи расшифровки (Wireshark 3.3.0+); либо использовать keytab — файл с ключами Kerberos, который Wireshark применяет для расшифровки Kerberos-блобов и зашифрованного DCE/RPC. Там же описано, как извлечь ключи из клиента ядра Linux и из Samba (клиента и сервера).

Ключевое

Расшифровка по session key (SMB3+)

  • Начиная с Wireshark 2.5.0 (февраль 2018) список соответствий SessionId → SessionKey можно передать через таблицу в настройках SMB2 или через командную строку.
  • «Session key» здесь — криптографические ключи, используемые при аутентификации и подписи сообщений; это не то же самое, что CIFS SessionKey.
  • Из MS-SMB2: Session.SessionKey: The first 16 bytes of the cryptographic key for this authenticated context. If the cryptographic key is less than 16 bytes, it is right-padded with zero bytes.

Ключи сервера и клиента (SMB3+)

  • С Wireshark 3.3.0 (сентябрь 2020) можно передавать список SessionId => ServerKey, ClientKey через таблицу в настройках SMB2 или командную строку; синтаксис при этом изменился.
  • Если непонятно, какой ключ серверный, а какой клиентский — не важно: Wireshark попробует оба.
  • При передаче ключей напрямую пакеты установки сессии (NegProt и Session Setup) в дампе не обязательны. Синтаксис CLI:
tshark -Y smb2 '-ouat:smb2_seskey_list:<sessionid>,<session key>,<server to client key>,<client to server key>' -r trace.pcap
  • Отсутствующий ключ можно пропустить пустой строкой "":
tshark -Y smb2 '-ouat:smb2_seskey_list:0502004c955a1080,a3c0338caf84f4a254445a9724f1c462,"",""' -r trace.pcap

Получение ключей: клиент ядра Linux

  • Для свежих ядер (функция добавлена в сентябре 2019, ядро 5.4) SMB3-ключи выгружаются утилитой smbinfo (запуск от root или с CAP_SYS_ADMIN, cifs-utils версии 6.10):
smbinfo keys <path-to-a-file-on-an-smb3-mount>
  • Для старых ядер клиент Linux (cifs.ko) можно собрать с опцией CONFIG_CIFS_DEBUG_DUMP_KEYS — тогда ключи видны в выводе dmesg.
  • Опция включается в .config или в make menuconfig: File systems → Network File Systems → SMB3 and CIFS support (advanced network filesystem) → Enable CIFS debugging routines → Dump encryption keys for offline decryption (Unsafe).
  • После включения смонтируйте шару с опциями vers=3 (или vers=3.11) и seal для обязательного шифрования. При достижении стадии Tree Connect в консоли ядра (dmesg) появится для каждой сессии:
CIFS VFS: generate_smb3signingkey: dumping generated AES session keys
CIFS VFS: Session Id    bc 1a fc 0d 00 00 00 00
CIFS VFS: Session Key   34 57 e1 90 4b 94 3a 0d 09 be 22 b9 b9 cf c7 4c
CIFS VFS: Signing Key   28 bf a3 71 39 e5 05 71 c6 15 58 f3 cf 42 3f 0e
CIFS VFS: ServerIn Key  79 2a 9a 40 1e cf 16 52 41 a5 ec bd 1c e5 84 17
CIFS VFS: ServerOut Key c0 73 c8 1d 36 f5 74 3e ef 6e c1 9d 5c e5 cb 71

Получение ключей: Samba-клиент и сервер

  • Начиная с Samba 4.11, и клиентский, и серверный код умеют выгружать сгенерированные ключи в лог при debug encryption = yes в smb.conf или через командную строку. Через smb.conf опция управляет сразу и серверным, и клиентским кодом.
  • Пример:
$ smbclient //localhost/scratch --option='debugencryption=yes' -e -mSMB3 -U aaptel%aaptel
debug encryption: dumping generated session keys

Установка ключа в Wireshark

  • Через GUI: Edit → Preferences → SMB2 → Edit.
  • Ядро печатает Session Id как он есть «на проводе» (little endian); расшифровка Wireshark тоже ожидает Session Id «как на проводе», поэтому значения можно копировать из dmesg прямо в Wireshark (несмотря на то, что в разобранных пакетах поле Session ID показывается декодированным).
  • Через командную строку (работает и в wireshark, и в tshark):
# Wireshark version pre-3.3.0
tshark -ouat:smb2_seskey_list:3d00009400480000,28f2847263c83dc00621f742dd3f2e7b -r smb3-aes-128-ccm.pcap

# Wireshark version 3.3.0 and above
tshark '-ouat:smb2_seskey_list:3d00009400480000,28f2847263c83dc00621f742dd3f2e7b,"",""' -r smb3-aes-128-ccm.pcap

Использование keytab

  • Разовая подготовка:
    1. Откройте Wireshark.
    2. Перейдите: Preferences → Protocols → KRB5.
    3. Включите: Try to decrypt encrypted Kerberos blobs.
  • Простейший способ на unix-подобной системе:
wireshark -K <PATH TO KEYTAB> <PCAP FILE>
  • Альтернатива — указать keytab в Preferences → Protocols → KRB5 → keytab path.
  • Как извлечь keytab — на вики есть отдельная страница «How to extract a keytab from a windows domain with Samba».

Расшифровка AES DCE/RPC и лучший разбор DRSUAPI

  • Для расшифрованного AES DCE/RPC нужен Wireshark 3.3.0 или новее; если такой версии нет — соберите из исходников или из git.
  • Лучший разбор DRSUAPI в Wireshark даёт ветка metze (на базе wireshark master). Для ветки ws-metze/20221103 сборка на Ubuntu 20.04:
CC="ccache gcc" cmake ../ -G Ninja -DUSE_qt6=OFF -Wno-error=dev -Wno-dev -DENABLE_WERROR=No
ninja

Подводные камни

  • Версии Wireshark для шифрования SMB3: AES-128 CCM для SMB3.0 — с 2.6.5 (декабрь 2018); AES-128 CCM для SMB3.1.1 — с 3.0.0 (февраль 2019); AES-128 GCM для SMB3.1.1 — с 3.1.0 (июль 2019); поддержка мультикапч/многоканальной расшифровки и передача ключей напрямую — с 3.3.0 (сентябрь 2020).
  • До Wireshark 3.3.0 из-за особенностей генерации ключей в дампе должны присутствовать начальные пакеты соединения (NegProt и SessSetup), иначе расшифровка не сработает.
  • Wireshark должен быть собран с libgcrypt >= 1.6.0 (проверяется в выводе wireshark -v).
  • AES-256 пока не поддерживается.
  • Если не расшифровываются образцы дампов с вики Wireshark — какое-то из перечисленных требований не выполнено.
  • CONFIG_CIFS_DEBUG_DUMP_KEYS — отладочная опция, её нельзя включать на производственной системе.
  • Wireshark для 64-битной Windows (GUI и командная строка) плохо работает с флагом -K — используйте 32-битную версию для Windows.
