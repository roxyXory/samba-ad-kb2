Сертификатный вход: PKINIT, KeyTrust и строгая привязка сертификатов

Суть

Вход по сертификату в Active Directory — это Kerberos-предварительная аутентификация PKINIT: клиент предъявляет KDC сертификат вместо пароля (смарт-карта, PIV-токен, Windows Hello for Business). Samba использует встроенный KDC Heimdal; PKINIT включается не в smb.conf, а в отдельном krb5.conf из каталога provision, плюс в smb.conf задаются TLS-файлы и CRL контроллера домена. Samba 4.24.0 (18 марта 2026) добавила вход KeyTrust для Windows Hello for Business (самоподписанные ключи, атрибут msDS-KeyCredentialLink), валидацию этого атрибута по MS-ADTS, команды keytrust и generate-csr — и включила по умолчанию строгую привязку сертификатов (strong certificate binding enforcement = full, аналог Microsoft KB5014754): проходят только «сильные» сопоставления (SID-расширение сертификата 1.3.6.1.4.1.311.25.2 или altSecurityIdentities), поэтому без миграции старые сертификаты перестают пускать пользователей в домен.

Ключевое

Что добавили в Samba (4.24.0 и 4.19.0)

Разделы release notes Samba 4.24.0 (дословно):

  • Kerberos PKINIT KeyTrust logon support: «Samba servers configured with the embedded heimdal KDC and running as an ADDC, now support "Windows Hello for Business Key-Trust logons". This allows the PKINIT authentication mechanism to be used with self-signed keys.» Публичный ключ хранится в атрибуте msDS-KeyCredentialLink учётной записи пользователя или компьютера.
  • msDS-KeyCredentialLink validation: «Updates to the msDS-KeyCredentialLink attribute are validated against the rules specified by MS-ADTS 3.1.1.5.3.1.1.6.»
  • Kerberos PKINIT strong/flexible key mappings: «The default enforcement mode ("full") allows only strong certificate mappings»; режимы compatibility и none описаны ниже.
  • Kerberos PKINIT SID extension: «PKINIT authentication now supports certificates containing an Object SID extension (extension 1.3.6.1.4.1.311.25.2), this is considered to be a STRONG mapping for KB5014754.»
  • Новые подкоманды samba-tool user|computer generate-csr и user|computer keytrust.
  • Таблица изменений smb.conf: strong certificate binding enforcement — New, default full; certificate backdating compensation — New, default 0.

Samba 4.19.0 добавила отзыв сертификатов PKINIT (см. ниже) и «Protocol level testsuite for (Smart Card Logon) PKINIT» — независимый python-тест KDC для PKINIT вместо shell-скриптов вокруг MIT/Heimdal.

Отдельно в 4.24.0 расширен аудит: классы отладки dsdb_password_audit и dsdb_password_json_audit теперь логируют изменения altSecurityIdentities, dNSHostName, msDS-AdditionalDnsHostName, msDS-KeyCredentialLink и servicePrincipalName; в JSON-логах для них поле action имеет значение "Auth info change".

Настройка PKINIT в KDC: два файла

1. smb.conf — TLS-сертификат самого DC (блок из вики-страницы Smart Card Login, подставьте свои пути):

tls enabled = yes
tls certfile = /var/lib/samba/private/tls/dc-cert.pem
tls keyfile = /var/lib/samba/private/tls/secure/dc-privkey.pem
tls cafile = /var/lib/samba/private/tls/cacert.pem
tls crlfile = /var/lib/samba/private/tls/greatlakes.crl
tls dhparams file = /var/lib/samba/private/tls/dcdhparams.pem

Значения по умолчанию из актуальной smb.conf(5): tls enabled = yes, tls cafile = tls/ca.pem, tls certfile = tls/cert.pem, tls crlfile по умолчанию пуст, пути без ведущего / считаются относительно private dir. Параметр параметров Диффи-Хеллмана в man-странице называется tls dh params file, в HOWTO — tls dhparams file.

2. krb5.conf — собственный krb5.conf Samba в каталоге provision (/var/lib/samba/private/krb5.conf). Блок из вики-страницы (в кавычках — предупреждение вики: «Note: the dash in "enable-pkinit" is not a typo.»):

[libdefaults]
        default_realm = GREATLAKES.EXAMPLE.COM
        dns_lookup_realm = false
        dns_lookup_kdc = true
        pkinit_anchors = FILE:/var/lib/samba/private/tls/cacert.pem

[appdefaults]
        pkinit_anchors = FILE:/var/lib/samba/private/tls/cacert.pem

[realms]
        GREATLAKES.EXAMPLE.COM = {
                pkinit_require_eku = true
        }

[kdc]
        enable-pkinit = yes
        pkinit_identity = FILE:/var/lib/samba/private/tls/dc-cert.pem,/var/lib/samba/private/tls/secure/dc-privkey.pem
        pkinit_anchors = FILE:/var/lib/samba/private/tls/cacert.pem
        pkinit_principal_in_certificate = yes
        pkinit_win2k = no
        pkinit_win2k_require_binding = yes

Затем вики предлагает заменить системный /etc/krb5.conf копией этого файла — не символической ссылкой: с Samba 4.7 каталог /var/lib/samba/private/ доступен только root, и по симлинку другие пользователи файл не прочитают (например, ломаются динамические DNS-обновления при бэкенде BIND_DLZ).

Смысл опций по man-странице Heimdal krb5.conf(5) (актуальная ветка master):

Опция (секция) Что делает
enable-pkinit ([kdc]) «Enable PKINIT (disabled by default).»
pkinit_identity ([kdc]) HX509-store с учётными данными PKINIT самого KDC (закрытый ключ + end-entity сертификат). Типы store: FILE, PEM-FILE, DER-FILE, PKCS12, PKCS11 (на macOS ещё KEYCHAIN); несколько store перечисляются через запятую.
pkinit_anchors ([kdc]) Один или несколько store доверенных якорей для клиентских сертификатов PKINIT; поддерживается тип DIR (хеш-каталог в стиле OpenSSL).
pkinit_pool ([kdc]) Промежуточные CA для end-entity сертификата KDC.
pkinit_revoke ([kdc]) Store'ы CRL для издателей клиентских сертификатов PKINIT: «Only the first valid CRL for a particular issuer will be checked. If no CRLs are configured, then CRLs will not be checked. This is because the KDC will not dereference CRL distribution points nor request OCSP responses.»
pkinit_principal_in_certificate ([kdc]) Если true, KDC сопоставляет имена принципалов из AS-REQ со значениями subjectAlternativeName клиентских сертификатов; «Defaults to true.»
pkinit_require_eku ([realms]) Если true, в PKINIT-сертификатах KDC обязан присутствовать EKU OID KDC PKINIT (1.3.6.5.2.3.5); «Defaults to true.»

Сертификат контроллера домена

Требования из вики-страницы (OpenSSL-конфигурация HOWTO): extendedKeyUsage = clientAuth,serverAuth,pkInitKDC, keyUsage = nonRepudiation, digitalSignature, keyEncipherment, crlDistributionPoints=URI:$CRLDISTPT, а в subjectAltName — DNS-имя сервера и otherName=msADGUID;FORMAT:HEX,OCTETSTRING:$set_dc_guid, где msADGUID=1.3.6.1.4.1.311.25.1, а значение — objectGUID контроллера в hex-виде без дефисов (скрипт вики переставляет байты GUID, в шаблоне openssl.cnf — «omitting spaces in the domain controller GUID hex entry», пример: set_dc_guid = 32bfa4aa2a1b43478ae3669f6109f08a). Проверяют, что в SAN появилась запись типа «DS Object Guid» со значением 04 10 [Domain Controller GUID], где 04 — тег octet string, а 10 — длина 16 байт. GUID вики предлагает доставать через ADSI Edit или скриптом на базе ldbsearch по OU=Domain Controllers на самом DC.

Требования Microsoft (страница Windows Hello for Business on-premises key trust) сформулированы так: в сертификате DC расширение CRL distribution point должно указывать на действительный CRL либо AIA — на OCSP-респондер; key usage — Digital Signature и Key Encipherment; extended key usage — Client Authentication (1.3.6.1.5.5.7.3.2), Server Authentication (1.3.6.1.5.5.7.3.1) и KDC Authentication (1.3.6.1.5.2.3.5); в SAN должно быть DNS-имя; корень сертификата должен быть в хранилище NTAuth (Certutil -viewstore -enterprise NTAuth), иначе аутентификация пользователя не пройдёт.

На Windows-клиенте дополнительно нужно: импортировать корневой CA в Trusted Root через GPO, обновить gpupdate и добавить корневой сертификат в Enterprise NTAuth store (вики ссылается на метод 2 из KB295663 и приводит команду):

certutil -dspublish -f .\cacert.cer NTAuthCA

Приватный ключ DC (в т. ч. расшифрованный) должен читать только root.

Сертификат пользователя и generate-csr

Пользовательский сертификат в HOWTO: extendedKeyUsage = clientAuth,msSmartcardLogin, а SAN содержит UPN как OtherName с OID msUPN:

openssl req -new -addext 'subjectAltName = otherName:msUPN;UTF8:tina@greatlakes.example.com,email:copy' -newkey rsa:2048 -keyout private/tinaadmin-key.pem -out tinaadmin-req.pem -config openssl.cnf

По вики именно UPN позволяет логике Kerberos на Samba сопоставить сертификат с учётной записью. На smart card сертификат с ключом переносится через PKCS#12 (openssl pkcs12 -in tinaadmin-cert.pem -inkey private/tinaadmin-key.pem -export -out tinaadmin.p12).

Начиная с 4.24 CSR можно сгенерировать самой Samba — команда добавляет в запрос расширение с SID объекта:

samba-tool user generate-csr username
	subject_name
	private_key_filename
	output_filename [options]

samba-tool computer generate-csr computername
	subject_name
	private_key_filename
	output_filename [options]

--private-key-encoding   Specify which encoding the private key uses. Default is 'auto'.
--private-key-pass       Provide a password to decrypt the private key.

Man-страница называет результат «PEM‐encoded Certificate Signing Request»; release notes уточняют, что CSR содержит Object SID extension (1.3.6.1.4.1.311.25.2). По коду python/samba/generate_csr.py (ветка master) в CSR включаются: SAN с OtherName msUPN (ID_PKINIT_MS_SAN = x509.ObjectIdentifier("1.3.6.1.4.1.311.20.2.3")), критичный BasicConstraints(ca=False), критичный Subject Key Identifier, некритичный EKU clientAuth, keyUsage с одним digital_signature=True и некритичное расширение SID (szOID_NTDS_CA_SECURITY_EXT = x509.ObjectIdentifier("1.3.6.1.4.1.311.25.2"), структура описана в [MS-WCCE] 2.2.2.7.7.4). Поддерживаются только RSA-ключи («So far only RSA keys are supported»).

KeyTrust: samba-tool ... keytrust и msDS-KeyCredentialLink

Команды (4.24.0, из man-страницы samba-tool(8); для компьютеров — то же самое с computer):

samba-tool user keytrust add username public-key-or-certificate [options]
samba-tool user keytrust view username [options]
samba-tool user keytrust delete username [options]
  • add: «Add a key-credential-link, which is a linked attribute that holds a public key in a binary field.» Второй аргумент — файл с 2048-битным RSA-ключом (или сертификатом с таким ключом) в PEM или DER; формат определяется автоматически, переопределяется --encoding=pem|der|auto; «Other types of public key are not supported, though the --force option can be used to add a non-2048 bit key.» --link-target=DN — на какой DN ссылаться (по умолчанию DN самого пользователя/компьютера).
  • view: показывает ссылки, их fingerprint и целевой DN (для последующего delete); -v добавляет подробности.
  • delete: выбор ссылки через --all, --link-target=DN или --fingerprint=HH:HH:..; если задано несколько — удаляются все совпавшие; --dry-run/-n ничего не удаляет, только печатает план. Fingerprint — «the SHA256 of the DER-encoded key material, expressed as hex-pairs separated by colons».

Реализация (python/samba/key_credential_link.py, master): создаётся KEYCREDENTIALLINK_BLOB версии 2 (bytes.fromhex("00 02 00 00") # Always version 2) с записями KeyID (SHA-256 материала ключа), KeyMaterial (публичный ключ в DER, SubjectPublicKeyInfo), KeyUsage — всегда KEY_USAGE_NGC — и KeyCreationTime (nttime); запись KeySource в коде закомментирована. Fingerprint считается как SHA-256 от DER-материала ключа и печатается парами hex-байт, разделёнными двоеточиями, в верхнем регистре.

Валидация атрибута — по MS-ADTS 3.1.1.5.3.1.1.6 (на неё прямо ссылаются release notes). Спецификация требует от добавляемого значения: корректный KEYCREDENTIALLINK_BLOB; The KeyUsage entry is KEY_USAGE_NGC.; The KeySource entry is KEY_SOURCE_AD.; The CustomKeyInformation entry is not present.; The KeyApproximateLastLogonTimeStamp entry is not present.; There is no existing value.; The requestor MUST be SELF. Плюс для записи нужно право DS-Validated-Write-Computer. Структура: Version (4 байта, MUST be set to KEY_CREDENTIAL_LINK_VERSION_2) и массив KEYCREDENTIALLINK_ENTRY, который MUST be sorted by their Identifier fields in increasing order (MS-ADTS 2.2.20.2). Заметим: правила MS-ADTS 3.1.1.5.3.1.1.6 сформулированы для объекта класса computer, тогда как Samba 4.24 даёт команду keytrust и для пользователей; как при работе через samba-tool выполняются условия «requestor MUST be SELF» и право DS-Validated-Write-Computer, в release notes и man-странице не описано.

Строгая привязка сертификатов: strong certificate binding enforcement

Новый глобальный параметр smb.conf (Samba 4.24.0), аналог KB5014754. Значения (дословно из smb.conf(5)):

  • none — «No validation of the certificate mappings is performed».
  • compatibility — «Weak certificate mappings are permitted. In compatibility mode for WEAK mappings the date the certificate was issued must be after the date that the user was created. Unless certificate backdating compensation has a value. In that case the certificate may have been issued no more than that number of minutes before the user was created.»
  • full — «Only strong certificate mappings are permitted. This is the default.»

Сопутствующий параметр certificate backdating compensation — число минут, на которое сертификат может быть выпущен раньше создания учётной записи, применяется только в режиме compatibility; по умолчанию 0.

Типы сопоставлений (по smb.conf(5) и KB5014754):

Сопоставление Пример записи Тип
X509 Issuer and subject (X509IssuerSubject) X509:<I>IssuerName<S>SubjectName WEAK
X509 Subject only (X509SubjectOnly) X509:<S>SubjectName WEAK
X509 RFC822 (адрес e-mail) X509:<RFC822>test@example.com WEAK
X509 Issuer and serial number (X509IssuerSerialNumber) X509:<I>IssuerName<SR>123456789 STRONG (KB: recommended)
X509 Subject Key Identifier (X509SKI) в smb.conf(5) — <SKI>01234xxxxx, в KB — X509:<SKI>123456789abcdef STRONG
X509 public key SHA1 (X509SHA1PublicKey) X509:<SHA1-PUKEY>1234567890abcdef STRONG
SID-расширение сертификата (OID 1.3.6.1.4.1.311.25.2) — STRONG

Сопоставления задаются в атрибуте altSecurityIdentities учётной записи; KB5014754 подчёркивает, что поля Issuer/Subject/Serial в сертификате печатаются «в прямом порядке», а в атрибут их нужно вписывать в обратном. Рекомендованная конфигурация KDC из release notes 4.24.0:

strong certificate binding enforcement                            full
kdc always include pac                                            yes
kdc require canonicalization                                      yes

(В прозе release notes встречается имя kdc always generate pac, но в таблице параметров и в smb.conf(5) параметр называется kdc always include pac.)

Что это значит на стороне Windows (KB5014754): значения HKEY_LOCAL_MACHINE\SYSTEM\CurrentControlSet\Services\Kdc — StrongCertificateBindingEnforcement 1 (проверка сильного сопоставления; иначе SID-расширение; иначе аутентификация разрешается, если учётная запись старше сертификата), 2 (то же, но без SID-расширения вход запрещён), 0 (проверка отключена, «Not recommended…»). С Windows-обновлением от 11 февраля 2025 DC переходят в Full Enforcement, если ключ не настроен; обновление от 9 сентября 2025 делает значение реестра неподдерживаемым. Enterprise CA добавляют SID-расширение с OID 1.3.6.1.4.1.311.25.2 во все сертификаты, выпущенные по online-шаблонам, с обновления от 10 мая 2022; отключить можно битом 0x00080000 в msPKI-Enrollment-Flag шаблона.

Отзыв сертификатов (Samba 4.19.0)

Release notes 4.19.0: «Samba will now correctly honour the revocation of 'smart card' certificates used for PKINIT Kerberos authentication.» Дополнительная опция krb5.conf:

 [kdc]
	pkinit_revoke = FILE:/path/to/crl.pem

Список CRL перечитывается при каждом изменении файла — достаточно заменить файл, ничего не перезапуская. В том же релизе: TLS-сертификаты LDAP-сервера Samba AD можно перезагружать без рестарта командой smbcontrol ldap_server reload-certs.

Диагностика

  • На Windows при входе по смарт-карте возможна ошибка «An untrusted certification authority was detected while processing the domain controller certificate used for authentication…»; в HOWTO она возникла при первом входе и ушла после перезагрузки сервера и клиента (репликация Samba ↔ Windows занимает время).
  • В KB5014754 описано событие KDC с текстом «The Key Distribution Center (KDC) encountered a user certificate that was valid but contained a different SID than the user to which it mapped…» — сертификат содержит SID другого пользователя.
  • Рекомендации KB: если сертификат старше учётной записи — перевыпустить сертификат или добавить сильное сопоставление в altSecurityIdentities; если в сертификате есть SID-расширение — проверить, что SID совпадает с учётной записью; если безопасного сопоставления нет — добавить его или оставить домен в Compatibility mode, пока это возможно.
  • В Samba 4.24 изменения altSecurityIdentities и msDS-KeyCredentialLink попадают в аудит (dsdb_password_audit, dsdb_password_json_audit, action "Auth info change") — удобно для отслеживания правок сопоставлений.
  • Сертификаты разбирают командой HOWTO openssl x509 -in cacert.pem -text -out cacert.txt; там же проверяют, что в SAN есть запись типа «DS Object Guid» со значением 04 10 [Domain Controller GUID].

Подводные камни

  • full по умолчанию ломает старый вход по сертификатам. Сертификат без SID-расширения и без altSecurityIdentities не проходит строгую привязку; заранее или вместе с обновлением нужно либо перевыпустить сертификаты с SID-расширением (samba-tool ... generate-csr), либо прописать сильные сопоставления, либо временно выставить compatibility/none. У Windows поддержку реестрового ключа прекратили обновлением от 9 сентября 2025 — на смешанных доменах сроки стоит синхронизировать.
  • Семантика режимов у Samba и Windows не совпадает буквально. В Samba compatibility разрешает слабые сопоставления, но требует, чтобы сертификат был выпущен позже создания учётной записи (с поправкой certificate backdating compensation); в Windows Compatibility mode — это отдельный набор правил из KB5014754.
  • Единицы и умолчания certificate backdating compensation различаются. В smb.conf(5) это минуты, по умолчанию 0; реестровый аналог Windows CertificateBackdatingCompensation по умолчанию равен 10 минутам при отсутствии ключа (в самом KB единицы описаны как «in seconds», хотя примеры значений приведены в годах). Это разные механизмы, значения нельзя переносить напрямую.
  • Отзыв сертификатов в 4.19+ не подтягивает CRL сам. KDC не обращается к CRL distribution point и не запрашивает OCSP (Heimdal krb5.conf(5)), поэтому CRL нужно локально положить в pkinit_revoke; проверяется только первый действительный CRL для издателя, а без настроенных CRL проверка не выполняется вовсе. При этом Windows-клиенты сами требуют, чтобы у смарт-карт-сертификата был доступный CDP (иначе отзыв не проверить).
  • Вики-HOWTO устарела. Страница описывает стенд на Ubuntu Server 22.04 с Samba 4.15.5 (2022 год) и ничего не знает ни о KeyTrust, ни о строгой привязке; её ссылка на руководство Heimdal «Setting up PK-INIT» (h5l.org) больше не открывается — домен перенаправляет на GitHub. Параметры pkinit_win2k и pkinit_win2k_require_binding из блока HOWTO описаны в архивной документации Heimdal 1.5, но в актуальной man-странице Heimdal krb5.conf(5) (ветка master) они не упоминаются — перед копированием блока в конфиг проверьте, что ваша сборка их принимает.
  • enable-pkinit пишется через дефис (Heimdal), в отличие от остальных опций с подчёркиваниями; вики отмечает это отдельно.
  • /etc/krb5.conf не делайте симлинком на /var/lib/samba/private/krb5.conf (Samba 4.7+): каталог читает только root, и, например, динамические DNS-обновления при BIND_DLZ сломаются — нужна копия файла.
  • KeyTrust ограничен RSA 2048. keytrust add принимает ключ/сертификат в PEM или DER, формат определяется автоматически, но «Other types of public key are not supported» без --force; generate-csr в текущем коде тоже умеет только RSA-ключи.
  • Требования к сертификату DC жёстче, чем «лишь бы TLS работал». Нужны EKU clientAuth + serverAuth + pkInitKDC (KDC Authentication 1.3.6.1.5.2.3.5), SAN с DNS-именем и otherName msADGUID, действующий CRL distribution point и корень в NTAuth — иначе Windows-клиент откажется входить (вики, KB295663, страница Microsoft по key trust).
  • В Samba параметр называется kdc always include pac, хотя в тексте release notes 4.24.0 встречается kdc always generate pac; ориентируйтесь на таблицу параметров и smb.conf(5).
  • Атрибут msDS-KeyCredentialLink защищён валидацией и правами. По MS-ADTS 3.1.1.5.3.1.1.6 при добавлении обязательны KEY_USAGE_NGC, отсутствие CustomKeyInformation и KeyApproximateLastLogonTimeStamp, единственное значение, requestor MUST be SELF и право DS-Validated-Write-Computer; release notes заявляют, что Samba 4.24 проверяет обновления по этим правилам.
