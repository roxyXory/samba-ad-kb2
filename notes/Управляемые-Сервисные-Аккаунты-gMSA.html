База знаний Samba AD DC

Управляемые групповые сервисные учётные записи (gMSA) в Samba AD DC

Суть

gMSA (Group Managed Service Account) — сервисная учётная запись Active Directory, пароль которой не задаётся статически: контроллер домена вычисляет его из ключей KDS (Key Distribution Service) и автоматически ротирует, а служба на Unix-хосте получает текущий и предыдущий пароль либо билет Kerberos. Поддержка gMSA появилась в Samba 4.21, чем была завершена поддержка функционального уровня 2012 (FL 2012); в 4.20 были только клиентские команды чтения пароля. Samba даёт и управление учётными записями (samba-tool service-account …) с ключами KDS (samba-tool domain kds root-key …), и клиентское получение секретов (samba-tool user getpassword, samba-tool user get-kerberos-ticket). Настройка gMSA привычными Windows-инструментами (PowerShell через ADWS) Samba не поддерживает — только samba-tool.

Ключевое

Назначение и хронология

  • Samba 4.21: «Samba 4.21 adds support for gMSAs (Group Managed Service Accounts), completing support for Functional Level 2012.»
  • Зачем это нужно (дословно из release notes): «The purpose of a gMSA is to allow a single host, or a cluster of hosts, to share access to an automatically rotating password, avoiding the weak static service passwords that are often the entrypoint of attackers to AD domains. Each server has a strong and regularly rotated password, which is used to access the gMSA account of (e.g.) the database server.»
  • «Samba provides management and client tools, allowing services on Unix hosts to access the current and next gMSA passwords, as well as obtain a credentials cache.»
  • Samba 4.20 (клиентская часть): «reading the current and previous gMSA password via "samba-tool user getpassword"» и «writing a Kerberos Ticket Granting Ticket (TGT) to a local credentials cache with a new command "samba-tool user get-kerberos-ticket"». Тогда же команды чтения пароля научились работать с удалённым сервером: «permit operation against a remote server with authenticated access to "-H ldap://$DCNAME"».
  • Samba 4.21 расширила существующие команды чтения пароля: они работают и с gMSA (с аутентификацией по LDAP, через -H), и локально для учётных записей с совместимым паролем (plaintext через GPG, совместимый хэш). Перечислены samba-tool user getpassword, samba-tool user get-kerberos-ticket, samba-tool domain exportkeytab.

Ограничения

  • ADWS нет. «Windows tools for dealing with gMSAs tend to use Active Directory Web Services (ADWS) from Powershell for setting up the accounts, and this separate protocol is not supported by Samba 4.21.» Значит, создавать и настраивать gMSA в домене Samba можно только через samba-tool.
  • Kerberos вместо simple bind. «Kerberos is a better choice (gMSA accounts should not use LDAP simple binds, for reasons of both security and compatibility).»
  • Чтение пароля — от root или уполномоченного пользователя. В справке samba-tool user getpassword: «The command must be run from the root user id or another authorized user id.»
  • -H для getpassword локальный по умолчанию, но для gMSA допускается удалённый DC. «The '-H' or '--URL' option normally only supports ldapi:// or [tdb://] and can be used to adjust the local path. By default, tdb:// is used. if the target account is a group managed service account, then in this case the -H can point to a remote AD DC LDAP server.»
  • Доступ к паролю определяется атрибутом msDS-GroupMSAMembership (SDDL). Значение по умолчанию в модели gMSA — O:BAD:(A;;CCDCLCSWRPWPDTLOCRSDRCWDWO;;;LA) (константа GROUP_MSA_MEMBERSHIP_DEFAULT).

Управление учётными записями: samba-tool service-account

Состав по man-странице samba-tool(8) (версия 4.25.0): list, view, create, modify, delete и group-msa-membership с подкомандами show, add, remove. У всех подкоманд есть -H, --URL — «LDB URL for database or target server».

Опции:

Подкоманда Опции
service-account list --json — «View service accounts as JSON instead of a list»
service-account view --name — «Account name of service account to view (required)»
service-account create --name (required), --dns-host-name (required), --group-msa-membership — «Optional Group MSA Membership SDDL», --managed-password-interval — «Managed password refresh interval in days»
service-account modify --name, --dns-host-name, --group-msa-membership
service-account delete --name
group-msa-membership show --name, --json
group-msa-membership add / remove --name, --principal — «Name, DN or SID of principal to add» / «… to remove»

Как эти вызовы выглядят на практике (из blackbox-тестов Samba 4.21.0, файл python/samba/tests/samba_tool/service_account.py и group_msa_membership.py):

samba-tool service-account create --name foo --dns-host-name example.com
samba-tool service-account list
samba-tool service-account view --name foo
samba-tool service-account delete --name foo
samba-tool service-account group-msa-membership show --name gmsa$ --json
samba-tool service-account group-msa-membership add --name gmsa$ --principal alice

(имена foo, example.com, gmsa$, alice — из самих тестов; в тесте group-msa-membership передаётся готовое значение account_name, то есть с $.)

Наблюдения из тестов:

  • --name принимается без завершающего $; созданная учётная запись получает sAMAccountName foo$ (комментарий в тесте: «Since GroupManagedServiceAccount is also a Computer it ends in '$'»). Реализация Computer.find при отсутствии $ в имени сама добавляет его для поиска по sAMAccountName.
  • service-account list выводит имена с $ (foo$, bar$, baz$).
  • service-account view всегда печатает JSON; msDS-ManagedPasswordInterval по умолчанию равен 30.
  • group-msa-membership show в текстовом виде печатает Account-DN: … и DN допущенных принципалов, с --json — поля dn и trustees.
  • group-msa-membership add добавляет в msDS-GroupMSAMembership ACE с полным доступом (SEC_ADS_GENERIC_ALL) для указанного principal; если доступ уже есть, печатается «Trustee '…' is already allowed to show managed passwords for: …».
  • Сообщения команд: «Created group managed service account: …», «Modified group managed service account: …», «Deleted group managed service account: …».

KDS root key — обязательная основа

  • «Group managed service accounts rotate passwords based on root keys, which can be managed using samba-tool, with commands such as» — в release notes приведены:
samba-tool domain kds root_key create
samba-tool domain kds root_key list

Написание root_key — так в release notes; фактически подкоманда называется root-key (см. «Подводные камни»).

  • «Samba will create a new root key for new domains at provision time, but users of gMSA accounts on upgraded domains will need to first create a root key.» То есть на домене, обновлённом до 4.21, ключ создаётся вручную.
  • В исходниках 4.21.0 (python/samba/provision/__init__.py) при провижининге нового домена создаётся GKDI-ключ с комментарием «We want the GKDI key to be instantly available for use»: время начала использования берётся как current_time - KEY_CYCLE_DURATION - MAX_CLOCK_SKEW (то есть ключ сразу пригоден), в лог пишется «gkdi/gmsa root key added with guid …».
  • Команды по man-странице (4.25.0):
    • domain kds root-key create [options] — «Create KDS root keys»; опция --use-start-time («The key will be valid from this time», форматы: "now", LDIF YYYYmmddHHMMSS.0Z или ISO 8601), --json;
    • domain kds root-key list [options] — «List KDS root keys. The newest keys are listed first.»; -v, --show-secrets («Print secret or potentially sensitive attributes, namely msKds-RootKeyData and msKds-SecretAgreementParam»), --json;
    • domain kds root-key view [options] — --latest («View the most recent root key») либо --name=NAME (GUID);
    • domain kds root-key delete --name={GUID} — «Use samba-tool domain kds root-key list to find the name of the key.»
  • В тестах Samba 4.21.0 ключи создаются и перечисляются так: samba-tool domain kds root-key list --json, samba-tool domain kds root-key create -H ldap://… --json --use-start-time <время>; после создания печатается created root key <GUID>, usable from <время>. Объекты ключей лежат в конфигурационном разделе, под CN=Master Root Keys,CN=Group Key Distribution Service,CN=Services.

Получение пароля и билета

Примеры дословно из release notes 4.21.0.

NT-хэш (для NTLM) — «An example command, which gets the NT hash for use with NTLM, is»:

samba-tool user getpassword -H ldap://server --machine-pass \
TestUser1 --attributes=unicodePwd

Билет Kerberos:

samba-tool user get-kerberos-ticket -H ldap://server --machine-pass \
TestUser1 --output-krb5-ccache=/srv/service/krb5_ccache

Предыдущий NT-хэш — «gMSAs disclose a current and previous password. To access the previous NT hash, use:»

samba-tool user getpassword -H ldap://server --machine-pass TestUser1 \
--attrs=unicodePwd;previous=1

Предыдущий пароль в UTF-8:

samba-tool user getpassword -H ldap://server --machine-pass TestUser1 \
--attributes=pwdLastSet,virtualClearTextUTF8;previous=1

Пояснения к этим командам:

  • -P, --machine-pass — «Use stored machine account password» (опция Credentials Options, python/samba/getopt.py); во всех примерах release notes команды чтения пароля gMSA запускаются именно с ней.
  • --attributes — список атрибутов через запятую. unicodePwd содержит NT-хэш; виртуальный virtualClearTextUTF16/virtualClearTextUTF8 — открытый текст: «When the account is a group managed service account, and the user is permitted to access msDS-ManagedPassword then the current and previous password can be read over LDAP. Add ;previous=1 to read the previous password.» Для ;previous допустимо единственное значение: иначе выводится «Invalid attribute parameter ;previous=…, only supported value is previous=1».
  • get-kerberos-ticket: «The --output-krb5-ccache option should point to a location for the credentials cache. The default is a FILE: type cache if no prefix is specified.»
  • Имя учётной записи в этих командах — sAMAccountName («The username specified on the command is the sAMAccountName»). У gMSA, созданных Samba, sAMAccountName заканчивается на $; в тестах getpassword вызывается с полным именем (GMSA_Test_User$), тогда как в примерах release notes имя приведено без $.

Детали реализации (Samba 4.21.0)

  • Объект gMSA имеет класс msDS-GroupManagedServiceAccount; модель — наследник Computer (python/samba/domain/models/gmsa.py), учётные записи создаются в well-known контейнере Managed Service Accounts (DS_GUID_MANAGED_SERVICE_ACCOUNTS_CONTAINER).
  • Поля модели: msDS-ManagedPasswordInterval (по умолчанию 30), dNSHostName, msDS-GroupMSAMembership (по умолчанию O:BAD:(A;;CCDCLCSWRPWPDTLOCRSDRCWDWO;;;LA)), msDS-ManagedPasswordId, msDS-ManagedPasswordPreviousId.
  • Список «trustees» строится из ACE, у которых есть право SEC_ADS_READ_PROP (и тип «allow»); в тесте доступ выдаётся SDDL вида O:SYD:(A;;RP;;;S-1-5-21-…).

Подводные камни

  • root_key из release notes не сработает — подкоманда называется root-key. В исходниках 4.21.0 зарегистрирована только подкоманда root-key (python/samba/netcmd/domain/kds/__init__.py), а SuperCommand ищет имя подкоманды точным совпадением (python/samba/netcmd/__init__.py, if a in self.subcommands). Проверено запуском установленного samba-tool 4.22.11-Debian: samba-tool domain kds root_key -h отвечает «samba-tool domain kds: no such subcommand: root_key», а samba-tool domain kds root-key -h работает. Те же команды в тестах Samba и в man-страницах начиная с 4.23.0 записаны как root-key.
  • --attrs из release notes не существует. В примере release notes для предыдущего NT-хэша стоит --attrs=unicodePwd;previous=1, но у команды объявлена только опция --attributes (исходник 4.21.0; в man-странице и в справке — --attributes). Проверено запуском samba-tool 4.22.11-Debian: samba-tool user getpassword --attrs=unicodePwd TestUser1 → «error: no such option: --attrs», а с --attributes команда доходит до попытки открыть базу.
  • ;previous=1 нужно брать в кавычки. В release notes аргумент приведён без кавычек (--attrs=unicodePwd;previous=1), но ; — разделитель команд оболочки: без кавычек оболочка обрывает аргумент на ; и пытается выполнить previous=1 отдельной командой (проверено на echo в bash: без кавычек выводится только --attributes=unicodePwd, в кавычках — строка целиком). Правильно: --attributes='unicodePwd;previous=1'.
  • На обновлённых доменах KDS root key надо создать самому. provision создаёт ключ только для новых доменов; «users of gMSA accounts on upgraded domains will need to first create a root key» — без ключа пароли gMSA не будут вычисляться. Не забудьте про samba-tool domain kds root-key create.
  • ADWS/PowerShell не поддержан (Samba 4.21): настройка gMSA выполняется только через samba-tool; Windows-инструменты, работающие через ADWS, в домене Samba не помогут.
  • gMSA не должны использовать LDAP simple bind — только Kerberos (release notes); практический смысл — получать билет (get-kerberos-ticket) и работать через него.
  • Доступ к чтению пароля выдаётся отдельно. msDS-GroupMSAMembership по умолчанию — O:BAD:(A;;CCDCLCSWRPWPDTLOCRSDRCWDWO;;;LA); чтобы конкретный хост/служба могли получать пароль, principal нужно добавить явно: samba-tool service-account group-msa-membership add --name <имя> --principal <sAMAccountName|DN>. Сама команда чтения пароля выполняется от root или уполномоченного пользователя, а --machine-pass использует пароль машинной учётной записи хоста.
  • Резервные копии. В Samba 4.23 samba-tool domain backup --no-secrets стал полностью удалять объекты класса msKds-ProvRootKey (раньше «it could still contain confidential attributes, including BitLocker recovery data and KDS root keys»). На более старых версиях бэкап, сделанный с --no-secrets, мог содержать KDS-ключи.
  • Man-страницы отстают от кода. В samba-tool(8) версий 4.21.5 и 4.22.0 команды domain kds root-key вообще не документированы (раздел появляется только в man-странице 4.23.0), хотя сами команды есть в 4.21.0. Команды service-account в man-странице 4.21.5 уже есть, а в 4.20.8 их нет — управление gMSA действительно новое в 4.21.
