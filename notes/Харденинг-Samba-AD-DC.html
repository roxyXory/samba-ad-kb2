База знаний Samba AD DC

Харденинг Samba AD DC

Суть

Страница вики «Hardening Samba as an AD DC» — готовый чек-лист усиления контроллера домена: какие параметры smb.conf нельзя ослаблять, какие стоит включить (по умолчанию они выключены), что делать на самом хосте (AppArmor/SELinux, замена автогенерируемого TLS-сертификата), как защитить секреты на диске и какие общедоменные настройки (LDAP-политики, Protected Users, парольные политики) стоит пересмотреть. Авторы подчёркивают: список не исчерпывающий, а «значения по умолчанию» некоторых опций исторически слабее, чем хотелось бы. Последняя правка страницы по данным API вики — 3 декабря 2025 (Bjacke, правка раздела ntlm auth).

При сверке с актуальным smb.conf(5) и release notes обнаруживаются расхождения в названиях параметров и в описании «будущих» возможностей — они вынесены в «Подводные камни», потому что на них легко ошибиться при копировании конфига из вики.

Ключевое

Аудит-логи

  • Страница: аудит-логи AD DC настраиваются параметром log level и на усиленной установке должны обрабатываться системой анализа логов. Подробности настройки и форматы (обычный и JSON) — в Аудит и JSON логи Samba.
  • Далее по странице есть отдельная секция про парольные политики (см. ниже): lockout по умолчанию выключен, минимальная длина пароля мала.

ldap server require strong auth

  • Причина появления опции — атаки на LDAP, известные как NTLM forwarding или «pass the hash». Если параметр выставлен в no или allow_sasl_over_tls, аутентификация привилегированного пользователя или компьютера к SMB-серверу может быть перенаправлена на LDAP-сервер, что позволяет имперсонацию. Усиленная установка сохраняет значение по умолчанию — yes.

  • Цитата со страницы: «It is more secure to use Kerberos with Kerberos encryption directly».

  • smb.conf(5) (текущая версия, 4.25): возможные значения — no, allow_sasl_without_tls_channel_bindings, yes, по умолчанию yes. Значения сопоставлены с Windows-параметром LdapEnforceChannelBinding в HKLM\SYSTEM\CurrentControlSet\Services\NTDS\Parameters\: no = 0, allow_sasl_without_tls_channel_bindings = 1, yes = 2.

  • allow_sasl_over_tls в текущем мануале — «just an alias of allow_sasl_without_tls_channel_bindings, but it will be removed in future versions»; конфигурации советуют переводить на yes или (если действительно нужно) на allow_sasl_without_tls_channel_bindings.

  • История: опция ldap server require strong auth появилась вместе с исправлением CVE-2016-2112 в ветках 4.4.1 / 4.3.7 / 4.2.10 со значением по умолчанию yes. Эти сборки были «privately released to vendors, but had a regression», поэтому публичными security-релизами стали 4.4.2 / 4.3.8 / 4.2.11 (advisory CVE-2016-2112), а Updating Samba по-прежнему отсчитывает появление опции от 4.4.1/4.3.7/4.2.10 — при обновлении ориентируйтесь на исправленную тройку (подробнее — LDAPS Сертификаты AD DC и Обновление Samba, где разобраны те же версии). Приложения, ходящие в AD по LDAP без TLS, получают ошибку:

    ldap_bind: Strong(er) authentication required (8)
       additional info: BindSimple: Transport encryption required.

  • Что изменилось в 4.21 (release notes): сервер LDAP теперь поддерживает SASL-binds (kerberos или NTLMSSP) поверх TLS (ldaps или starttls) с корректными TLS channel bindings. Установки, где раньше требовалось ldap server require strong auth = allow_sasl_over_tls, «can now most likely move to the default of ldap server require strong auth = yes». Если SASL-binds без корректных channel bindings всё же нужны — используйте allow_sasl_without_tls_channel_bindings; значение allow_sasl_over_tls «will generate a warning in every start of 'samba', as well as '[samba-tool ]testparm'».

ntlm auth

  • Страница: NTLM — «56-bit encryption at best and compromised badly for well-known word lists». С точки зрения пассивного атакующего no (оно же ntlmv2-only) и значение для MSCHAPv2 одинаково небезопасны, потому что криптография одна и та же; MSCHAPv2 оставлен, так как его труднее устранить, он не предъявляется на административных интерфейсах и может быть защищён TLS-туннелем.
  • Для полностью усиленной установки страница предписывает: disabled — требуются только Kerberos или simple-bind, поскольку «even NTLMv2 is quite poor security in 2023».
  • smb.conf(5): значения ntlmv1-permitted (alias yes), ntlmv2-only (alias no), mschapv2-and-ntlmv2-only, disabled; по умолчанию ntlm auth = ntlmv2-only. При disabled не принимаются ни NTLM, ни LanMan, ни смена паролей по NTLM.
  • Предупреждение мануала (важно для DC): и Microsoft Windows, и Samba RODC преобразуют простой текстовый LDAP Simple Bind в аутентификацию NTLMv2, которую пересылают на полный DC, поэтому disabled сломает такие пересылаемые аутентификации. Кроме того: «these settings apply only to local users… To control NTLM authentication for domain users, this option must be configured on each DC».

lanman auth

  • Страница: Samba 4.17 удалила LanMan-аутентификацию; если у вас Samba 4.16 и старше — убедитесь, что lanman auth остался в значении по умолчанию no.
  • Release notes 4.17 подтверждают: «The storage and authentication with LanMan passwords has been entirely removed from the Samba AD DC, even when 'lanman auth = yes' is set». В текущем smb.conf(5) параметр помечен устаревшим с Samba 4.13.

nt hash store — в вики он назван «allow store nt hash»

  • Страница вики называет опцию allow store nt hash и пишет, что Samba 4.17 получила эту опцию, позволяющую не хранить NT-хеш. В актуальном smb.conf(5) параметра allow store nt hash нет вовсе — параметр называется nt hash store (это же имя в таблице изменений release notes 4.17: «nt hash store — New parameter — always»).
  • Возможные значения (smb.conf(5)): always (значение по умолчанию), never (не хранить NT-хеш для пользовательских аккаунтов, только для машинных), auto (хранить, если ntlm auth не выставлен в disabled). Харденинг по вики: never.
  • Зачем: NT-хеш не засолен и требуется для аутентификации NTLM, NTLMv2, MSCHAPv2 и для Kerberos-типа arcfour-hmac-md5; цель опции — не хранить хеш, который не будет использоваться, поскольку он представляет уязвимость при утечке базы.
  • Последствия отключения (мануал и release notes 4.17): для новых и изменённых аккаунтов NT-хеш не хранится в sam.ldb (кроме trust-аккаунтов — компьютеров, DC и межлесных доверий); тип ключа arcfour-hmac-md5 в KDC для этих пользователей недоступен (современные клиенты выберут AES). История паролей в AD хранится как NT-хеш, поэтому применяется обходной путь через Kerberos-хеши: хранятся текущий, предыдущий и предпредыдущий пароли (то есть история длиной 3). Так как эти значения засолены, смена sAMAccountName, userAccountControl или userPrincipalName меняет соль — после редкого совпадения переименования и смены пароля для истории будет распознан только текущий пароль.
  • Значение по умолчанию проверено по исходникам тега 4.25.0: source3/param/loadparm.c:731 — Globals.nt_hash_store = NT_HASH_STORE_ALWAYS;; docs-xml/smbdotconf/security/nt_hash_store.xml — <value type="default">always</value>.

Протоколы SMB: server min protocol, client min protocol, client ipc min protocol

  • Страница: современные версии Samba по умолчанию используют SMB2 и выше; усиленная установка не должна выставлять эти параметры в значения вроде NT1, включающие поддержку SMB1. Отказ от SMB1 убирает поддержку NTLMv2 без NTLMSSP (менее безопасна, чем NTLMv2 внутри NTLMSSP, например в SMB2) и большой объём старого C-кода Samba; протоколы подписи сообщений (integrity protection) в SMB2 существенно лучше.
  • Значение по умолчанию в smb.conf(5): server min protocol = SMB2_02.

smb1 unix extensions, unix extensions

  • Актуально, только если включён SMB1. Символические ссылки SMB1 unix extensions позволяют создать на сервере ссылку в выбранное пользователем место; работа по защите от последования таких ссылок завершена, но лучше вообще не разрешать создание таких симлинков. Усиленная установка сохраняет значение по умолчанию no.

NETLOGON secure channel (schannel)

  • Значения по умолчанию этих опций менять не следует (перечислены на странице): allow nt4 crypto = no, reject md5 clients = yes, server schannel require seal = yes, server schannel = yes.
  • Если конкретным клиентским хостам нужна устаревшая криптография NETLOGON, страница отсылает к smb.conf(5) за персональными переопределениями. Мануал прямо предупреждает: все эти опции устарели и в будущем будут удалены, а их ослабление — проблема безопасности. Вместо глобальных значений используйте исключения по компьютерным аккаунтам (имя — sAMAccountName с завершающим $):
    • server require schannel:COMPUTERACCOUNT = no (вместо server schannel = auto),
    • server schannel require seal:COMPUTERACCOUNT = no,
    • allow nt4 crypto:COMPUTERACCOUNT = yes,
    • server reject md5 schannel:COMPUTERACCOUNT = no.
  • Ссылки в мануале: CVE-2020-1472 (ZeroLogon) и CVE-2022-38023. Дополнительно: reject md5 clients отклоняет клиентов без NETLOGON_NEG_SUPPORTS_AES (появился в Windows 7/Server 2008R2, в Samba с 4.0), а allow nt4 crypto управляет использованием 64-битных ключей; значение по умолчанию у reject md5 clients изменено с no на yes патчами CVE-2022-38023.

tls priority и GnuTLS

  • Samba может передать криптопровайдеру GnuTLS строку приоритетов, описывающую, какие TLS-протоколы поддерживать, а какие — нет; допустимые строки — в GnuTLS Priority-Strings. Опция tls priority полезна, чтобы отключить недавно ставший уязвимым TLS-протокол. Значение по умолчанию в Samba (и в современном GnuTLS) гарантирует, что SSLv3 отключён: tls priority = NORMAL:-VERS-SSL3.0 (значение дописывается к списку приоритетов GnuTLS по умолчанию).

  • Пример со страницы LDAPS (отключает дополнительно TLS 1.0 и 1.1):

    tls priority = NORMAL:-VERS-TLS1.0:-VERS-TLS1.1

Замена автогенерируемого TLS-сертификата

  • Страница: Samba автоматически генерирует TLS-сертификат для службы LDAP; его следует заменить на корректно подписанный сертификат, которому доверяют и который проверяют клиенты организации. Расположением файлов управляют параметры tls cafile, tls certfile, tls crlfile, tls dh params file, tls keyfile. По состоянию на страницу: «Currently Samba will need to be restarted when these files are updated».
  • Практические детали (имена файлов, 700 дней жизни автогенерируемого сертификата, права 0600, PEM-формат, CN = FQDN DC, команды openssl, перезагрузка сертификатов на 4.19+ через smbcontrol ldap_server reload-certs) разобраны в LDAPS Сертификаты AD DC.
  • 4.19.0 release notes: TLS-сертификаты AD DC LDAP-сервера раньше читались только при запуске, теперь их можно перезагружать «на лету» командой smbcontrol ldap_server reload-certs — то есть утверждение страницы про обязательный рестарт устарело для 4.19 и новее.

Шифрование секретов на диске (encryption at rest)

  • AD DC Samba поддерживает шифрование «на диске» паролей и других секретных значений (для фиксированного списка атрибутов). Чтобы воспользоваться этим полностью, нужны два шага усиления и управление ключом.
  • --plaintext-secrets в samba-tool domain provision или samba-tool domain join задавать нельзя. По умолчанию шифрование включено; даже без управления ключом оно устраняет ряд атак на базу через память, разделяя ключ и зашифрованные данные.
  • Список атрибутов из release notes 4.8 (когда появилось шифрование): pekList, msDS-ExecuteScriptPassword, currentValue, dBCSPwd, initialAuthIncoming, initialAuthOutgoing, lmPwdHistory, ntPwdHistory, priorValue, supplementalCredentials, trustAuthIncoming, trustAuthOutgoing, unicodePwd, clearTextPassword. Шифрование включено по умолчанию при новом provision или join и может быть отключено при provision/join опцией --plaintext-secrets; «However, an in-place upgrade will not encrypt the database».
  • Убедитесь, что sam.ldb создана на Samba 4.8 или новее: база AD DC, непрерывно обновлявшаяся «на месте» с более старой версии, не получит эту возможность и продолжит писать секреты в sam.ldb в открытом виде. Правильный путь — присоединить к домену новый DC на современной Samba, а исторически «до-4.8» DC понизить (см. Присоединение второго DC к домену, Понижение роли AD DC).
  • Ключ private/encrypted_secrets.key: Samba не пытается управлять им. Усиленный DC может подавать этот файл Samba при старте — например, с рамдиска, получив ключ из хранилища секретов. Страница честно предупреждает, что это лишь частичное решение: в private/ есть и другие секретные файлы (secrets.keytab, host-пароли в secrets.tdb и secrets.ldb), для которых специальной инженерной работы не делалось.

Харденинг хоста: AppArmor и SELinux

  • Samba в некоторых дистрибутивах идёт с обширным набором правил AppArmor (замечено в openSUSE/SUSE) или SELinux (Fedora, RHEL), ограничивающих доступ Samba только к нужным частям файловой системы. Отключать эти правила не следует. Команда Samba не сопровождает такие методы харденинга, но рекомендует использовать пакеты, где они подготовлены и протестированы.
  • Подробнее — в SELinux и AppArmor для Samba AD DC.

Харденинг сборки

  • Система сборки Samba и многих пакетов Samba закаляет код против части атак на C-код. Подробности — в разделе «Hardening practices» страницы Samba Security Documentation: используются опции безопасности компилятора, статический анализ, ограничение прав на чувствительные файлы, меры против переполнения буфера; Debian собирает с DEB_BUILD_MAINT_OPTIONS = hardening=+all, Fedora — со стандартным hardening (кроме -Wl,-z,defs). Samba никогда не нуждается в исполняемом стеке или куче.
  • Там же: все файлы Samba с ключами защищены ограничительными правами — для AD-операций Samba работает от root, файлы имеют режим 0600 и владельца root, а приватные файлы лежат в подкаталоге (в тексте — privat/, опечатка источника) с режимом 0700.

lDAPAdminLimits MaxQueryDuration

  • Страница: Samba соблюдает [MS-ADTS] lDAPAdminLimits MaxQueryDuration, но значение по умолчанию — 120 секунд. Это очень много: worker, обрабатывающий такой запрос, всё это время не обрабатывает другие запросы. Значение стоит понизить. Запросы длительностью более 25 % от максимума логируются на уровне log level = 3.
  • Спецификация Microsoft подтверждает: политики задаются атрибутом lDAPAdminLimits (мультизначная строка, где имя и значение разделены =, — пример из спецификации: MaxActiveQueries=0), значение по умолчанию MaxQueryDuration — 120 секунд; при достижении лимита DC возвращает timeLimitExceeded.
  • Готовой команды для смены этого значения в проверенных источниках нет — страница вики её не приводит.

Protected Users

  • Protected Users (реализовано в Samba 4.17 и новее) не могут использовать NTLM, ограничены в делегировании Kerberos (когда один сервер действует от имени пользователя на другом) и имеют укороченное время жизни тикетов. Windows-клиенты также распознают защищённых пользователей и применяют локальные защиты для этих аккаунтов.

  • Из release notes 4.17 — конкретные защиты для аккаунтов в группе: NTLM-аутентификация отключена; TGT, зашифрованные RC4, не выдаются и не принимаются (тикеты с AES и сервисные тикеты с RC4 не затронуты); время жизни TGT ограничено четырьмя часами; ограниченное и неограниченное делегирование Kerberos отключено. Защиты предназначены только для пользовательских аккаунтов — сервисные и компьютерные аккаунты в группу добавлять не следует.

  • Группа идентифицируется в домене RID 525, поэтому создавать её нужно только через samba-tool со специальным параметром:

    samba-tool group add 'Protected Users' --special

    Для удалённого сервера в release notes приведён вариант samba-tool group add 'Protected Users' --special -H ldap://dc1.example.com -U Administrator.

Парольные политики и check password script

  • Samba поддерживает доменные и гранулярные (Fine-Grained) парольные политики / Password Setting Objects (PSO). Доменные политики можно задавать через GPO, если установлено apply group policies = yes (значение по умолчанию — no), но прямой метод — правка значений в LDAP или samba-tool domain passwordsettings. Гранулярные — через samba-tool domain passwordsettings pso (подкоманды create, set, list, show, apply, unapply, delete, show-user).

  • Значения по умолчанию в Samba (таблица со страницы): сложность пароля — on; хранение открытых паролей — off; длина истории — 24; минимальная длина — 7; минимальный возраст — 1 день; максимальный возраст — 42 дня; блокировка аккаунта — 30 минут; порог блокировки — 0 (никогда); сброс счётчика попыток — 30 минут. Значения совпадают с Windows, но в усиленном домене их следует ужесточить: обязательно включить блокировку (порог 0 → ненулевой) и заметно увеличить минимальную длину пароля.

  • check password script — путь к программе проверки сложности пароля: пароль подаётся ей на стандартный вход, программа должна вернуть 0 для хорошего пароля и любое другое значение для плохого (иначе смена пароля не состоится). На AD DC скрипт запускается от root («In Samba AD, this script will be run AS ROOT by samba(8) without any substitutions»). Начиная с Samba 4.11 скрипту экспортируются переменные SAMBA_CPS_ACCOUNT_NAME (всегда), SAMBA_CPS_USER_PRINCIPAL_NAME и SAMBA_CPS_FULL_NAME (если есть). В каталоге примеров есть программа crackcheck, использующая cracklib:

    check password script = /usr/local/sbin/crackcheck

    Страница вики замечает, что cracklib, который использует crackcheck, устарел — его вытеснили инструменты, проверяющие большие базы утечек паролей.

Небезопасные обновления DNS

  • Samba можно настроить так, чтобы неаутентифицированные клиенты обновляли записи динамического DNS. Значение по умолчанию allow dns updates = secure only и его следует сохранять (возможные значения: disabled, secure only, nonsecure).

Шифрование Kerberos: AES по умолчанию в 4.24/4.25 (CVE-2026-20833)

  • Release notes 4.24.0 и 4.25.0 (в вики и в официальных notes) заявляют одно и то же: значение по умолчанию параметра kdc default domain supported enctypes теперь соответствует aes128-cts-hmac-sha1-96 aes256-cts-hmac-sha1-96 (оба типа шифрования AES), если функциональный уровень домена 2008 или выше. Указанная причина — CVE-2026-20833.

  • В таблице изменений smb.conf у 4.24.0 и 4.25.0: kdc default domain supported enctypes — «New default» — «AES encryption types (if supported by domain)».

  • smb.conf(5) объясняет значение по умолчанию 0: это «maps to what the software supports currently» — AES-типы, если ключи AES доступны (функциональный уровень домена 2008+), иначе arcfour-hmac-md5 aes256-cts-hmac-sha1-96-sk. Параметр задаёт значение msDS-SupportedEncryptionTypes для сервисных аккаунтов, у которых атрибут отсутствует или равен 0 (аналог ветки реестра HKLM\System\CurrentControlSet\services\KDC\DefaultDomainSupportedEncTypes в Windows).

  • Смежная опция kdc force enable rc4 weak session keys (по умолчанию no) позволяет KDC считать, что rc4-hmac сессионный ключ может использоваться по запросу потенциально старого клиента, независимо от msDS-SupportedEncryptionTypes.

  • Рекомендованная конфигурация KDC из release notes 4.24:

    strong certificate binding enforcement                            full
kdc always include pac                                            yes
kdc require canonicalization                                      yes

    Если kdc require canonicalization = yes использовать нельзя, в notes советуют по возможности выставить kdc name match implicit dollar without implicit canonicalization = no.

Подводные камни

  • Название параметра в вики не совпадает с настоящим. Страница называет опцию allow store nt hash, тогда как в smb.conf(5) и в release notes 4.17 она называется nt hash store (значения always / never / auto). Параметра allow store nt hash в текущем мануале нет вовсе — проверяйте итоговый конфиг через testparm.
  • В мануале описания nt hash store расходятся. В разделе про ntlm auth тот же smb.conf(5) называет значением по умолчанию auto, а в конце описания nt hash store стоит Default: nt hash store = always; в исходниках тега 4.25.0 зашито NT_HASH_STORE_ALWAYS (source3/param/loadparm.c:731). Ориентируйтесь на always как на фактическое умолчание.
  • Значение allow-mschapv2 из вики в мануале отсутствует. Для ntlm auth текущий smb.conf(5) перечисляет ntlmv1-permitted (alias yes), ntlmv2-only (alias no), mschapv2-and-ntlmv2-only, disabled — значения allow-mschapv2 в списке нет.
  • nt hash store = never ломает часть сценариев: история паролей сокращается до трёх значений, а после переименования аккаунта вместе со сменой пароля распознаётся только текущий пароль; из-за отсутствия NT-хеша недоступен Kerberos-тип arcfour-hmac-md5, то есть клиенты, умеющие только RC4, перестанут проходить аутентификацию. Trust-аккаунты (компьютеры, DC, межлесные доверия) NT-хеш всё равно сохраняют.
  • ntlm auth = disabled на DC ломает пересылаемый NTLM. Windows и Samba RODC преобразуют текстовый LDAP Simple Bind в NTLMv2, который пересылают на полный DC, — при disabled такие аутентификации будут отклонены (предупреждение smb.conf(5)).
  • Раздел «Future possible hardening» на странице устарел. Вики утверждает, что Samba не выставляет channel bindings как клиент и не проверяет их как сервер «at this time», и что новая опция может появиться в будущем. На самом деле поддержка SASL over TLS с корректными TLS channel bindings появилась в 4.21 (release notes), а текущий smb.conf(5) описывает значения ldap server require strong auth именно в терминах channel bindings.
  • Вики-страница «Configuring LDAP over SSL (LDAPS) on a Samba AD DC» тоже отстала от 4.21 (это вики-источник заметки LDAPS Сертификаты AD DC, а не сама заметка): она описывает allow_sasl_over_tls без упоминания, что с 4.21 это лишь alias, вызывающий предупреждение при каждом старте samba и в testparm (и подлежащий удалению).
  • Опции NETLOGON намеренно устаревают. allow nt4 crypto, reject md5 clients, server schannel, server schannel require seal помечены в мануале как deprecated и будут удалены; вместо ослабления этих глобальных значений для старых клиентов используйте персональные исключения по COMPUTERACCOUNT (см. выше).
  • Шифрование секретов не лечится in-place обновлением. База, обновлявшаяся с версии до 4.8, продолжит писать секреты в открытом виде; нужен новый DC (provision/join на современной версии) и понижение старого. Ключ private/encrypted_secrets.key Samba не администрирует, и даже вынос его в хранилище — лишь частичное решение: secrets.keytab и host-пароли в secrets.tdb/secrets.ldb остаются неуправляемыми.
  • --plaintext-secrets отключает свойство защиты. Опция предназначена для отказа от шифрования секретов при provision/join; на усиленной установке её быть не должно.
  • check password script выполняется от root на AD DC. Скрипт получает пароль на stdin и должен возвращать 0 для хорошего пароля. Отдельная сложность с подстановкой %u — это CVE-2026-4408 (RCE на файловых серверах и классических DC с samba-dcerpcd в системной службе); AD DC не затронуты, так как не раскрывают имя пользователя через %u, но скрипт по-прежнему исполняется с правами root.
  • Максимальный возраст пароля: 42 или 43 дня. Свежесозданный домен Samba получает maxPwdAge: -36288000000000 (42 дня) из source4/setup/provision_basedn_modify.ldif:36, а samba-tool domain passwordsettings set --max-pwd-age=default выставляет 43 (python/samba/netcmd/domain/passwordsettings.py:228, то же значение в подсказке --help). Сброс «в значение по умолчанию» на день отличается от исходного.
  • Понижение MaxQueryDuration не бесплатно: по достижении лимита DC возвращает ошибку timeLimitExceeded, а долгие запросы (свыше 25 % лимита) начинают попадать в лог на уровне 3. Значение по умолчанию — 120 секунд.
  • Доменную парольную политику через GPO применяют только при apply group policies = yes (по умолчанию no); иначе используйте прямой метод (samba-tool domain passwordsettings или LDAP). По умолчанию порог блокировки равен 0, то есть блокировки аккаунтов нет вовсе.
