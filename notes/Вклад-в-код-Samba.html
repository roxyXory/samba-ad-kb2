Вклад в код Samba

Суть

Страница описывает, как вносить вклад в проект Samba: от поддержки пользователей и тестирования до отправки патчей. Предпочтительный способ отправки патчей — merge request (MR) в официальном зеркале https://gitlab.com/samba-team/samba на GitLab.com. Страница также фиксирует правила: политику авторских прав (Copyright Policy), требования к коммитам и тестам, процесс код-ревью (см. Код ревью) и альтернативный способ — патчи в список рассылки samba-technical.

Ключевое

Способы помочь проекту

Как и все OpenSource-проекты, Samba зависит от волонтёров; специальные навыки не обязательны. Категории работы:

  • улучшение документации;
  • ответы на вопросы пользователей и разбор issues в списке рассылки Samba users (https://lists.samba.org/mailman/listinfo/samba);
  • обновление и написание статей Wiki;
  • помощь в тестировании, особенно готовящегося релиза или master (https://wiki.samba.org/index.php/Samba_Release_Planning#Upcoming_Release), чтобы найти ошибки до финального релиза;
  • сообщение об ошибках в Bugzilla (http://bugzilla.samba.org);
  • проверка (verify) патчей в Bugzilla и в merge requests (https://gitlab.com/samba-team/samba/-/merge_requests);
  • создание патчей (разработчики на C и Python);
  • всё остальное, что вы можете предложить.

Участвуя в сообществе Samba, следуйте рекомендациям страницы Как делать Samba хорошо (How to do Samba: Nicely). Перед началом работы прочтите политику авторских прав: https://www.samba.org/samba/devel/copyright-policy.html.

Подготовка окружения разработки

git clone https://git.samba.org/samba.git
  • Новые возможности и исправления сначала разрабатываются в ветке master и только потом переносятся (backport) в релизные ветки.
  • Для установки зависимостей сборки запустите скрипт bootstrap.sh для вашей ОС из каталога bootstrap/generated-dists/ (см. Package Dependencies Required to Build Samba).

Первый merge request

  1. Начните с малого. Если это не исправление опечатки или однострочное изменение, изучите полные инструкции по созданию серий патчей Samba (страница Creating Gitlab Merge Requests) до создания патчей — это избавит от переделок.

  2. Заведите аккаунт на GitLab.com (https://gitlab.com/users/sign_in#register-pane); можно войти через аккаунт GitHub.

  3. Сделайте fork официального зеркала https://gitlab.com/samba-team/samba. Этого достаточно для первых и небольших вкладов; для постоянной работы запросите доступ к репозиторию samba-devel (Samba on GitLab → Getting Access).

  4. Добавьте remote для своего форка (URL показывается в GitLab под синей кнопкой Clone):

    $ git remote add gitlab-$USER git@gitlab.com:$USER/samba.git

  5. В настройках форка измените таймаут CI (по умолчанию 1 час): рекомендуется 3 часа — это допустимо на бесплатных runner'ах.

  6. Там же очистите поле CI/CD configuration file: новый форк копирует неподходящий конфиг из мастер-проекта; верните значение по умолчанию (пустое).

  7. Подготовьте патчи (см. ниже) и отправьте их в свой форк:

    $ git push gitlab-$USER -f

  8. Создайте merge request (после push появится ссылка). Предварительно посмотрите примеры хороших и плохих MR (Creating Gitlab Merge Requests → Examples). MR попадёт в очередь на ревью членам Samba Team (https://www.samba.org/samba/team/).

Подготовка патчей

  • Стандарты кодирования — файл README.Coding.md в корне исходников.
  • Каждый патч должен быть настолько мал, насколько возможно, — менять только одну вещь: это упрощает ревью.
  • У патча должно быть уместное описание коммита.
  • Патчи, исправляющие ошибку, должны содержать тег BUG:.

Copyright Policy и теги. Политика авторских прав требует обязательных тегов в каждом git-коммите, прежде всего Signed-off-by (см. CodeReview → commit message tags). Samba — проект с распределённым владением авторскими правами: соблюдение политики подтверждает ваше право и намерение внести вклад и лицензию, под которой он делается.

Хорошее сообщение коммита должно включать:

  • краткое описание исправления/возможности с указанием версии Samba и компонента, затем пустая строка;
  • более подробное описание;
  • номер ошибки, если есть (обязателен для backport'ов в релизную ветку — сначала заведите баг);
  • описание для release notes, начинающееся с RN: (формулировка должна быть понятна администраторам);
  • ваш тег Signed-off-by согласно Copyright Policy.

Пример со страницы:

s3:smbd: Add new funky shiny and groovy feature

The funky shiny and groovy feature has been added to
be able to do whatever you like. A typical usecase is the
following.

BUG: https://bugzilla.samba.org/show_bug.cgi?id=1
RN: Fix problem xyz.

Signed-off-by: Author <author@example.org>

Включайте тесты. Большинство изменений должно сопровождаться тестом; тесты запускаются командой make test из дерева исходников Samba. Виды тестов:

  • Написание torture тестов — smbtorture в каталоге source4/torture, прямые тесты протокола на C;
  • Writing Python Tests — если протокол DCERPC, Python-биндинги уже автосгенерированы PIDL; LDAP доступен через LDB;
  • Writing cmocka Tests — идеально для юнит-тестов C-функций;
  • LDB — тесты в lib/ldb/tests, начиная с Samba 4.21 запускаются через верхнеуровневый make test;
  • CTDB — тесты-оболочки в ctdb/tests, запускаются через make test внутри ctdb.

Последующие MR и общий репозиторий разработки

Поскольку Samba Team содержит собственные GitLab-runner'ы для полного набора тестов, используется один общий «песочный» репозиторий разработки вместо персональных форков:

  • после ревью первого MR (когда убедятся, что вы реальный контрибьютор) вам могут выдать доступ к репозиторию https://gitlab.com/samba-team/devel/samba;
  • если первый MR сложный, ревьюер, вероятно, сам зальёт его туда (и приложит ссылку на pipeline) или попросит вас;
  • при переносе закройте исходный MR и откройте новый с пометкой: This replaces !123 submitted from a private fork.
  • для сложных изменений изучите страницу Creating a Samba patch series.

Правила общего репозитория:

  • используйте его только для разработки Samba; не затирайте работу других;
  • именуйте ветки с префиксом — вашим именем пользователя GitLab: $USER/topic (описание работы в имени ветки упрощает создание MR — имя ветки становится шаблоном заголовка);
  • взамен вы получаете полный прогон CI на ресурсах Samba Team, что облегчает Код ревью.

Пошаговые команды:

$ git remote add gitlab-ci git@gitlab.com:samba-team/devel/samba.git
$ git checkout -b $USER/foo
$ git push gitlab-ci -f

Pipelines и отладка CI

Push ветки в samba-team/devel/samba запускает полную CI-сборку:

  • результаты CI: https://gitlab.com/samba-team/devel/samba/pipelines;
  • каждый merge request показывает ссылку на результаты pipeline;
  • как это устроено: Samba CI on gitlab/Under the hood (CI Samba на GitLab);
  • отладка падений CI: Samba CI on gitlab/Debugging CI failures.

Код-ревью и слияние в master

  • Ответственность отправителя: ревьюер укажет, скорее всего, лишь один экземпляр каждой проблемы — вы обязаны найти и исправить все такие места в коде перед повторной отправкой.
  • Процесс: члены Samba Team reviewing комментируют MR; более широкие обсуждения идут в списке рассылки — подпишитесь на samba-technical (https://lists.samba.org/mailman/listinfo/samba-technical).
  • Патчи от не-членов команды требуют минимум 2 ревью от членов Samba Team перед слиянием. Сторонние контрибьюторы могут участвовать в ревью — хороший способ изучить Samba.
  • Слияние (для членов команды): скачать патч, например https://gitlab.com/samba-team/samba/merge_requests/12.patch, добавить теги ревью и выполнить git autobuild локально; после завершения autobuild закрыть MR комментарием вида Merged into master as <git hash> for Samba <next version>.

Отправка патчей в список рассылки

Очень небольшая часть патчей приходит напрямую через рассылку: сформируйте патчи командой git format-patch и отправьте письмом в список samba-technical, включив тег Signed-off-by. Требуемый формат набора патчей — один файл-бандл, приложенный к письму:

git format-patch --stdout origin/master > master-featureX-01.patches.txt

Минусы этого пути: ручная обработка на стороне проекта; для отправки нужна подписка; патч могут пропустить; нет мгновенной обратной связи по ошибкам компиляции и тестам; CI всё равно требуется — разработчик Samba сам отправит патч в GitLab и сообщит ссылку на результаты. Поэтому, если можете, отправляйте merge request: последняя версия патчей остаётся в списке открытых MR и не будет забыта.

Bugzilla

  • Новые патчи для master не следует отправлять только в Bugzilla — отправляйте их в GitLab и указывайте merge request в поле See Also бага.
  • Bugzilla используется для процедуры чек-инов в релизные ветки (Samba Release Planning → Release Branch Check-in Procedure, см. Планирование релизов Samba).

Подводные камни

  • Таймаут CI в форке: по умолчанию на gitlab.com pipelines ограничены 1 часом. Без увеличения (рекомендуется 3 часа) push завершится ошибкой:

    ERROR: Job failed: execution took longer than 1h0m0s seconds
The script exceeded the maximum execution time set for the job

  • CI-конфиг форка: новый форк копирует неподходящий файл CI/CD-конфигурации из мастер-проекта — сбросьте настройку CI/CD configuration file в пустое значение.

  • git send-email в проекте Samba не допускается (not permitted): письма, разосланные этой командой напрямую в список, без ручной правки получателем атрибутируются адресу списка samba-technical@..., а не вашему собственному — авторство патча теряется. Это не противоречит разделу «Отправка патчей в список рассылки» выше: там бандл git format-patch прикладывается к письму файлом, что атрибуцию сохраняет.

  • Кнопка Merge в GitLab не работает для слияния в master — члены команды используют локальный git autobuild.

  • В общем репозитории разработки не перезаписывайте работу других и всегда начинайте имена веток с имени пользователя ($USER/topic).

  • Разработка только в master: новые возможности и исправления сначала делаются в master; backport'ы в релизные ветки — отдельная процедура через Bugzilla.

  • Патчи от не-членов команды требуют минимум двух ревью от членов Samba Team перед слиянием.
